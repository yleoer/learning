# 第 1 章 硬件基础、CPU 执行与缓存架构

## 本章要点

操作系统与应用程序最终都运行在物理硬件之上，不理解 CPU 的执行方式与存储层次，就难以看清上下文切换、锁争用、内存延迟和浮点误差背后的真实成本。本章整合原书《图解系统》第 1 章的硬件内容，去掉多处重复的存储层级铺垫，沿着“指令如何执行 → 数据如何缓存 → 多核如何保持一致 → 数值如何编码”四条主线展开，并对原书中 64 位指令长度、分支预测归因和存储延迟等处进行现代硬件校准。

读完本章后，应能说明 CPU 执行一条指令的流水线阶段与性能公式，准确区分硬件位宽与 64 位软件 ABI，解释局部性、分支预测失败与伪共享对代码性能的决定性影响，掌握 MESI 状态机及现代多核缓存一致性演进，并能推导负数补码与 `0.1 + 0.2 != 0.3` 的底层成因。

> 核对日期：2026 年 11 月 20 日；核对环境为 Linux 6.12 LTS 文档、Intel 64/IA-32 与 ARMv8-A 架构参考手册及 IEEE 754-2019 标准。

## 1.1 CPU 执行程序与指令流水线 {#ch1-1}

### 1.1.1 冯·诺依曼模型与核心部件 {#ch1-1-1}

现代通用计算机遵循**冯·诺依曼（von Neumann）模型**：程序指令与运行数据统一以二进制形式存放在线性编址的**内存**中，核心由五大部件构成：

```text
+-----------------------------------+
|             CPU 核心              |
|  +-------------+  +------------+  |
|  |  控制单元   |  | 算术逻辑单元|  |
|  | (CU / 译码) |  |   (ALU)    |  |
|  +-------------+  +------------+  |
|  +-----------------------------+  |
|  | 寄存器组 (通用 / PC / IR)    |  |
|  +-----------------------------+  |
+--------+--------+--------+--------+
         |        |        |
      地址总线  数据总线  控制总线
         |        |        |
+--------+--------+--------+--------+
|    主内存 (RAM)     |  输入/输出设备 |
+--------------------+--------------+
```

- **内存**：按字节（Byte，8 bit）线性编址，从 `0` 递增到总字节数减 1，支持随机访问。
- **CPU 内部部件**：
  - **算术逻辑单元（ALU）**：负责加减乘除、逻辑与移位运算。
  - **控制单元（CU）**：负责取指、译码，并向总线和运算部件发送控制信号。
  - **寄存器（Register）**：紧贴执行单元的高速存储。最关键的三类包括：**通用寄存器**（存放待运算数据）、**程序计数器（PC，x86-64 下为 `RIP`）**（存放下一条待执行指令的内存地址，而非指令本身）和**指令寄存器（IR）**（暂存当前正在译码执行的机器指令）。
- **三类总线**：**地址总线**指定访问的内存或设备地址，**数据总线**传输读写内容，**控制总线**传递读写方向、中断请求和复位等控制信号。

### 1.1.2 从 `a = 1 + 2` 到指令流水线 {#ch1-1-2}

CPU 不直接识别高级语言源码。编译器将源码翻译为汇编代码，汇编器将其编码为二进制机器码。程序加载到内存后，指令与数据分置不同区域（代码段与数据段）。以经典的负载-存储架构执行 `a = 1 + 2` 为例（设常量 `1`、`2` 和变量 `a` 分别位于数据段 `0x100`、`0x104`、`0x108`）：

1. `load R0, [0x100]`：将 `1` 从内存加载到通用寄存器 `R0`；
2. `load R1, [0x104]`：将 `2` 从内存加载到通用寄存器 `R1`；
3. `add R2, R0, R1`：ALU 将 `R0` 与 `R1` 相加，结果写入 `R2`；
4. `store [0x108], R2`：将 `R2` 写回变量 `a` 的内存地址 `0x108`。

按功能划分，CPU 指令通常分为**数据传输**（`load`/`store`/`mov`）、**算术逻辑运算**（`add`/`mul`/`cmp`）、**控制流跳转**（条件分支、函数调用）、**系统与陷入**（`syscall`/`svc`）以及**空操作**（`nop`）五类。

早期 CPU 串行执行每一条指令，现代 CPU 则普遍采用**指令流水线**（Pipeline）将一条指令拆分为多个阶段并行重叠执行。最经典的四阶段抽象为：

1. **取指（Fetch）**：控制单元根据 `PC` 指向的地址取出指令放入 `IR`，并推进 `PC`；
2. **译码（Decode）**：解析操作码与源/目的寄存器操作数；
3. **执行（Execute）**：ALU 完成算术逻辑计算、地址计算或分支条件判断；
4. **写回（Write-back / Store）**：将结果写回目标寄存器或提交到存储缓冲区。

真实的高性能微架构（如现代 Intel/AMD x86-64 与 ARM Cortex-X/Apple Silicon）在此基础上进一步发展出 **14–20 级深度流水线、超标量（多发射）与乱序执行（Out-of-Order Execution）**，单周期可同时退休（Retire）多条微操作。

### 1.1.3 32 位与 64 位的真实含义（勘误校准） {#ch1-1-3}

原书 1.1 节将“64 位软件”表述为“指令长度是 64 位”，并称“PC 每次自增大小由 CPU 位宽决定”。这一说法在现代架构下并不准确，需要区分三个概念：

| 维度 | 准确含义 | 常见误区纠偏 |
| --- | --- | --- |
| **硬件 CPU 位宽** | 通用寄存器宽度与 ALU 单次原生整数运算宽度（32 位=4 字节，64 位=8 字节） | 并不等于指令编码长度，也不等于芯片实际引出的物理地址引脚数 |
| **指令长度与 PC 步进** | 取决于指令集架构（ISA）：**ARM64（AArch64）** 虽是 64 位 CPU，但指令定长为 **32 位（4 字节）**；**x86-64** 为 **1–15 字节变长指令** | `PC` 推进的是“当前指令的实际字节长度”，而非一律按 4 字节或 8 字节固定自增 |
| **64 位软件与寻址空间** | 指程序编译所遵循的 64 位 **ABI**（指针宽 8 字节，如 Linux 的 LP64、Windows 的 LLP64） | 64 位 CPU 的理论地址宽度是 2<sup>64</sup>，但当前硬件通常只实现 **48 位**（256 TB）或 **57 位**（128 PB，5 级页表）规范虚拟地址，物理地址位宽常见为 46–52 位 |

64 位 CPU 相比 32 位 CPU 的核心工程优势在于**远超 4 GB 的虚拟/物理寻址能力**以及**单条指令处理 64 位整型/指针与更丰富的通用寄存器**（x86-64 将通用寄存器从 x86 的 8 个扩至 16 个，显著减少访存）；若仅做 32 位整数算术，二者单次计算本身差异并不悬殊。64 位 CPU 可通过硬件兼容模式（如 x86-64 的 Compatibility Mode）运行 32 位程序，反之 32 位硬件无法执行 64 位指令与 64 位寻址。

### 1.1.4 程序的 CPU 执行时间公式 {#ch1-1-4}

程序的 CPU 执行时间可严格拆解为三个因子的乘积：

```text
CPU 执行时间 = 指令数 × CPI（每条指令平均时钟周期数） × 时钟周期时间
```

其中**时钟周期时间**等于主频的倒数（例如 4 GHz 主频对应时钟周期 0.25 ns）。现代 CPU 主频难以继续翻倍，根源在于**登纳德缩放定律（Dennard Scaling）失效**——晶体管缩小后静态漏电与动态功耗密度撞上散热墙（而非单靠摩尔定律概括）。因此，软件工程师优化计算性能的核心杠杆落在前两项：

- **减少指令数**：改进算法复杂度、借助编译器优化（内联、循环展开、SIMD 向量化）。
- **降低 CPI**：减少 CPU 停顿（Stall）——其中开销最大的两大杀手正是**缓存未命中（Cache Miss）**与**分支预测失败（Branch Misprediction）**。

## 1.2 存储器金字塔与 CPU Cache 结构 {#ch1-2}

### 1.2.1 存储器层次与现代延迟量级 {#ch1-2-1}

CPU 执行速度与主存（DRAM）访问速度之间存在上百倍的“存储墙（Memory Wall）”。为兼顾速度、容量与成本，计算机采用逐级缓存的**存储器金字塔**——每一层主要与相邻层级交换数据：

| 存储层级 | 介质 / 特性 | 典型容量（单机/单核参考） | 典型访问延迟 | 相对 L1 倍数 |
| --- | --- | --- | --- | --- |
| **寄存器** | CPU 内部触发器，核私有 | 数十至数百个（几百 B） | < 0.5 ns（半周期内） | 0.5× |
| **L1 Cache** | SRAM，每核私有，分 **iCache（指令）** 与 **dCache（数据）** | 每核 32–128 KB | 约 1 ns（4–5 周期） | 1× |
| **L2 Cache** | SRAM，每核私有（部分架构按簇共享） | 每核 256 KB–2 MB | 约 3–5 ns（12–15 周期） | 3–5× |
| **L3 Cache** | SRAM，多核共享（LLC，末级缓存） | 几 MB 至数百 MB | 约 10–25 ns（30–60 周期） | 10–25× |
| **主内存（RAM）** | DRAM（1T1C 电容，需定时刷新） | 16 GB 至数 TB | 约 60–100 ns（200–300 周期） | 60–100× |
| **NVMe SSD** | NAND 闪存 + PCIe 通道，断电持久化 | 512 GB 至数十 TB | 约 10–70 µs（早期 SATA SSD 约 150 µs） | 10<sup>4</sup>–7×10<sup>4</sup>× |
| **机械硬盘（HDD）** | 旋转盘片 + 机械磁头寻道 | 数 TB 至数十 TB | 约 5–10 ms | 5×10<sup>6</sup>–10<sup>7</sup>× |

**SRAM 与 DRAM 的物理差异**：SRAM（静态随机存储器）通常用 6 个晶体管保存 1 bit，只要不断电数据就稳定保持、读写极快，但面积大、成本高，专用于 CPU Cache；DRAM（动态随机存储器）仅用 1 个晶体管加 1 个电容保存 1 bit，集成度高、成本低，但电容会漏电，需要内存控制器周期性刷新充电，因而访问更慢。

在 Linux 系统中，可直接读取 `/sys/devices/system/cpu/cpu0/cache/` 查看本机各级缓存类型、容量及缓存行大小（`index0` 通常为 L1d，`index1` 为 L1i，`index2` 为 L2，`index3` 为 L3）：

```bash
grep . /sys/devices/system/cpu/cpu0/cache/index*/{level,type,size,coherency_line_size}
```

### 1.2.2 Cache Line 与地址映射机制 {#ch1-2-2}

CPU 从内存加载数据到 Cache 并非按单个字节搬运，而是以固定大小的**缓存行**（Cache Line）为基本传输与一致性维护单位。x86-64 与多数 ARM64 服务器上，Cache Line 大小为 **64 字节**（Apple Silicon M 系列等部分 ARM64 处理器为 128 字节）。当程序读取 `int arr[100]` 的 `arr[0]` 时，CPU 会一次性将 `arr[0]` 至 `arr[15]` 所在的整块 64 字节内存加载入缓存。

为了把庞大的物理内存地址映射到小巧的 CPU Cache 中，硬件将内存地址切分为三段：

```text
|<-------------- 高位 -------------->|<---- 中位 ---->|<--- 低位 --->|
+------------------------------------+----------------+--------------+
|            组标记 (Tag)            | 组索引 (Index) | 块内偏移(Offset)|
+------------------------------------+----------------+--------------+
```

每条 Cache Line 除了存放 64 字节**数据块**（Data）外，还包含 **Valid 位**（有效位）、**Dirty 位**（写回策略下的脏标记）和 **Tag**（用于区分映射到同一位置的不同内存块）。以最简单的**直接映射**（Direct-Mapped）为例，CPU 查找数据的 4 个步骤是：

1. 根据地址中的 `Index` 定位到唯一的 Cache Line 槽位；
2. 检查该槽位的 `Valid` 位是否为 1（若为 0 则直接未命中，回源下级缓存/内存）；
3. 比对地址中的 `Tag` 与槽位中记录的 `Tag` 是否一致（若不一致则为冲突未命中）；
4. 命中后，根据 `Offset` 从 64 字节数据块中取出目标字节或机器字。

直接映射虽然硬件电路简单，但多个步长为 Cache 容量整数倍的地址会反复争抢同一个槽位，引发严重的**冲突未命中（Conflict Miss）**。因此现代 CPU 普遍采用 **N 路组相联（N-way Set Associative）**：一个 `Index` 对应包含 N 条 Cache Line 的集合（例如现代 x86-64 的 L1d 常见为 8 路或 12 路组相联，L3 常见为 16 路以上），硬件并行比对这 N 路的 `Tag`，在硬件复杂度与冲突率之间取得平衡；而 **全相联（Fully Associative）** 则不划分 `Index`，任意内存块可放入任意槽位，因比较器开销大通常只用于小容量硬件结构（如部分 TLB）。

## 1.3 编写缓存与流水线友好的代码 {#ch1-3}

### 1.3.1 提升数据缓存命中率：空间局部性与预取 {#ch1-3-1}

C/C++/Go/Rust 等语言中的二维数组按**行优先**（Row-Major）在内存中连续排布。遍历一个大型 `int arr[N][N]` 时：

- **按行遍历（`arr[i][j]`）**：访问地址严格递增且连续。加载 `arr[i][0]` 触发一次 Cache Miss 后，同行的后续 15 个 `int` 已在同一个 64 字节 Cache Line 中直接命中；更重要的是，连续步长会激活 CPU 内部的**硬件预取器（Hardware Prefetcher）**，在代码读到之前提前把下一批 Cache Line 拉入 L1/L2。
- **按列遍历（`arr[j][i]`）**：相邻两次访问跨度为 `4 * N` 字节。只要一行尺寸超过 Cache Line 甚至 L1 容量，每次访问都会触发 Cache Miss，硬件预取也难以生效，实测耗时往往慢数倍甚至一个数量级。

同理，在高性能数据结构设计中，紧凑数组（如切片、结构体数组 SoA）通常显著快于节点散落在堆上的指针链表。

### 1.3.2 提升分支预测效率（修正原书 iCache 归因误区） {#ch1-3-2}

考虑一个经典实验：给定包含数万个 0–99 随机整数的数组，对每个元素判断 `if (arr[i] < 50) arr[i] = 0;`。对比“先排序再遍历”与“直接遍历”，**排序后的遍历阶段明显快得多**。

原书 1.3 节将这一现象归因于“分支预测把 `arr[i] = 0` 这条指令提前放进了指令缓存（iCache）”，**这一归因并不准确**。整个循环体编译后只有寥寥数条机器指令，无论数组是否排序，这些指令从第一次迭代起就已经完整驻留在几十 KB 的 L1 iCache 中，根本不存在指令缓存未命中。

真正的性能差距来自**动态分支预测（Dynamic Branch Prediction）与流水线冲刷（Pipeline Flush）**：

1. 在深度流水线中，CPU 尚未算出 `arr[i] < 50` 的结果时，就必须依靠分支预测器猜测下一步走哪条路径，并提前将后续指令送入流水线**推测执行（Speculative Execution）**。
2. 数组**未排序**时，每次元素小于 50 的概率接近 50% 且完全随机，动态分支预测器的猜错率接近一半；每次猜错都必须作废流水线中已经执行的十多条指令并重新取指，白白浪费约 **15–20 个时钟周期**。
3. 数组**已排序**后，前半段连续全为真、后半段连续全为假，整个遍历过程仅在临界点附近预测失败 1–2 次，流水线几乎零停顿。

工程上的两条优化手段：

- **消除不可预测分支（Branchless）**：在热点循环中用位运算或条件传送指令（x86 `CMOV`）替代随机性极高的 `if/else`（现代编译器在 `-O2`/`-O3` 下也常自动生成 `CMOV`）。
- **分支概率提示（`likely` / `unlikely`）**：Linux 内核的 `likely(x)` / `unlikely(x)` 宏（底层为 GCC/Clang `__builtin_expect`）以及 **C++20** 引入的 `[[likely]]` / `[[unlikely]]` 属性，本质上是**编译期提示**——指导编译器把高概率路径紧挨条件跳转放置为“顺序直落（Fall-through）”分支，把罕见错误处理路径移到代码段末尾，从而减少跳转并改善热路径的 **iCache 空间局部性**，而非用来“训练”硬件动态预测器。只有在确知分支概率极度偏斜（如热路径错误检查）时才值得使用。

### 1.3.3 多核缓存亲和性与 NUMA 视角 {#ch1-3-3}

由于 L1/L2 Cache 为单个 CPU 核心私有，当计算密集型线程被操作系统调度器频繁在不同核心之间迁移时，新核心上的 L1/L2 缓存完全是冷的，必须重新从共享 L3 或主存加载数据。

在 Linux 中，可使用 `sched_setaffinity()` 系统调用或 `taskset` 命令将关键工作线程绑定到指定核心，降低跨核迁移带来的缓存抖动。需要注意的是，绑核并非银弹：在多任务混布环境中盲目绑核可能导致负载不均、人为制造核内排队延迟；同时在多路服务器（**NUMA** 架构）中，除了绑定 CPU 核心，还应确保线程访问的内存尽量分配在**同一 NUMA 节点**的本地 DRAM 上，避免跨互联总线（UPI/Infinity Fabric）访问远端内存带来的额外延迟。

## 1.4 多核缓存一致性与伪共享 {#ch1-4}

### 1.4.1 写策略：写直达与写回 {#ch1-4-1}

CPU 向缓存写入数据时，需要决定何时将修改传播到下一级存储：

- **写直达（Write-Through）**：每次写操作在更新当前级 Cache（若命中）的同时，将写入传播到**下一级存储**（如下级缓存 L2/L3，直至主存）。实现相对简单、下级副本保持同步；不过在现代多级缓存与**写缓冲（Write Buffer / Store Buffer）**存在时，写入并不必然每次直接同步落到 DRAM 或迫使 CPU 停等 DRAM 完成（缓冲满或遇到串行化约束时才会停顿），但高频写入仍会持续放大下级缓存与互联总线带宽压力，因此主流 CPU 数据缓存很少采用。
- **写回（Write-Back）**：现代 CPU Cache 的默认策略。写命中时仅修改 Cache 并置位 **Dirty（脏）标记**，不立刻写向下级存储；只有当该脏缓存行因容量冲突被替换淘汰，或被其他核心的一致性协议要求交出最新数据时，才写回下级存储。

### 1.4.2 缓存一致性、MESI 状态机与现代演进 {#ch1-4-2}

写回策略在多核环境下立刻引发**缓存一致性**（Cache Coherence）问题：核心 A 修改了私有 L1 中的变量 `i` 但尚未写回内存，此时核心 B 读取 `i` 可能读到旧值；若核心 A、B 同时分别将 `i` 改写为 `100` 和 `200`，核心 C 和核心 D 还可能按相反顺序观察到这两次写入。

解决一致性必须同时满足两个保证：

1. **写传播（Write Propagation）**：一个核心对缓存的写入必须传播到其他持有该数据的核心。
2. **事务串行化（Transaction Serialization）**：所有核心对**同一内存地址**的写操作必须观察到完全一致的全局先后顺序。

经典实现建立在**总线嗅探**（Bus Snooping）之上：每个核心监听共享总线上的读写广播，并配合 **MESI 协议**用 4 个状态管理每条 Cache Line：

| 状态 | 含义 | 与内存是否一致 | 本核写入是否需对外通知 |
| --- | --- | --- | --- |
| **M（Modified，已修改）** | 仅本核缓存，且已被修改（脏行） | 不一致 | **否**，直接本地修改 |
| **E（Exclusive，独占）** | 仅本核缓存，数据干净 | 一致 | **否**，直接转为 M 并修改 |
| **S（Shared，共享）** | 多个核心均可能缓存，数据干净 | 一致 | **是**，须先广播使其他核对应行转为 I |
| **I（Invalidated，已失效）** | 缓存行无效，不可读取 | — | 须先发读独占（Read For Ownership）获取最新行 |

MESI 的精妙之处在于区分了 **E** 和 **S**：单线程独占数据时处于 E 或 M 状态，后续修改无需在总线上发送任何无效化广播，极大减轻了互联带宽压力。

**现代多核处理器的三项关键演进**：

1. **MOESI 与 MESIF 扩展**：AMD 采用 **MOESI**，新增 **O（Owned）** 状态——当核心 A 处于 M 态而核心 B 读取该行时，A 可直接把脏数据转发给 B 并将自身转为 O 态、B 转为 S 态，不必立刻写回慢速 DRAM；Intel 采用 **MESIF**，新增 **F（Forward）** 状态，在多份 S 态副本中仅指定一个核心负责转发数据，避免多个共享者同时响应造成流量浪费。
2. **目录协议（Directory-Based）**：当服务器核心数达到数十甚至上百核时，全局总线广播会成为瓶颈。现代多核芯片改用环形（Ring）或网格（Mesh）互联，并在末级缓存或内存控制器中维护**目录**，记录每条 Cache Line 被哪些核心缓存，实现点对点精准无效化。
3. **Store Buffer、Invalidate Queue 与内存屏障**：严格同步等待所有核心返回“失效确认（Invalidate ACK）”会让写操作停顿几十个周期。现代 CPU 在核与 L1 之间加入 **Store Buffer（写缓冲）** 和 **Invalidate Queue（失效队列）** 将一致性消息异步化——这在硬件层带来了**内存重排（Memory Reordering）**，也是并发编程中必须使用原子操作与**内存屏障（Memory Barrier / Fence）**（如 `acquire`/`release` 语义）的硬件根源。

### 1.4.3 伪共享（False Sharing）与规避手段 {#ch1-4-3}

因为 MESI 的状态维护与失效粒度是**整条 64 字节 Cache Line** 而非单个变量，多核并发时会出现隐蔽的性能杀手——**伪共享（False Sharing）**：

```text
同一条 64 字节 Cache Line:
+-------------------+-------------------+-------------------------------+
|  long counterA    |  long counterB    |           其余 48 字节         |
+-------------------+-------------------+-------------------------------+
       ^                     ^
       | 核 1 频繁写          | 核 2 频繁写
```

线程 1（核 1）只修改 `counterA`，线程 2（核 2）只修改 `counterB`，逻辑上毫无共享竞争。但因为两者相邻落在同一条 Cache Line 中：

1. 核 1 写 `counterA`：发送无效化消息，核 2 的整条缓存行变为 `I`，核 1 变为 `M`；
2. 核 2 写 `counterB`：发现本核缓存行已 `I`，触发 Cache Miss，迫使核 1 交出/写回整条缓存行，核 1 变为 `I`，核 2 变为 `M`；
3. 如此循环往复（Cache Ping-Pong），私有 L1/L2 形同虚设，并发吞吐甚至反不如单线程。

**规避原则（空间换时间）**：通过**缓存行对齐（Alignment）或字节填充（Padding）**，将不同线程高频写入的独立热点变量隔离到不同的 Cache Line 中：

- **Linux 内核**：`____cacheline_aligned_in_smp` 宏（多核 SMP 编译下按缓存行对齐，单核下为空）。
- **C++17+**：`alignas(64)` 或 `alignas(std::hardware_destructive_interference_size)`。
- **Go**：在结构体热点字段之间嵌入 `golang.org/x/sys/cpu.CacheLinePad`（按目标架构自动匹配 64 或 128 字节）。
- **Java**：使用 `@jdk.internal.vm.annotation.Contended`（需开启 `-XX:-RestrictContended`）或如 Disruptor 框架那样在热点字段前后显式填充无用 `long` 字段。

## 1.5 整数补码与 IEEE 754 浮点数 {#ch1-5}

### 1.5.1 负数为什么用补码表示 {#ch1-5-1}

有符号整数如果只用最高位做符号位（原码），会遇到两个棘手问题：一是存在 `+0`（`0000...0`）和 `-0`（`1000...0`）两种零表示；二是做加法时硬件必须先判断符号位，同号相加、异号转减法并比较绝对值，电路复杂且拖慢高频算术运算。

现代计算机统一采用**二进制补码（Two's Complement）**：对 w 位有符号整数，最高位权重为 -2<sup>w-1</sup>，其余位权重为正的 2<sup>k</sup>；求一个正数对应负数的补码，等价于**按位取反再加 1**（数学上是模 2<sup>w</sup> 的加法逆元）。

以 8 位有符号整数计算 `-2 + 1` 为例：

- `+2` = `0000 0010`，按位取反得 `1111 1101`，加 1 得 `-2` = `1111 1110`；
- `+1` = `0000 0001`；
- 直接按无符号二进制相加：`1111 1110 + 0000 0001 = 1111 1111`，即 `-1`（`0000 0001` 取反加 1）。

补码带来三大好处：**减法彻底化为加法**（ALU 只需一套加法器电路）、**0 的编码唯一**（全 `0`），并且 32 位 `int` 能多表示一个最小负数 `-2147483648`（-2<sup>31</sup> 到 2<sup>31</sup> - 1）。

### 1.5.2 IEEE 754 浮点数与 `0.1 + 0.2 != 0.3` {#ch1-5-2}

十进制转二进制时，整数部分用**除 2 取余法**，小数部分用**乘 2 取整法**。能被二进制有限位精确表示的小数，其最简分数的分母必须是 2<sup>k</sup>（如 0.5 = 1/2、0.625 = 5/8 = 0.101<sub>2</sub>）。而十进制的 0.1 = 1/10 与 0.2 = 1/5 分母含质因子 5，在二进制下都是无限循环小数：

```text
0.1 (十进制) = 0.00011001100110011... (二进制，0011 无限循环)
0.2 (十进制) = 0.00110011001100110... (二进制，0011 无限循环)
```

计算机使用 **IEEE 754** 标准以二进制科学计数法（规格化形式 (-1)<sup>S</sup> × (1.M)<sub>2</sub> × 2<sup>E - Bias</sup>）存储浮点数，由三段组成：

| 类型 | 总位宽 | 符号位 S | 指数位 E（偏移量 Bias） | 尾数位 M（含隐含前导 1 的有效位） | 十进制有效数字 |
| --- | --- | --- | --- | --- | --- |
| **单精度（`float` / `float32`）** | 32 bit | 1 bit | 8 bit（Bias = 127） | 23 bit（共 24 bit 精度） | 约 7 位 |
| **双精度（`double` / `float64`）** | 64 bit | 1 bit | 11 bit（Bias = 1023） | 52 bit（共 53 bit 精度） | 约 15–17 位 |

三个关键设计细节：

1. **指数加偏移量（Bias）**：将可正可负的真实指数统一平移为无符号整数存储，便于硬件直接按字典序比较浮点数大小。
2. **隐含前导 `1`**：规格化二进制科学计数法的小数点左侧必为 `1`，因此省略不存，白赚 1 bit 精度。以 `10.625` 存为 `float32` 为例：先化为二进制 `1010.101`，小数点**左移** 3 位（修正原书“右移 3 位”笔误）得 1.010101<sub>2</sub> × 2<sup>3</sup>；符号位 `0`，指数位 `3 + 127 = 130`（`10000010`），尾数位 `010101` 后补零至 23 位。
3. **特殊保留指数**：指数位全 `0` 用于表示 ±0（尾数全 0）和**次正规数（Subnormal）**（尾数非 0，无隐含前导 1，平滑填补 0 附近的下溢间隙）；指数位全 `1` 用于表示 ±∞（尾数全 0）和 **NaN**（尾数非 0）。

**为什么 `0.1 + 0.2 != 0.3`？** 因为 `0.1`、`0.2` 和 `0.3` 在二进制下都是无限循环小数，按 IEEE 754 编码存储时必须按**向最近偶数舍入**（Round to Nearest, Ties to Even）截断到 53 位（`double`）或 24 位（`float`）有效精度。以 IEEE 754 `double`（如 JavaScript `Number`、C/C++ `double`、Go 运行时 `float64` 变量）为例：

- `0.1` 实际存储值略大于 0.1（约 `0.10000000000000000555...`）；
- `0.2` 实际存储值略大于 0.2（约 `0.20000000000000001110...`）；
- 两者相加后再舍入得到 `0.30000000000000004440...`，而直接存储的 `0.3` 略小于 0.3（约 `0.29999999999999998889...`），二者二进制位型不同，因此在运行时比较为假。

> **语言求值差异提示（以 Go 为例）**：上述结论针对**已按 IEEE 754 编码存储并参与运算的浮点数**。在 Go 语言中，字面量 `0.1`、`0.2`、`0.3` 属于**无类型浮点常量**，编译器在编译期采用高精度任意精度算术求值，因此直接写 `0.1 + 0.2 == 0.3` 结果为 **`true`**；必须先存入 `float64` 变量或显式转换为 `float64`（例如 `a, b := 0.1, 0.2; a + b == 0.3`），使值按 IEEE 754 `float64` 舍入并在运行时计算，结果才会是 **`false`**（已在 Go 1.27.4 / `linux/amd64` 实测验证）。

**工程实践**：涉及金融金额或精确十进制运算时，应使用整数最小单位（如以“分”计价的 `int64`）或十进制高精度库（如 `Decimal`）；科学计算中判断两个浮点数是否相等，应比较差值绝对值是否小于容差（如相对误差 / ULP），而不要直接用 `==`。

### 练习 1：直接映射与组相联 Cache 的地址切分

某 32 位物理地址机器配备一块容量为 32 KB、Cache Line 大小为 64 字节的 L1 数据缓存：

1. 若采用**直接映射**，32 位物理地址中的 `Offset`、`Index`、`Tag` 各占多少 bit？
2. 若改为 **8 路组相联**（总容量与 Cache Line 大小不变），这三部分各占多少 bit？相比直接映射解决了什么问题？

<details>
<summary>查看参考答案</summary>

1. **直接映射**：
   - Cache Line 大小 = 64 = 2<sup>6</sup> 字节，因此 `Offset` 占 **6 bit**。
   - Cache Line 总数 = 32 KB / 64 B = 512 = 2<sup>9</sup> 条，因此 `Index` 占 **9 bit**。
   - 剩余高位为 `Tag` = 32 - 9 - 6 = **17 bit**。
2. **8 路组相联**：
   - Cache Line 大小不变，`Offset` 仍为 **6 bit**。
   - 共有 512 条 Cache Line，每组 8 路，因此组数（Sets）= 512 / 8 = 64 = 2<sup>6</sup>，故 `Index` 占 **6 bit**。
   - 剩余高位为 `Tag` = 32 - 6 - 6 = **20 bit**。
   - **解决的问题**：将映射到同一 `Index` 的不同内存块从只能存 1 条扩展到可同时存 8 条，大幅降低步长访问导致的**冲突未命中（Conflict Miss）**，同时比全相联硬件成本低得多。

</details>

### 练习 2：定位两段热点循环的真实瓶颈

观察下面两段 C 代码（`N = 4096`，`int` 占 4 字节，Cache Line 为 64 字节）：

```c
// 片段 A
long sum = 0;
for (int j = 0; j < N; j++) {
    for (int i = 0; i < N; i++) {
        sum += matrix[i][j];
    }
}

// 片段 B（data 为 0~99 随机整数，已全部驻留 L1/L2）
long count = 0;
for (int i = 0; i < 10000; i++) {
    if (data[i] < 50) {
        count += data[i];
    }
}
```

请分别指出片段 A 与片段 B 的核心硬件性能瓶颈，并给出对应的改写方案。

<details>
<summary>查看参考答案</summary>

- **片段 A 的瓶颈：数据缓存空间局部性差 + 硬件预取失效**。
  - C 语言二维数组按行连续存储，每行占 `4096 * 4 = 16 KB`。片段 A 内层递增行号 `i`，相邻访问跨度高达 16 KB，几乎每次读取都触发 L1 dCache 未命中。
  - **改写**：交换内外循环顺序，外层遍历 `i`、内层遍历 `j`（按行顺序访问 `matrix[i][j]`），使单条 64 字节 Cache Line 服务连续 16 个 `int` 并触发硬件预取。
- **片段 B 的瓶颈：动态分支预测失败导致的流水线冲刷**（注意：并非 iCache 未命中）。
  - `data[i] < 50` 在随机分布下约 50% 概率真假交替，分支预测器频频猜错并冲刷流水线。
  - **改写**：若业务允许不依赖原顺序且遍历多次，可先排序；更通用的优化是改写为**无分支**（Branchless）表达式，例如：

```c
for (int i = 0; i < 10000; i++) {
    count += (data[i] < 50) ? data[i] : 0; // 现代编译器通常会生成条件传送指令 CMOV，消除分支跳转
}
```

（若进一步确保无分支，也可用掩码 `int mask = -(data[i] < 50); count += data[i] & mask;`。）

</details>

### 练习 3：识别并修复结构体中的伪共享

某高并发监控模块定义了如下全局统计结构，线程 1 只持续执行 `stats.rx_packets++`，线程 2 只持续执行 `stats.tx_packets++`（运行在 64 字节 Cache Line 的 x86-64 多核 Linux 机器上）：

```c
struct net_stats {
    uint64_t rx_packets;
    uint64_t tx_packets;
};
```

1. 解释为何两个线程操作不同字段却仍会出现严重的吞吐下降。
2. 给出 C++17 与 Go 两种语言的修复写法，并说明代价。

<details>
<summary>查看参考答案</summary>

1. **原因**：`rx_packets` 和 `tx_packets` 各占 8 字节且地址相邻，极大概率落在同一条 64 字节 Cache Line 中。在 MESI 协议下，核 1 修改 `rx_packets` 会使核 2 缓存中的整条行失效（`I`），紧接着核 2 修改 `tx_packets` 又触发未命中并使核 1 的整条行失效。两核间高频产生缓存行所有权来回传递（Cache Ping-Pong），即**伪共享**。
2. **修复写法**：

```cpp
// C++17：显式按缓存行对齐，隔离到不同 Cache Line
struct net_stats {
    alignas(64) uint64_t rx_packets;
    alignas(64) uint64_t tx_packets;
};
```

```go
// Go：利用标准扩展包按目标平台缓存行尺寸填充（需导入 "golang.org/x/sys/cpu"）
type NetStats struct {
    RxPackets uint64
    _         cpu.CacheLinePad
    TxPackets uint64
    _         cpu.CacheLinePad
}
```

- **代价**：空间换时间——结构体体积从 16 字节膨胀至 128 字节，会增加内存占用并降低其他冷数据的缓存密度，因此**只应对多核高频写入的热点变量使用**。

</details>

### 练习 4：手工编码 IEEE 754 单精度浮点数

将十进制数 `-6.75` 编码为 32 位 IEEE 754 单精度浮点数（二进制与十六进制），并说明它是否存在精度损失。

<details>
<summary>查看参考答案</summary>

1. **符号位 S**：负数，故 `S = 1`。
2. **转为二进制**：
   - 整数部分：`6` = `110`；
   - 小数部分：`0.75 * 2 = 1.5`（取 `1`），`0.5 * 2 = 1.0`（取 `1`），故 `0.75` = `.11`；
   - 合并得 `110.11`。
3. **规格化**：小数点左移 2 位，得 1.1011<sub>2</sub> × 2<sup>2</sup>。
4. **指数位 E**：真实指数 `2` + 偏移量 `127` = `129` = `10000001`（8 位）。
5. **尾数位 M**：省去隐含前导 `1`，小数部分 `1011` 右侧补零至 23 位：`10110000000000000000000`。
6. **拼接结果**：
   - 二进制：`1 10000001 10110000000000000000000`
   - 4 位分组：`1100 0000 1101 1000 0000 0000 0000 0000` → 十六进制 **`0xC0D80000`**。
7. **有无精度损失**：**无损失**，因为 6.75 = 27 / 4，分母为 2<sup>2</sup>，二进制展开有限且有效位远小于 24 位。

</details>

### 面试题 1：64 位 CPU 上运行的 64 位程序，每条机器指令都占 8 字节吗？

<details>
<summary>查看参考答案</summary>

**结论**：**不是。**

**关键依据**：
- “64 位 CPU”指通用寄存器与原生整数运算位宽为 64 位，“64 位软件”指采用 64 位 ABI（指针占 8 字节），均不规定机器指令必须占 8 字节。

</details>

### 面试题 2：在 MESI 协议中，为什么已经有了 `S`（共享）和 `M`（已修改），还要额外设计 `E`（独占）状态？

<details>
<summary>查看参考答案</summary>

**结论**：为了**优化单核独占数据的“先读后写”开销**，避免不必要的总线广播。

**关键依据**：
- 如果没有 `E` 状态（即退化为 MSI 协议），当某核心独占读取一个变量并紧接着修改它时，读取后状态只能标为 `S`；写入时由于不知道其他核是否也持有副本，**必须向总线广播一次无效化请求**（Invalidate）才能转为 `M`。
- 引入 `E` 状态后，首次读取时若确认其他核心均未缓存，则直接标为 `E`；随后写入只需在本地静默将 `E` 改为 `M`，完全不占用互联总线带宽。

</details>

### 面试题 3：既然现代 CPU 硬件已经实现了 MESI 缓存一致性协议，为什么多线程编程中还需要锁或内存屏障？

<details>
<summary>查看参考答案</summary>

**结论**：MESI 只能保证**单条缓存行的最终一致与单地址写串行化**，既不保证复合操作的原子性，也不消除硬件/编译器的内存重排。

**关键依据**：
1. **非原子复合操作**：`i++` 包含读、改、写三条独立步骤，两核可能同时读到同一旧值并覆盖彼此结果，必须借助原子指令（如 `LOCK XADD`）或互斥锁保护。
2. **Store Buffer 与 Invalidate Queue 引发的重排**：现代 CPU 为掩盖等待失效确认的延迟，将写操作先暂存于核内 Store Buffer、将失效消息先放入 Invalidate Queue，导致一个核上的写入顺序在另一个核看来可能发生乱序（例如经典 StoreLoad 重排），且编译器也可能重排指令。必须通过内存屏障（`acquire`/`release`/`seq_cst`）强制刷出缓冲并建立跨核可见性顺序。

</details>

### 面试题 4：把工作线程用 `sched_setaffinity` 绑定到固定 CPU 核心，性能一定会提升吗？

<details>
<summary>查看参考答案</summary>

**结论**：**不一定，盲目绑核反而可能降低整体吞吐或抬高尾延迟。**

**关键依据**：
- **收益场景**：计算密集型或低延迟网络线程（如 DPDK、高频交易、固定分片工作线程），绑核能避免跨核迁移导致的私有 L1/L2 Cache 与 TLB 变冷，配合 NUMA 本地内存效果显著。
- **负面场景**：若被绑定的核心恰好承载大量硬件中断、软中断或其他高负载进程，而其余核心空闲，操作系统调度器却无法将其迁移走，反而造成严重的核内排队饥饿；在超线程（SMT）CPU 上，若把两个高负载线程绑到同一物理核的两个逻辑核上，还会激烈争抢同一套 L1/L2 与执行单元。

</details>

### 面试题 5：为什么双精度浮点数（`double`）能精确表示 `9007199254740992`（2<sup>53</sup>），却无法精确表示 `0.1`？

<details>
<summary>查看参考答案</summary>

**结论**：是否能精确表示，取决于该数能否写成 m × 2<sup>e</sup>（其中整数 |m| ≤ 2<sup>53</sup> 且指数在范围内），与数值绝对大小无关。

**关键依据**：
- `double` 拥有 53 位二进制有效精度（52 位尾数 + 1 位隐含前导 1），因此 [-2<sup>53</sup>, 2<sup>53</sup>] 内的所有**整数**以及分母为 2<sup>k</sup> 且有效位不超过 53 位的小数都能无损精确表示（例如 2<sup>53</sup> = 1.0<sub>2</sub> × 2<sup>53</sup>，尾数全 0）。
- `0.1` 等于 1/10 = 1/(2 × 5)，分母含有质因子 5，无法写成有限位二进制小数，只能截断舍入为近似值。

</details>
