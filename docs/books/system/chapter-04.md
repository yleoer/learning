# 第 4 章 进程、线程与 CPU 调度

## 本章要点

程序是存储在磁盘上的静态可执行文件，只有被操作系统装载进内存并赋予执行上下文后，才会成为动态推进的任务实体。本章整合原书《图解系统》第 4.1 节、第 1.5 节（Linux 调度器）以及第 5.1 节（进程调度算法），彻底消除原书在进程调度上的三处重复，并结合现代操作系统实践做出关键更新：对照教科书状态模型与 Linux 实际进程状态（特别是不可中断睡眠 `D`、孤儿进程与僵尸进程），将 M:N 线程模型衔接至 Go GMP 与 Java 虚拟线程，并将 Linux 调度器从历史上的 CFS 更新至 **Linux 6.6+ 默认的 EEVDF 调度器**及 **Linux 6.12+ 的 `sched_ext`**。

读完本章后，应能区分进程与线程在资源归属、切换开销和内核实现上的异同，诊断僵尸进程与 `D` 状态进程，理解 1:1 与 M:N 并发模型的取舍，并说明经典调度算法如何演化至现代 Linux 多级调度类与 EEVDF。

> 核对日期：2026 年 11 月 23 日；核对环境为 Linux 6.12 LTS 调度器内核文档及 POSIX/NPTL 规范。

## 4.1 进程模型与 Linux 实际生命周期 {#ch4-1}

### 4.1.1 进程控制块（`task_struct`） {#ch4-1-1}

**进程（Process）**是操作系统进行**资源分配与隔离的基本单位**。在操作系统内核中，每个进程都由唯一的**进程控制块**（PCB）描述；在 Linux 内核中，这一结构体称为 **`struct task_struct`**（原书 1.5 节多处误拼为 `tark_struct`），核心包含四类信息：

- **身份标识**：进程号 PID、线程组号 TGID（用户态 `getpid()` 实际返回 TGID）、父进程指针与所属用户凭证（UID/GID）。
- **调度与状态信息**：任务当前状态、调度类指针、静态/动态优先级、虚拟运行时间与截止时间参数。
- **资源清单**：指向虚拟地址空间描述符 `mm_struct`（含页表）、打开文件描述符表 `files_struct`、信号处理器与 Namespace/cgroup 归属。
- **CPU 上下文现场**：任务切换出 CPU 时保存的内核栈指针、通用寄存器与浮点/向量寄存器状态。

### 4.1.2 理论状态模型与 Linux 实际状态对照 {#ch4-1-2}

教科书常用五态（创建、就绪、运行、阻塞、终止）或加入内存换出概念的七态（就绪挂起、阻塞挂起）模型来抽象进程生命周期。而在实际排查 Linux 系统（如 `ps`、`top`）时，需要重点掌握 Linux 内核的真实状态码：

| 状态码 | 内核宏 | 含义与典型触发场景 |
| --- | --- | --- |
| **`R`** | `TASK_RUNNING` | **运行中或就绪**：正在 CPU 上执行，或位于就绪队列等待调度（Linux 不在状态码上区分运行与就绪） |
| **`S`** | `TASK_INTERRUPTIBLE` | **可中断睡眠**：等待网络数据、管道、定时或锁；收到信号（如 `SIGTERM`、`SIGKILL`）可被唤醒响应 |
| **`D`** | `TASK_UNINTERRUPTIBLE` | **不可中断睡眠**：通常在等待关键内核态硬件 I/O（如故障磁盘或卡死的 NFS）。**该状态下进程不响应任何信号，连 `kill -9` 也无法立即终止**，且会计入系统 Load Average |
| **`T` / `t`** | `TASK_STOPPED` / `TRACED` | 收到 `SIGSTOP`/`SIGTSTP`（如 `Ctrl+Z`）暂停，或正被调试器（`gdb`/`strace`）跟踪 |
| **`Z`** | `EXIT_ZOMBIE` | **僵尸状态**：进程已执行退出，内存与文件已释放，但 `task_struct` 与 PID 仍残留等待父进程读取退出码 |
| **`X`** | `EXIT_DEAD` | 彻底消亡的瞬态，通常不可见 |

### 4.1.3 孤儿进程与僵尸进程（纠偏原书泛化表述） {#ch4-1-3}

原书 4.1 节曾按早期教材概括称“终止父进程时同时也会终止其所有子进程”，这与 Linux/Unix 实际行为不符。在 Linux 中，父子进程的退出先后会产生两种截然不同的现象：

- **孤儿进程（Orphan Process）**：**父进程先于子进程退出**。子进程不会被连带杀死，而是被内核重新托管给 **PID 1（如 `systemd`）** 或设置了 `PR_SET_CHILD_SUBREAPER` 的祖先进程，由新父进程负责后续回收。孤儿进程本身通常无害（许多守护进程正是利用该机制脱离终端）。
- **僵尸进程（Zombie Process）**：**子进程已退出，但父进程一直未调用 `wait()` / `waitpid()` 回收其退出状态**。僵尸进程不再占用 CPU 和用户态物理内存，但仍占据一个内核 `task_struct` 和 PID 槽位。大量僵尸进程积压会耗尽系统 PID 上限，导致无法创建新进程。由于僵尸进程已经“死亡”，**对其执行 `kill -9` 无效**——只能修复父进程（正确处理 `SIGCHLD` 并调用 `waitpid`）或终止失职的父进程（让僵尸被 PID 1 接管并立即清理）。

## 4.2 线程、上下文切换与现代并发线程模型 {#ch4-2}

### 4.2.1 线程与 Linux 轻量级进程（LWP） {#ch4-2-1}

**线程（Thread）**是进程内的一条独立执行流，也是 **CPU 调度的基本单位**。同一进程内的多个线程**共享**虚拟地址空间（代码段、数据段、堆、页表）与打开的文件描述符等重型资源，各自**独享**少量执行现场：

- 独立的**用户态栈**与**内核态栈**；
- 独立的 **CPU 寄存器状态**（含程序计数器 PC 与栈指针 SP）；
- 独立的**线程局部存储（TLS）**、错误码 `errno` 与信号掩码。

在 Linux 内核的设计哲学中，**没有专门独立于 PCB 之外的 TCB 结构体**——无论是进程还是线程，底层都由同一个系统调用 `clone()` 创建并表示为 `struct task_struct`。调用 `fork()` 时不共享地址空间与文件表，得到独立进程；调用 `pthread_create()` 时传入 `CLONE_VM | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD` 等标志共享进程资源，得到的就是共享同一 TGID 的线程（常称**轻量级进程 LWP**）。

线程的代价在于**故障隔离弱**：同一进程内任意一个线程触发非法内存访问（`SIGSEGV`）或未捕获致命信号，会导致整个进程及其全部线程一同崩溃。

### 4.2.2 进程与线程上下文切换的真实开销 {#ch4-2-2}

CPU 上下文切换（Context Switch）指内核暂停当前任务、将其 CPU 寄存器与内核栈指针保存到 `task_struct`，再加载下一个任务的现场恢复执行的过程。触发场景包括：时间片耗尽、等待 I/O 或锁主动阻塞、高优先级任务抢占。

上下文切换的开销分为两部分：

1. **直接开销（微秒级）**：保存/恢复通用寄存器、浮点/AVX 寄存器、切换内核栈及调度器选任务的计算开销。
   - **同进程线程切换**：共享虚拟地址空间，**无需切换页表**，直接开销较小；
   - **跨进程切换**：还须切换虚拟地址空间（更新 `CR3` 页表基址）。
2. **间接开销（往往更大）**：切入新任务后，私有 **L1/L2 CPU Cache** 中原有热点数据失效，跨进程切换还会导致 **TLB 命中率骤降**（见[第 1 章缓存亲和性](./chapter-01#ch1-3-3)与[第 3 章 TLB](./chapter-03#ch3-2-2)），使新任务在最初数千至数万条指令内持续承受缓存未命中。

### 4.2.3 线程实现模型与现代用户态调度（M:N） {#ch4-2-3}

按用户态执行流与操作系统内核线程的映射关系，并发执行模型分为三类：

| 模型 | 映射方式 | 优势 | 劣势 | 典型代表 |
| --- | --- | --- | --- | --- |
| **N:1（纯用户态线程）** | 多个用户线程映射到 1 个内核线程 | 创建/切换全在用户态，开销极低 | 无法利用多核 CPU；任一线程发起阻塞系统调用会卡死整个进程 | 早期绿色线程、单线程事件循环协程（如 Python `asyncio`） |
| **1:1（内核级线程）** | 1 个用户线程对应 1 个内核线程（LWP） | 真正多核并行；单线程阻塞不影响同进程其他线程 | 栈默认占数 MB，难以创建数十万个；阻塞唤醒需陷入内核 | Linux **NPTL `pthread`**、Windows 线程、传统 Java 平台线程 |
| **M:N（两级混合调度）** | M 个轻量用户态任务复用到 N 个内核线程（N ≈ CPU 核数） | 兼具多核并行与 KB 级超轻量栈、纳秒级用户态切换；网络 I/O 阻塞只挂起用户任务而不占 OS 线程 | 运行时实现复杂；**严禁直接依赖 OS 线程局部存储（TLS）或无锁定的单线程绑核假设**（任务被挂起恢复后可能漂移到另一 OS 线程，如 Go 需显式调 `runtime.LockOSThread()`） | **Go goroutine（GMP 模型，详见[《Go 语言并发之道》第 5 章](../go-concurrency/chapter-05#ch5-2)）**、**Java 虚拟线程（JDK 21+）**、**Rust Tokio** |

## 4.3 经典 CPU 调度算法取舍对照 {#ch4-3}

当就绪任务数超过 CPU 核数时，抢占式调度器需要在**吞吐量、周转时间与交互响应延迟**之间做权衡。经典理论算法的演进只围绕两个核心矛盾展开——**如何防止长任务堵死短任务（护航效应）**，以及**如何在优待短/高优任务时不让长/低优任务饿死**：

| 调度算法 | 核心规则 | 解决了什么问题 | 固有缺陷（为何需要继续演进） |
| --- | --- | --- | --- |
| **FCFS（先来先服务）** | 非抢占，按到达顺序执行 | 实现极简、无饥饿 | **护航效应**：一个长计算任务堵死后面所有短交互任务 |
| **SJF / SRTF（最短优先）** | 优先运行预计剩余耗时最短者 | 平均等待时间理论最优 | 真实耗时无法预知；短任务持续涌入会导致**长任务饥饿** |
| **HRRN（高响应比优先）** | 选 `(等待 + 服务) / 服务` 最大者 | 等待越久优先级越高，消除饥饿 | 依然需要预知服务时间，且每次调度重算开销高 |
| **RR（时间片轮转）** | 抢占式，轮流运行固定时间片 | 无需预估耗时，响应延迟有界 | 时间片太小被上下文切换吞噬，太大退化为 FCFS；无法区分任务轻重 |
| **MLFQ（多级反馈队列）** | 多级优先级队列，用满时间片降级，高优抢占低优 | 自动让 I/O 交互短任务留在高优队列、计算长任务沉入底层 | 需定期全局提权（Boost）防饥饿，且恶意任务可在时间片耗尽前故意短暂 I/O 操纵优先级 |

## 4.4 Linux 现代调度器：从 CFS 到 EEVDF 与 `sched_ext` {#ch4-4}

### 4.4.1 优先级体系与多级调度类 {#ch4-4-1}

Linux 内核为每个逻辑 CPU 维护独立的运行队列（`struct rq`），避免多核争抢同一把全局大锁。按响应严格程度，任务优先级统一映射到 **`0–139`**（数值越小优先级越高）：

- **`0–99` 实时任务**：对延迟有硬性或准实时要求，总是优先于普通任务执行（为防止实时任务写死循环彻底锁死整机，Linux 默认通过 `kernel.sched_rt_runtime_us = 950000` 限制实时调度类每秒最多占 95% CPU 时间，预留 5% 给普通管理进程救场）；
- **`100–139` 普通任务**：日常服务与应用进程，通过 **`nice` 值**（范围 **`-20` 到 `+19`**，默认 `0`，对应内核优先级 `120 + nice`）微调权重。

Linux 采用模块化的**调度类**（Scheduling Class）链式架构，挑选下一个任务时严格按以下优先级顺序从高到低遍历：

```text
高优先级                                                               低优先级
  stop  --->  Deadline (dl_rq)  --->  Realtime (rt_rq)  --->  Fair (cfs_rq)  --->  sched_ext  --->  idle
              SCHED_DEADLINE          SCHED_FIFO               SCHED_NORMAL         SCHED_EXT       空闲线程
                                      SCHED_RR                 SCHED_BATCH          (Linux 6.12+)
```

- **Deadline（`SCHED_DEADLINE`）**：按最早截止时间优先（EDF）调度，需声明运行周期、单周期运行预算与截止期，适用于音视频硬实时等严苛场景。
- **Realtime（`SCHED_FIFO` / `SCHED_RR`）**：高实时优先级可无条件抢占低优先级与全部普通任务；同优先级下 `FIFO` 跑至阻塞/让出，`RR` 按时间片轮转。
- **Fair（`SCHED_NORMAL` / `SCHED_BATCH`）**：服务绝大多数普通任务与后台批处理任务。

### 4.4.2 从 CFS 到 EEVDF（Linux 6.6+ 重大演进） {#ch4-4-2}

原书 1.5 节介绍的是 Linux 2.6.23 以来沿用十余年的 **CFS（Completely Fair Scheduler，完全公平调度器）**。理解 CFS 的历史局限及其继任者 **EEVDF（Earliest Eligible Virtual Deadline First）**，是掌握现代 Linux 调度的核心：

1. **CFS 的核心思想与瓶颈（Linux 2.6.23 – 6.5）**：
   - CFS 放弃传统固定时间片，改为追踪每个任务的**虚拟运行时间（`vruntime`）**：`Δvruntime = Δ实际运行时间 × (NICE_0_LOAD / 任务权重)`。`nice` 越低权重越大，`vruntime` 涨得越慢；内核用**红黑树**每次挑最左端（`vruntime` 最小）的任务运行，保证长期 CPU 份额按权重公平。
   - **CFS 的痛点**：纯粹追最小 `vruntime` 只刻画了“公平份额”，没有原生表达“**延迟敏感度**”。一个刚唤醒、只需跑 0.2 ms 的 RPC 线程和一个要跑 10 ms 的批处理线程若 `vruntime` 相近，CFS 不知道该先满足前者，历年只能打满脆弱的唤醒抢占启发式补丁。

2. **EEVDF 取代 CFS（Linux 6.6+ 正式成为默认公平调度器）**：
   - 自 **Linux 6.6**（已成为 6.6 LTS 与 6.12 LTS 标准实现）起，内核正式用 **EEVDF** 替换了 CFS 的选任务逻辑（仍沿用 `fair_sched_class` 与权重体系）。
   - EEVDF 仅用两个清晰的数学量同时统一了**带宽公平**与**低延迟响应**：
     - **资格（Eligibility / Lag）**：定义任务滞后量 `lag = V - v_i`（V 为队列加权平均虚拟时间，`v_i` 为任务当前实际虚拟时间）。只有当 **`lag ≥ 0`**（尚未透支应得份额）时，任务才**具备调度资格（Eligible）**。
     - **虚拟截止时间（Virtual Deadline）**：设 `v_e` 为任务本轮进入 Eligible 状态时的虚拟时间（对于新就绪且 `lag ≥ 0` 的任务，起始点取当前 `v_i`），结合任务请求的时间片长度 `r_i` 计算虚拟截止时间：
       ```text
       v_d = v_e + r_i / weight_i
       ```
   - **调度规则**：EEVDF 利用增强红黑树，在所有**具备资格（`lag ≥ 0`）**的任务中，挑选**虚拟截止时间 `v_d` 最早**的任务运行。短时间片 `r_i` 的交互任务拥有更早的 `v_d` 得以合法插队降延迟；一旦用完份额使 `lag < 0` 便立刻失去资格，从数学上杜绝饿死长计算任务。

### 4.4.3 `sched_ext` 可编程调度与容器 CPU 限流治理 {#ch4-4-3}

**Linux 6.12 LTS** 合入了 **`sched_ext`（`SCHED_EXT`）**——允许通过 **eBPF**（见[第 2 章 eBPF](./chapter-02#ch2-4-3)）动态加载用户自定义调度器（如游戏低延迟 `scx_lavd`、多 CCX/NUMA 拓扑感知 `scx_rusty`），且内置看门狗：一旦检测到 eBPF 调度器报错或超过数秒未调度就绪任务，内核会自动卸载它并无损回退至内置 EEVDF。

日常调整任务优先级的命令：`nice -n -5 ./svc`（启动时设普通权重）、`renice -n 10 -p <pid>`（动态调整普通进程 `nice`）、`chrt -r -p 20 <pid>`（切换为 `SCHED_RR` 实时进程，慎用）。

在 Kubernetes 等容器化环境中，**cgroups v2** 通过 `cpu.weight`（相对权重，竞争时生效）与 `cpu.max`（CFS Bandwidth Control 硬性配额，如 `200000 100000` 代表每 100 ms 周期最多消耗 200 ms CPU 时间，即 `limits.cpu = 2`）控制容器算力（详见[《凤凰架构》第 8 章可压缩资源与 QoS](../architecture/chapter-08#ch8-3-1)）。若容器内工作线程数远大于核配额，极易触发周期性 **CPU Throttling（配额提前耗尽后全容器线程被强制冻结至下个周期）**，造成宿主机很闲但接口 P99 延迟飙升的典型故障。

- 进程组 A：数百个状态为 `Z`（`<defunct>`）的子进程；
- 进程组 B：2 个状态为 `D` 的备份进程，执行 `kill -9` 后依然纹丝不动。

1. **进程组 A（`Z` 僵尸进程）**：
   - **原因**：子进程已终止，但父进程没有调用 `wait()`/`waitpid()` 回收退出状态，也没有将 `SIGCHLD` 设为 `SIG_IGN`。
   - **处置**：对僵尸进程本身执行 `kill -9` 无效（它已经死亡）。应查出其父进程 PID（`ps -o ppid= -p <zombie_pid>`），若是可重启的异常父进程则重启父进程（父进程退出后僵尸会被 PID 1 迅速接管回收），根本解法是修复父进程代码确保正确 `waitpid` 回收子进程（容器内还须确保 PID 1 具备子进程收割能力，如使用 `tini`）。
2. **进程组 B（`D` 不可中断睡眠进程）**：
   - **原因**：进程正陷入内核态等待关键硬件/存储操作完成（如损坏磁盘、无响应的硬挂载 NFS），为防止内核数据结构不一致，内核屏蔽了所有信号（包括 `SIGKILL`）。
   - **处置**：`kill -9` 信号只会被挂起排队，待 I/O 返回后才会生效。应先用 `cat /proc/<pid>/stack` 查看内核调用栈定位卡在哪个存储/文件系统，进而恢复底层存储或解除故障网络挂载（如 `umount -lf`）；若底层驱动彻底死锁，往往只能重启主机。

</details>

### 练习 2：为什么把线程池线程数从 16 调到 2000 后，CPU 密集型服务吞吐反而暴跌？

一台 16 核 Linux 服务器上运行纯内存计算服务（几乎无磁盘/网络阻塞）。某开发者误以为“线程越多并发越高”，将工作线程池从 16 个扩到 2000 个，压测发现 QPS 下降了近 40%，且 `vmstat` 显示 `cs`（每秒上下文切换次数）飙升。请从 CPU 调度与硬件缓存两层解释根因。

<details>
<summary>查看参考答案</summary>

1. **物理并行度已达上限**：16 核 CPU 同一物理瞬间最多同时执行 16 个计算线程。线程数从 16 增至 2000 不会增加任何实际算力，只会让 1984 个线程长期在就绪队列排队等待，显著拉长单个请求的**等待时间与尾延迟**。
2. **上下文切换直接与间接开销激增**：调度器不断在 2000 个就绪线程间轮换抢占，带来大量寄存器保存/恢复与内核调度开销；更致命的是**私有 L1/L2 CPU Cache 被反复冲刷变冷**，缓存命中率大幅下降，有效计算占比缩水。
3. **调优原则**：纯 CPU 密集型任务线程数应贴近可用 CPU 核心数（通常为 N 或 N+1）；只有存在阻塞 I/O 时，才需超出核数或改用 M:N 异步/协程模型。

</details>

### 练习 3：诊断并修复 K8s 容器内高并发网关的 CPU Throttling 延迟毛刺

某团队在 64 核物理宿主机上部署了一个延迟敏感的 RPC 网关容器，K8s 配置为 `requests.cpu: 1`、`limits.cpu: 2`（对应 cgroup v2 `cpu.max = 200000 100000`）。上线后监控呈现诡异现象：宿主机整体 CPU 利用率不到 30%，该容器平均 CPU 使用量也只有 `0.8` 核，但接口每隔百毫秒就会爆出 **80～95 ms** 的 P99 延迟尖刺！进入容器排查发现网关启动了 64 个工作线程。

1. 请从 Linux CFS/EEVDF 带宽控制器（`cpu.max`）的记账机制推导：为什么平均只用了 0.8 核，却会产生近 90 ms 的冻结毛刺？
2. 给出观测实锤指标及三项工程治理方案。

<details>
<summary>查看参考答案</summary>

1. **底层发生机制**：
   - `cpu.max = 200000 100000` 意味着以 **100 ms** 为一个刷新周期，容器内**所有线程累加**最多只能消耗 **200 ms** 的 CPU 时间片。
   - 网关未做 cgroup 配额感知（见[第 2 章 `/proc` 陷阱](./chapter-02#ch2-4-3)），读取 64 核宿主机 `/proc/cpuinfo` 创建了 64 个活跃工作线程。当一波并发请求同时到达时，64 个线程在 64 个物理核上并行执行，仅需 **`200 ms / 64 ≈ 3.125 ms`** 就把本周期的 200 ms 配额彻底烧光！
   - 随后内核带宽控制器强行将该容器全部线程移出运行队列挂起（Throttle），必须干等剩余的 **`100 - 3.125 ≈ 96.8 ms`** 直到下个周期发新配额才能继续响应，而从 1 秒均值看消耗并不高。
2. **观测实锤与治理方案**：
   - **实锤指标**：查看 `/sys/fs/cgroup/<pod_cgroup>/cpu.stat` 中的 `nr_throttled`（限流次数）和 `throttled_usec`（累计被冻结微秒数），两者在毛刺期间会急剧飙升。
   - **治理方案**：① **对齐并发线程数**：开启运行时容器配额感知（如 Go 1.25+ 默认感知或显式设 `GOMAXPROCS=2`～`4`），从源头消除 64 线程瞬间透支；② **利用突发预算（`cpu.max.burst`，Linux 5.14+）**：允许空闲周期攒下少量突发配额应对微突发流量；③ **按 QoS 权衡是否移除硬 `limits.cpu`**：对延迟极度敏感且节点算力充裕的在线服务，业内常仅设 `requests.cpu`（映射为 `cpu.weight` 保障底线份额）而放宽或取消过紧的 `limits.cpu`。

</details>

### 练习 4：推导 EEVDF 如何同时照顾延迟敏感任务与吞吐公平

某单核上当前队列加权平均虚拟时间 `V = 100`，有三个权重相同的就绪任务（设 `weight = 1`）：
- **任务 A（后台批处理）**：刚透支了一点份额，`v_A = 102`，请求时间片 `r_A = 10`；
- **任务 B（刚唤醒的交互短任务）**：`v_B = 99`（进入本轮 Eligible 起点 `v_e = 99`），请求时间片 `r_B = 2`；
- **任务 C（另一长计算任务）**：`v_C = 98`（`v_e = 98`），请求时间片 `r_C = 10`。

按照 Linux 6.6+ 的 **EEVDF** 规则，判断三个任务的资格（Eligibility）与虚拟截止时间 `v_d`，指出谁会被优先调度，并对比旧纯 CFS 的选择差异。

<details>
<summary>查看参考答案</summary>

1. **计算资格（`lag = V - v_i ≥ 0`）与虚拟截止时间（`v_d = v_e + r_i / weight`）**：
   - **任务 A**：`lag = 100 - 102 = -2 < 0` → **不具备资格**（直接排除）；
   - **任务 B**：`lag = 100 - 99 = +1 ≥ 0` → **具备资格**，`v_d(B) = 99 + 2/1 =` **101**；
   - **任务 C**：`lag = 100 - 98 = +2 ≥ 0` → **具备资格**，`v_d(C) = 98 + 10/1 =` **108**。
2. **调度结果对比**：
   - **EEVDF 选择任务 B**：虽然 C 的 `v_C = 98` 比 B 的 `99` 更小，但两者都具备资格且 B 的虚拟截止时间 `101 < 108`，交互短任务 B 被优先执行以降低响应延迟。
   - **旧纯 CFS 选择任务 C**：旧 CFS 只挑最小 `vruntime`（98），导致交互短任务 B 被迫排在长任务后面等待（除非靠脆弱的唤醒抢占补丁干预）。

</details>

## 面试题 {#ch4-interview}

本节精选 5 道进程、协程与现代调度深度面试题，聚焦底层机制与跨层踩坑边界。

### 面试题 1：在 Linux 内核底层，进程和线程的本质区别是什么？追问：同进程内的某个工作线程因为空指针解引用触发了 `SIGSEGV`，其他正常工作的线程还能继续运行吗？能否注册信号处理函数忽略 `SIGSEGV` 让程序接着跑？

<details>
<summary>查看参考答案</summary>

**结论**：Linux 内核调度器眼中进程和线程都是 `struct task_struct`（均经 `clone()` 创建），区别仅在于是否共享 `mm_struct` 地址空间与 `files_struct` 等资源；**任一线程触发未恢复的 `SIGSEGV` 会直接杀死整个进程组内的全部线程，且绝不能靠简单忽略信号继续运行**。

**关键依据**：
- **为何牵连全进程**：致命信号（如 `SIGSEGV`、`SIGABRT`、`SIGFPE`）的默认动作作用于整个线程组（TGID）。既然所有线程共享同一片虚拟内存，某线程发生非法内存越界意味着共享堆或全局状态可能已被破坏，继续运行其他线程会导致静默脏数据扩散。
- **为何不能忽略 `SIGSEGV` 继续跑**：`SIGSEGV` 属于 CPU 同步异常触发的硬件故障信号。如果信号处理函数什么都不修就直接 `return`，CPU 会按异常恢复规则**重新执行刚才那条解引用空指针的机器指令**，瞬间再次触发 `SIGSEGV` 陷入百分百 CPU 死循环（或被内核强制杀死）！唯一合法用途是在信号处理器中记录崩溃栈后退出（或如 Go 运行时仅对同步故障转译为当前协程 `panic` 并安全展开栈）。

</details>

### 面试题 2：既然 1:1 内核线程已经能跑满多核，为什么 Go（goroutine）和 Java 21+（虚拟线程）还要引入 M:N 两级调度？追问：将依赖 `thread_local`（TLS）或 `sched_setaffinity` 绑核的旧代码直接放进 M:N 协程里，会引发什么严重 Bug？

<details>
<summary>查看参考答案</summary>

**结论**：M:N 模型是为了将“**百万级高并发 I/O 会话**”与“**昂贵的 MB 级内核线程栈及内核切换**”解耦；但正因为多个协程会在不同内核线程（Carrier Thread / M）之间动态迁移复用，**直接读写 OS 线程级 TLS 或单调 `sched_setaffinity` 会导致上下文串号污染与绑核错乱**。

**关键依据**：
- **M:N 迁移引发的两大灾难**：
  1. **TLS 串号与泄漏**：协程 G1 在内核线程 M1 上往 `thread_local` 存入用户 A 的鉴权信息，随后 G1 因网络读被挂起；M1 立刻切去执行协程 G2，G2 读到的将是用户 A 的残留身份！而 G1 醒来后可能被调度到 M2 上，读到空值。
  2. **裸调 `sched_setaffinity` 污染底层载体线程**：在未锁定载体线程的情况下调用绑核或切换 Namespace（`setns`，这在编写 CNI 网络插件或容器工具时极常见！），被修改的其实是底层的共享内核线程 M1，会影响后续所有调度到 M1 上的无关协程！在 Go 中操作 OS 线程级状态前，必须先调用 `runtime.LockOSThread()` 独占绑定并在必要时销毁该 M。

</details>

### 面试题 3：把普通进程的 `nice` 值调到最高的 `-20`，它能抢占一个 `SCHED_RR` 实时进程吗？追问：如果线上某个 `SCHED_FIFO` 实时线程写出了 `while(1)` 死循环，整台服务器会被彻底卡死连 SSH 都登不上吗？

<details>
<summary>查看参考答案</summary>

**结论**：**`nice = -20` 绝不能抢占任何实时进程**；但若 `SCHED_FIFO` 死循环，现代 Linux 默认开启了 **RT Throttling（实时带宽节流）** 安全阀，通常仍给普通进程（如 `sshd`）保留了 5% 的救命算力（除非多核全部被实时死循环占满且关闭了该保护）。

**关键依据**：
- **调度类严格分层**：调度器按 `Deadline → Realtime (0–99) → Fair (100–139)` 顺序选任务，`nice` 仅调节 `Fair` 类内部的权重，只要 `rt_rq` 非空，`Fair` 任务连参与竞争的机会都没有。
- **实时节流兜底**：Linux 内核默认设置 `/proc/sys/kernel/sched_rt_period_us = 1000000`（1 秒）与 `sched_rt_runtime_us = 950000`（0.95 秒）——当实时任务在 1 秒内累计占满 0.95 秒后，内核强行暂停实时队列 50 ms 让普通任务（如运维排障终端）得以响应。若有人将该参数改为了 `-1`（不限制）且死循环铺满所有核，整机将彻底假死只能硬重启。

</details>

### 面试题 4：在 Linux 6.6+ 的 EEVDF 调度器下，如果某个线程故意“每跑 0.5 ms 就主动 `usleep` 极短时间再醒来”，能否不断骗取早截止期特权饿死同核的计算任务？追问：Linux 6.12 引入的 `sched_ext` 允许用户加载自定义 eBPF 调度器，万一写出了漏调度 Bug 会把机器搞死吗？

<details>
<summary>查看参考答案</summary>

**结论**：**不能饿死其他任务**，因为 EEVDF 严格用滞后量 **`lag ≥ 0` 控制准入资格**；`sched_ext` **不会搞死整机**，内核内置了硬件时钟看门狗与自动回退机制。

**关键依据**：
- **EEVDF 防操纵机制**：短请求时间片只会让任务的虚拟截止时间 `v_d` 靠前，前提是它必须先满足 `lag = V - v_i ≥ 0`（没透支自己应得的权重带宽）。一旦它累计消耗超出了公平份额使 `lag < 0`，哪怕睡眠极短时间立即醒来，内核仍会保留/约束其负 `lag` 状态，使其无法获得 Eligible 插队资格，从而封死早期调度器常见的“睡眠刷优先级”漏洞。
- **`sched_ext` 安全兜底**：不仅加载时受 eBPF Verifier 校验防死循环，运行时内核还设有可运行任务停滞看门狗（Watchdog，默认超时 30 秒可调），一旦发现有就绪任务长期未被 eBPF 调度器派发或触发运行时错误，内核立即原子踢出该 eBPF 调度器，将全部任务平滑迁回内置 EEVDF。

</details>

### 面试题 5：为什么 `top` 显示一台 8 核服务器的 Load Average 高达 `32.0`，但 CPU 总使用率（`us + sy + si`）却只有 `10%`？

<details>
<summary>查看参考答案</summary>

**结论**：与其他 Unix 只统计就绪/运行任务不同，**Linux 的 Load Average 同时统计 `R`（运行/就绪）状态和 `D`（`TASK_UNINTERRUPTIBLE` 不可中断睡眠）状态的任务数**；CPU 很闲而 Load 极高，说明有大量线程正阻塞在 `D` 状态等待慢速或故障 I/O。

**关键依据**：
- 当磁盘故障、Swap 剧烈颠簸、NFS 网络存储断联或内核文件系统锁拥塞时，数十个工作线程陷入内核态 `D` 状态休眠，完全不消耗 CPU 周期（故 `us + sy` 仅 10%），却全部计入系统活跃负载。
- **一步定界命令**：执行 `vmstat 1` 看 `b` 列（阻塞任务数）与 `wa`（iowait），再执行 `ps -eo stat,pid,comm,wchan:32 | grep '^D'` 或查看 `/proc/<pid>/stack`，即可在几秒内锁定所有线程究竟卡在哪个内核 I/O 函数上。

</details>
