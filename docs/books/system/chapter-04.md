# 第 4 章 进程、线程与 CPU 调度

## 本章要点

程序是存储在磁盘上的静态可执行文件，只有被操作系统装载进内存并赋予执行上下文后，才会成为动态推进的任务实体。本章整合原书《图解系统》第 4.1 节、第 1.5 节（Linux 调度器）以及第 5.1 节（进程调度算法），彻底消除原书在进程调度上的三处重复，并结合现代操作系统实践做出关键更新：对照教科书状态模型与 Linux 实际进程状态（特别是不可中断睡眠 `D`、孤儿进程与僵尸进程），将 M:N 线程模型衔接至 Go GMP 与 Java 虚拟线程，并将 Linux 调度器从历史上的 CFS 更新至 **Linux 6.6+ 默认的 EEVDF 调度器**及 **Linux 6.12+ 的 `sched_ext`**。

读完本章后，应能区分进程与线程在资源归属、切换开销和内核实现上的异同，诊断僵尸进程与 `D` 状态进程，理解 1:1 与 M:N 并发模型的取舍，并说明经典调度算法如何演化至现代 Linux 多级调度类与 EEVDF。

> 核对日期：2026 年 11 月 20 日；核对环境为 Linux 6.12 LTS 调度器内核文档及 POSIX/NPTL 规范。

## 4.1 进程模型与 Linux 实际生命周期 {#ch4-1}

### 4.1.1 进程控制块（`task_struct`） {#ch4-1-1}

**进程（Process）**是操作系统进行**资源分配与隔离的基本单位**。在操作系统内核中，每个进程都由唯一的**进程控制块**（PCB）描述；在 Linux 内核中，这一结构体称为 **`struct task_struct`**（原书 1.5 节多处误拼为 `tark_struct`），核心包含四类信息：

- **身份标识**：进程号 PID、线程组号 TGID（用户态 `getpid()` 实际返回 TGID）、父进程指针与所属用户凭证（UID/GID）。
- **调度与状态信息**：任务当前状态、调度类指针、静态/动态优先级、虚拟运行时间与截止时间参数。
- **资源清单**：指向虚拟地址空间描述符 `mm_struct`（含页表）、打开文件描述符表 `files_struct`、信号处理器与 Namespace/cgroup 归属。
- **CPU 上下文现场**：任务切换出 CPU 时保存的内核栈指针、通用寄存器与浮点/向量寄存器状态。

### 4.1.2 理论状态模型与 Linux 实际状态对照 {#ch4-1-2}

教科书常用五态（创建、就绪、运行、阻塞、终止）或加入内存换出概念的七态（就绪挂起、阻塞挂起）模型来抽象进程生命周期。而在实际排查 Linux 系统（如 `ps`、`top`）时，需要重点掌握 Linux 内核的真实状态码：

| 状态码 | 内核宏 | 含义与典型触发场景 |
| --- | --- | --- |
| **`R`** | `TASK_RUNNING` | **运行中或就绪**：正在 CPU 上执行，或位于就绪队列等待调度（Linux 不在状态码上区分运行与就绪） |
| **`S`** | `TASK_INTERRUPTIBLE` | **可中断睡眠**：等待网络数据、管道、定时或锁；收到信号（如 `SIGTERM`、`SIGKILL`）可被唤醒响应 |
| **`D`** | `TASK_UNINTERRUPTIBLE` | **不可中断睡眠**：通常在等待关键内核态硬件 I/O（如故障磁盘或卡死的 NFS）。**该状态下进程不响应任何信号，连 `kill -9` 也无法立即终止**，且会计入系统 Load Average |
| **`T` / `t`** | `TASK_STOPPED` / `TRACED` | 收到 `SIGSTOP`/`SIGTSTP`（如 `Ctrl+Z`）暂停，或正被调试器（`gdb`/`strace`）跟踪 |
| **`Z`** | `EXIT_ZOMBIE` | **僵尸状态**：进程已执行退出，内存与文件已释放，但 `task_struct` 与 PID 仍残留等待父进程读取退出码 |
| **`X`** | `EXIT_DEAD` | 彻底消亡的瞬态，通常不可见 |

### 4.1.3 孤儿进程与僵尸进程（纠偏原书泛化表述） {#ch4-1-3}

原书 4.1 节曾按早期教材概括称“终止父进程时同时也会终止其所有子进程”，这与 Linux/Unix 实际行为不符。在 Linux 中，父子进程的退出先后会产生两种截然不同的现象：

- **孤儿进程（Orphan Process）**：**父进程先于子进程退出**。子进程不会被连带杀死，而是被内核重新托管给 **PID 1（如 `systemd`）** 或设置了 `PR_SET_CHILD_SUBREAPER` 的祖先进程，由新父进程负责后续回收。孤儿进程本身通常无害（许多守护进程正是利用该机制脱离终端）。
- **僵尸进程（Zombie Process）**：**子进程已退出，但父进程一直未调用 `wait()` / `waitpid()` 回收其退出状态**。僵尸进程不再占用 CPU 和用户态物理内存，但仍占据一个内核 `task_struct` 和 PID 槽位。大量僵尸进程积压会耗尽系统 PID 上限，导致无法创建新进程。由于僵尸进程已经“死亡”，**对其执行 `kill -9` 无效**——只能修复父进程（正确处理 `SIGCHLD` 并调用 `waitpid`）或终止失职的父进程（让僵尸被 PID 1 接管并立即清理）。

## 4.2 线程、上下文切换与现代并发线程模型 {#ch4-2}

### 4.2.1 线程与 Linux 轻量级进程（LWP） {#ch4-2-1}

**线程（Thread）**是进程内的一条独立执行流，也是 **CPU 调度的基本单位**。同一进程内的多个线程**共享**虚拟地址空间（代码段、数据段、堆、页表）与打开的文件描述符等重型资源，各自**独享**少量执行现场：

- 独立的**用户态栈**与**内核态栈**；
- 独立的 **CPU 寄存器状态**（含程序计数器 PC 与栈指针 SP）；
- 独立的**线程局部存储（TLS）**、错误码 `errno` 与信号掩码。

在 Linux 内核的设计哲学中，**没有专门独立于 PCB 之外的 TCB 结构体**——无论是进程还是线程，底层都由同一个系统调用 `clone()` 创建并表示为 `struct task_struct`。调用 `fork()` 时不共享地址空间与文件表，得到独立进程；调用 `pthread_create()` 时传入 `CLONE_VM | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD` 等标志共享进程资源，得到的就是共享同一 TGID 的线程（常称**轻量级进程 LWP**）。

线程的代价在于**故障隔离弱**：同一进程内任意一个线程触发非法内存访问（`SIGSEGV`）或未捕获致命信号，会导致整个进程及其全部线程一同崩溃。

### 4.2.2 进程与线程上下文切换的真实开销 {#ch4-2-2}

CPU 上下文切换（Context Switch）指内核暂停当前任务、将其 CPU 寄存器与内核栈指针保存到 `task_struct`，再加载下一个任务的现场恢复执行的过程。触发场景包括：时间片耗尽、等待 I/O 或锁主动阻塞、高优先级任务抢占。

上下文切换的开销分为两部分：

1. **直接开销（微秒级）**：保存/恢复通用寄存器、浮点/AVX 寄存器、切换内核栈及调度器选任务的计算开销。
   - **同进程线程切换**：共享虚拟地址空间，**无需切换页表**，直接开销较小；
   - **跨进程切换**：还须切换虚拟地址空间（更新 `CR3` 页表基址）。
2. **间接开销（往往更大）**：切入新任务后，私有 **L1/L2 CPU Cache** 中原有热点数据失效，跨进程切换还会导致 **TLB 命中率骤降**（见[第 1 章缓存亲和性](./chapter-01#ch1-3-3)与[第 3 章 TLB](./chapter-03#ch3-2-2)），使新任务在最初数千至数万条指令内持续承受缓存未命中。

### 4.2.3 线程实现模型与现代用户态调度（M:N） {#ch4-2-3}

按用户态执行流与操作系统内核线程的映射关系，并发执行模型分为三类：

| 模型 | 映射方式 | 优势 | 劣势 | 典型代表 |
| --- | --- | --- | --- | --- |
| **N:1（纯用户态线程）** | 多个用户线程映射到 1 个内核线程 | 创建/切换全在用户态，开销极低 | 无法利用多核 CPU；任一线程发起阻塞系统调用会卡死整个进程 | 早期绿色线程、单线程协程库（如 Python `asyncio` 单事件循环） |
| **1:1（内核级线程）** | 1 个用户线程对应 1 个内核线程（LWP） | 真正多核并行；单线程阻塞不影响同进程其他线程 | 栈默认占数 MB，难以轻松创建数十万个；阻塞唤醒需陷入内核 | Linux **NPTL `pthread`**、Windows 线程、传统 Java 平台线程 |
| **M:N（混合/两级调度）** | M 个轻量用户态任务多路复用到 N 个内核线程（N ≈ CPU 核数） | 兼具多核并行与 KB 级超轻量创建、纳秒级用户态切换；阻塞 I/O 自动挂起用户任务而不占 OS 线程 | 运行时调度器实现复杂，需配合非阻塞 I/O 网络轮询器与抢占机制 | **Go goroutine（GMP 模型）**、**Java 虚拟线程（JDK 21+）**、**Rust Tokio 异步任务** |

## 4.3 经典 CPU 调度算法演进 {#ch4-3}

当就绪任务数多于 CPU 核心数时，调度器需要决定何时切换以及下一个运行谁。按能否在任务主动阻塞前打断它，调度分为**非抢占式**（仅在阻塞或退出时切换）和**抢占式**（借助硬件时钟中断与高优先级唤醒强行夺回 CPU）。评价调度算法围绕五个目标：**CPU 利用率**、**系统吞吐量**、**周转时间**（完成时刻 − 提交时刻）、**等待时间**（在就绪队列排队总时间）与 **响应时间**（交互场景下从提交到首次响应的延迟）。

六种经典单核理论调度算法的演进脉络如下：

| 调度算法 | 抢占性 | 核心规则 | 优势 | 局限与痛点 |
| --- | --- | --- | --- | --- |
| **先来先服务（FCFS）** | 非抢占 | 按到达顺序排队执行 | 实现最简单、无饥饿 | **护航效应（Convoy Effect）**：长作业堵死后面所有短作业，交互体验极差 |
| **最短作业优先（SJF）** | 非抢占（抢占版称 SRTF） | 选预计运行时间最短的任务 | 理论上平均等待时间最优、吞吐高 | 无法预知任务真实耗时；源源不断的短作业会导致**长作业饥饿** |
| **高响应比优先（HRRN）** | 非抢占 | 选响应比 `R = (等待时间 + 服务时间) / 服务时间` 最大者 | 兼顾短作业优先与长作业随等待升权（防饥饿） | 仍需预估服务时间，且每次调度需重算所有就绪任务响应比 |
| **时间片轮转（RR）** | 抢占 | 每任务轮流运行固定时间片（Quantum） | 公平、响应时间有界 | 时间片过短导致频繁上下文切换；过长退化为 FCFS |
| **最高优先级（HPF）** | 可选 | 选静态或动态优先级最高者 | 保障关键业务与紧急事件优先 | 纯静态优先级易致低优先级任务**饥饿**（需引入动态老化提权） |
| **多级反馈队列（MLFQ）** | 抢占 | 多级队列，优先级越高时间片越短；用满时间片降级，高队列非空时抢占低队列 | 无需预估耗时，自动区分 I/O 交互型短任务（常驻高队列）与 CPU 计算型长任务 | 需配合定期优先级提升（Boost）防止底层长作业被饿死 |

## 4.4 Linux 现代调度器：从 CFS 到 EEVDF 与 `sched_ext` {#ch4-4}

### 4.4.1 优先级体系与多级调度类 {#ch4-4-1}

Linux 内核为每个逻辑 CPU 维护独立的运行队列（`struct rq`），避免多核争抢同一把全局大锁。按响应严格程度，任务优先级统一映射到 **`0–139`**（数值越小优先级越高）：

- **`0–99` 实时任务**：对延迟有硬性或准实时要求，总是优先于普通任务执行；
- **`100–139` 普通任务**：日常服务与应用进程，通过 **`nice` 值**（范围 **`-20` 到 `+19`**，默认 `0`，对应内核优先级 `120 + nice`）微调权重。

Linux 采用模块化的**调度类**（Scheduling Class）链式架构，挑选下一个任务时严格按以下优先级顺序从高到低遍历：

```text
高优先级                                                               低优先级
  stop  --->  Deadline (dl_rq)  --->  Realtime (rt_rq)  --->  Fair (cfs_rq)  --->  sched_ext  --->  idle
              SCHED_DEADLINE          SCHED_FIFO               SCHED_NORMAL         SCHED_EXT       空闲线程
                                      SCHED_RR                 SCHED_BATCH          (Linux 6.12+)
```

- **Deadline（`SCHED_DEADLINE`）**：按最早截止时间优先（EDF）调度，需声明运行周期、单周期运行预算与截止期，适用于音视频硬实时等严苛场景。
- **Realtime（`SCHED_FIFO` / `SCHED_RR`）**：高实时优先级可无条件抢占低优先级与全部普通任务；同优先级下 `FIFO` 跑至阻塞/让出，`RR` 按时间片轮转。
- **Fair（`SCHED_NORMAL` / `SCHED_BATCH`）**：服务绝大多数普通任务与后台批处理任务。

### 4.4.2 从 CFS 到 EEVDF（Linux 6.6+ 重大演进） {#ch4-4-2}

原书 1.5 节介绍的是 Linux 2.6.23 以来沿用十余年的 **CFS（Completely Fair Scheduler，完全公平调度器）**。理解 CFS 及其继任者 **EEVDF（Earliest Eligible Virtual Deadline First）**，是掌握现代 Linux 调度的核心：

1. **CFS 的核心思想与瓶颈（Linux 2.6.23 – 6.5）**：
   - CFS 放弃传统固定时间片，改为追踪每个任务的**虚拟运行时间（`vruntime`）**：
     ```text
     Δvruntime = Δ实际运行时间 × (NICE_0_LOAD / 任务权重)
     ```
   - `nice` 值越低、权重越大，`vruntime` 涨得越慢；内核用**红黑树**按 `vruntime` 排序，每次挑最左端（`vruntime` 最小）的任务运行，保证长期 CPU 份额按权重绝对公平。
   - **CFS 的痛点**：纯粹追最小 `vruntime` 只刻画了“公平份额”，没有原生表达“**延迟敏感度**”。一个刚唤醒、只需跑 0.2 ms 的交互任务和一个需要跑 10 ms 的计算任务若 `vruntime` 相近，CFS 不知道该先满足前者。为此内核历年叠加了大量脆弱的启发式补丁（如 `GENTLE_FAIR_SLEEPERS`、`wakeup_granularity`），调优困难且尾延迟不可控。

2. **EEVDF 取代 CFS（Linux 6.6+ 正式成为默认公平调度器）**：
   - 自 **Linux 6.6**（2023 年发布，已成为 6.6 LTS 与 6.12 LTS 标准实现）起，内核正式用 **EEVDF** 替换了 CFS 的选任务逻辑（仍沿用 `fair_sched_class` 与权重体系）。
   - EEVDF 仅用两个清晰的数学量就同时统一了**带宽公平**与**低延迟响应**：
     - **资格（Eligibility / Lag）**：定义任务滞后量 `lag = V - v_i`（其中 V 是当前队列的理想平均虚拟时间，v_i 是该任务的实际虚拟运行时间）。只有当 `lag ≥ 0`（即任务还没“透支”它应得的公平份额）时，它才**具备调度资格（Eligible）**。
     - **虚拟截止时间（Virtual Deadline）**：每个任务可声明自己的请求时间片长度 `r_i`（默认由内核按延迟需求设定），其虚拟截止时间为：
       ```text
       v_d = v_e + r_i / weight_i
       ```
   - **调度规则**：EEVDF 利用增强红黑树，在所有**具备资格（`lag ≥ 0`）**的任务中，挑选**虚拟截止时间 `v_d` 最早**的任务运行。
   - **直观效果**：短请求时间片 `r_i` 的延迟敏感任务拥有更早的 `v_d`，只要未超额透支份额就能立刻插队获得极低响应延迟；而一旦运行完本次份额、`lag < 0`，它立刻失去资格，把 CPU 交还给长计算任务，既消除启发式黑魔法，又严格守住长期公平性。

### 4.4.3 `sched_ext` 可编程调度与运维调优 {#ch4-4-3}

**Linux 6.12 LTS**（2024 年底）合入了备受瞩目的 **`sched_ext`（`SCHED_EXT`）**——允许通过 **eBPF**（见[第 2 章 eBPF](./chapter-02#ch2-4-3)）动态加载用户自定义调度器（如 Meta 开源的 `scx_lavd`、`scx_rusty` 等），在不修改内核源码的前提下针对特定业务（游戏低延迟、大规模微服务混布、拓扑感知）定制调度策略；若 eBPF 调度器超时或出错，内核会自动安全回退到内置 EEVDF。

日常运维中调整任务优先级的常用命令：

```bash
# 以 nice = -5 启动普通任务（调高优先级需 root 或 CAP_SYS_NICE 权限）
nice -n -5 ./my_service

# 动态调整运行中进程的 nice 值（无法将普通进程变为实时进程）
renice -n 10 -p 12345

# 将进程设为 SCHED_RR 实时策略，实时优先级 20（慎用！失控可能饿死系统管理进程）
chrt -r -p 20 12345
```

在容器化环境中，**cgroups v2** 通过 `cpu.weight`（相对权重，类似 nice）与 `cpu.max`（硬性带宽配额，如 `200000 100000` 表示每 100 ms 最多使用 200 ms 即 2 核 CPU）控制容器组 CPU 份额；需特别注意，配置过严的 `cpu.max` 易引发 **CPU Throttling（限流周期内被强行挂起）**，导致服务尾延迟飙升。

### 练习 1：线上出现大量 `Z` 状态和 `D` 状态进程该如何处置？

运维告警显示某服务器 `ps aux` 输出中同时出现两类异常进程：
- 进程组 A：数百个状态为 `Z`（`<defunct>`）的子进程；
- 进程组 B：2 个状态为 `D` 的备份进程，执行 `kill -9` 后依然纹丝不动。

请分别解释原因，并给出正确的处置方案。

<details>
<summary>查看参考答案</summary>

1. **进程组 A（`Z` 僵尸进程）**：
   - **原因**：子进程已终止，但父进程没有调用 `wait()`/`waitpid()` 回收退出状态，也没有将 `SIGCHLD` 设为 `SIG_IGN`。
   - **处置**：对僵尸进程本身执行 `kill -9` 无效（它已经死亡）。应查出其父进程 PID（`ps -o ppid= -p <zombie_pid>`），若是可重启的异常父进程则向父进程发 `SIGCHLD` 测试或重启父进程（父进程退出后僵尸会被 PID 1 迅速回收），根本解法是修复父进程代码确保正确回收子进程。
2. **进程组 B（`D` 不可中断睡眠进程）**：
   - **原因**：进程正陷入内核态等待关键硬件/存储操作完成（如损坏磁盘、无响应的硬挂载 NFS），为防止内核数据结构不一致，内核屏蔽了所有信号（包括 `SIGKILL`）。
   - **处置**：`kill -9` 信号只会被挂起排队，待 I/O 返回后才会生效。应先用 `cat /proc/<pid>/stack` 查看内核调用栈定位卡在哪个存储/文件系统，进而恢复底层存储或解除故障网络挂载（如 `umount -lf`）；若底层驱动彻底死锁，往往只能重启主机。

</details>

### 练习 2：为什么把线程池线程数从 16 调到 2000 后，CPU 密集型服务吞吐反而暴跌？

一台 16 核 Linux 服务器上运行纯内存计算服务（几乎无磁盘/网络阻塞）。某开发者误以为“线程越多并发越高”，将工作线程池从 16 个扩到 2000 个，压测发现 QPS 下降了近 40%，且 `vmstat` 显示 `cs`（每秒上下文切换次数）飙升。请从 CPU 调度与硬件缓存两层解释根因。

<details>
<summary>查看参考答案</summary>

1. **物理并行度已达上限**：16 核 CPU 同一物理瞬间最多同时执行 16 个计算线程。线程数从 16 增至 2000 不会增加任何实际算力，只会让 1984 个线程长期在就绪队列排队等待，显著拉长单个请求的**等待时间与尾延迟**。
2. **上下文切换直接与间接开销激增**：调度器不断在 2000 个就绪线程间轮换抢占，带来大量寄存器保存/恢复与内核调度开销；更致命的是**私有 L1/L2 CPU Cache 被反复冲刷变冷**，缓存命中率大幅下降，有效计算占比缩水。
3. **调优原则**：纯 CPU 密集型任务线程数应贴近可用 CPU 核心数（通常为 N 或 N+1）；只有存在大量阻塞 I/O 时，才需超出核数或改用异步事件驱动/协程模型（M:N）。

</details>

### 练习 3：用具体工作负载推导 FCFS、SJF 与 RR 的表现差异

假设 0 时刻同时到达三个纯计算任务：P1（需 24 ms）、P2（需 3 ms）、P3（需 3 ms），在单核 CPU 上忽略切换开销：

1. 按 **FCFS**（P1 → P2 → P3 顺序）执行，三者的平均等待时间是多少？
2. 按 **SJF**（P2 → P3 → P1 顺序）执行，平均等待时间是多少？
3. 若改为 **RR（时间片 4 ms）**，P2 和 P3 各自的响应时间与周转时间有何变化？说明这揭示了什么调度权衡。

<details>
<summary>查看参考答案</summary>

1. **FCFS（P1 → P2 → P3）**：
   - 等待时间：P1 = 0 ms，P2 = 24 ms，P3 = 27 ms；
   - 平均等待时间 = (0 + 24 + 27) / 3 = **17 ms**（典型长作业堵死短作业的护航效应）。
2. **SJF（P2 → P3 → P1）**：
   - 等待时间：P2 = 0 ms，P3 = 3 ms，P1 = 6 ms；
   - 平均等待时间 = (0 + 3 + 6) / 3 = **3 ms**（大幅下降）。
3. **RR（时间片 4 ms，顺序 P1[0–4] → P2[4–7] → P3[7–10] → P1[10–30]）**：
   - P2 响应时间 4 ms、周转时间 7 ms；P3 响应时间 7 ms、周转时间 10 ms；平均等待时间 = (6 + 4 + 7) / 3 = 5.67 ms。
   - **揭示的权衡**：RR 不需要提前预知任务耗时（现实中通常未知），以略高于 SJF 的平均等待时间为代价，换取了所有短任务都有界的**低响应时间**和防饥饿公平性。

</details>

### 练习 4：推导 EEVDF 如何同时照顾延迟敏感任务与吞吐公平

某单核上当前队列理想虚拟时间 `V = 100`，有两个权重相同的就绪任务（设 `weight = 1`）：
- **任务 A（后台批处理）**：已透支一点份额，`v_A = 102`，请求时间片 `r_A = 10`；
- **任务 B（刚唤醒的交互短任务）**：尚未运行过久，`v_B = 99`，请求时间片 `r_B = 2`；
- **任务 C（另一长计算任务）**：`v_C = 98`，请求时间片 `r_C = 10`。

按照 Linux 6.6+ 的 **EEVDF** 规则，请分别判断三个任务的资格（Eligibility）与虚拟截止时间 `v_d`，并指出哪一个会被优先调度。这与旧 CFS 的选择有何不同？

<details>
<summary>查看参考答案</summary>

1. **计算资格（`lag = V - v_i ≥ 0`）与虚拟截止时间（`v_d = v_i + r_i / weight`）**：
   - **任务 A**：`lag = 100 - 102 = -2 < 0` → **不具备资格**（先排除）；
   - **任务 B**：`lag = 100 - 99 = +1 ≥ 0` → **具备资格**，`v_d(B) = 99 + 2/1 =` **101**；
   - **任务 C**：`lag = 100 - 98 = +2 ≥ 0` → **具备资格**，`v_d(C) = 98 + 10/1 =` **108**。
2. **调度结果对比**：
   - **EEVDF 选择任务 B**：虽然任务 C 的 `v_C = 98` 比任务 B 的 `v_B = 99` 更小，但两者都具备资格且任务 B 的虚拟截止时间 101 < 108，因此交互短任务 B 被优先执行，获得极低延迟。
   - **旧纯 CFS 选择任务 C**：旧 CFS 只挑 `vruntime` 最小的 C，导致交互短任务 B 不得不等待更久（除非靠额外的启发式补丁强行干预）。

</details>

## 面试题 {#ch4-interview}

本节精选 5 道高频进程与调度面试题，聚焦底层机制与现代演进辨析。

### 面试题 1：从操作系统底层看，Linux 中的进程和线程本质区别是什么？

<details>
<summary>查看参考答案</summary>

**结论**：在 Linux 内核调度器眼中，**进程和线程没有本质数据结构区别，都是 `struct task_struct`（均由 `clone()` 创建）**；区别仅在于创建时是否共享地址空间、文件描述符表等资源。

**关键依据**：
- **进程**是资源分配单位，拥有独立的虚拟地址空间（`mm_struct`）和文件描述符表（`files_struct`），彼此强隔离。
- **线程**（轻量级进程 LWP）是 CPU 调度单位，同进程内的多个线程共享同一个 `mm_struct`、`files_struct` 和线程组 ID（TGID），仅各自拥有独立的栈、寄存器上下文与内核态 `task_struct`。

</details>

### 面试题 2：既然 1:1 内核线程已经能利用多核，为什么 Go（goroutine）和 Java 21+（虚拟线程）还要在用户态引入 M:N 调度模型？

<details>
<summary>查看参考答案</summary>

**结论**：为了把高并发 I/O 服务中“**高吞吐并发连接数**”与“**昂贵的操作系统内核线程数量**”解耦。

**关键依据**：
- **内存成本**：Linux `pthread` 默认栈空间常为 2–8 MB，开 10 万个线程仅虚拟/物理内存开销就难以承受；而 Go goroutine 初始栈仅 2 KB 且动态扩缩，轻松支撑数十万并发。
- **切换与阻塞成本**：OS 线程挂起/唤醒需陷入内核态并伴随较重上下文切换；M:N 运行时在遇到网络 I/O 阻塞时，底层用 `epoll`/`io_uring` 托管连接，在用户态纳秒级把空闲 OS 线程切换去执行其他就绪任务，兼顾同步代码的易读性与异步事件驱动的高并发。

</details>

### 面试题 3：调整普通进程的 `nice` 值到 `-20`，能否让它抢占一个 `SCHED_RR` 实时进程？

<details>
<summary>查看参考答案</summary>

**结论**：**不能。**

**关键依据**：
- `nice` 值（`-20` 到 `+19`）仅作用于普通调度类（Fair / EEVDF），映射到内核优先级 `100–139`，本质是调整普通任务间的 CPU 权重比例。
- 实时任务（`SCHED_FIFO` / `SCHED_RR`）位于更高优先级的 `rt_sched_class`（优先级 `0–99`）。只要实时队列中存在就绪任务，调度器就会优先于所有普通任务执行它；要将任务变为实时任务，必须使用 `sched_setscheduler()` 或 `chrt` 显式修改调度策略。

</details>

### 面试题 4：为什么 Linux 6.6 选择用 EEVDF 取代运行了十多年的 CFS 调度器？

<details>
<summary>查看参考答案</summary>

**结论**：CFS 只能表达长期 CPU 带宽公平、缺乏对“延迟敏感度”的原生建模，导致内核堆积了大量难以维护的启发式补丁；EEVDF 通过**资格（Lag）+ 虚拟截止时间**用统一算法同时解决了公平性与低延迟问题。

**关键依据**：
- 在 EEVDF 中，只有未超额透支份额的任务（`lag ≥ 0`）才有资格被选中，从数学上封死了短任务长期霸占 CPU 饿死长任务的可能；
- 在有资格的任务中优先调度虚拟截止时间（`v_e + slice / weight`）最早者，让时间片需求短的交互任务天然插队，移除了 CFS 中脆弱的唤醒抢占启发式规则。

</details>

### 面试题 5：容器环境里宿主机 CPU 利用率不高，为什么容器内服务偶尔会出现几十毫秒的响应毛刺？

<details>
<summary>查看参考答案</summary>

**结论**：常见根因之一是 **cgroups CPU 带宽限流（CPU Throttling）**。

**关键依据**：
- 若容器设置了 `cpu.max`（例如 100 ms 周期配额 200 ms，对应 Kubernetes `limits.cpu: 2`），当进程内的多个线程在周期前 25 ms 就并发消耗完 200 ms 的 CPU 时间片时，即使宿主机其他核完全空闲，内核也会强行把整个容器内所有线程挂起，直到剩余的 **75 ms** 周期结束重新补充配额。
- 排查时可查看 cgroups v2 的 `cpu.stat` 中 `nr_throttled` 与 `throttled_usec` 指标是否持续飙升。

</details>
