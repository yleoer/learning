# 第 6 章 文件系统与存储 I/O

## 本章要点

内存断电即失，持久化数据必须落盘到非易失存储设备；但物理硬盘只认扇区和块号，各种外设控制器的寄存器协议也千差万别。操作系统借助**虚拟文件系统（VFS）**、**页缓存（PageCache）**、**通用块层**与**设备驱动**搭起分层抽象，把五花八门的硬件统一包装成易用的文件与目录。本章整合原书《图解系统》第 6 章（文件系统）、第 7 章（设备管理）与第 5 章的磁盘调度算法，补齐原书略过的 **Ext4 区段树（Extent Tree）与日志机制**、Linux **三层打开文件结构**，并将已过时的旧单队列磁盘调度器（CFQ）与 POSIX 伪异步 I/O 全面更新为现代 **NVMe + `blk-mq` 多队列块层**与 **Linux `io_uring`**。

读完本章后，应能说清 `inode`、`dentry`、`struct file` 与文件描述符的层次关系，对比硬链接与软链接、Ext2/3 与 Ext4/XFS/Btrfs 的存储演进，理解 DMA 与 `blk-mq` 如何消除高并发存储瓶颈，并准确辨析缓冲/直接 I/O、`fsync` 落盘语义以及 `io_uring` 真异步 I/O 原理。

> 核对日期：2026 年 11 月 20 日；核对环境为 Linux 6.12 LTS VFS、Ext4、Block Layer（`blk-mq`）与 `io_uring` 内核文档。

## 6.1 虚拟文件系统（VFS）与文件核心抽象 {#ch6-1}

### 6.1.1 VFS 与“一切皆文件” {#ch6-1-1}

Linux 支持磁盘文件系统（Ext4、XFS、Btrfs）、内存虚拟文件系统（`/proc`、`/sys`、`tmpfs`）和网络文件系统（NFS、SMB）。为了向上层应用提供统一的 `open`/`read`/`write`/`close` 接口、屏蔽底层实现差异，内核引入了中间抽象层——**虚拟文件系统（Virtual File System, VFS）**。

VFS 围绕四个核心数据结构运作：

- **超级块（`super_block`）**：记录整个文件系统的全局元信息（块大小、inode 总数、空闲块统计），在文件系统**挂载（mount）时**加载进内存。
- **索引节点（`inode`）**：文件的**唯一身份标识**，持久化保存在磁盘的 inode 区，记录文件大小、权限、属主、时间戳、链接计数及数据块位置（**不含文件名**）；在文件被访问时加载进内存缓存。
- **目录项（`dentry`）**：**仅存在于内核内存中的缓存结构**，记录“文件名 → `inode` 指针”的映射及父子目录层级关系，用于加速路径解析。需注意区分**目录**与**目录项**：目录本身也是磁盘上的特殊文件（有自己的 `inode`，其数据块里存子文件名与 inode 号列表），而 `dentry` 是内核为避免反复读盘建立的内存哈希缓存。
- **打开文件对象（`struct file`）**：每次调用 `open()` 时在内核创建的会话状态对象。

### 6.1.2 Linux 三层打开文件结构（纠偏混淆） {#ch6-1-2}

进程操作文件时传入的只是一个整数——**文件描述符（File Descriptor, fd）**。内核实际通过**三层映射**将其关联到磁盘文件（原书 6.1 节把进程 FD 表与系统打开文件表混在一起描述，实际必须拆分理解）：

```text
进程 A (files_struct)            系统级打开文件表 (struct file)          全局 inode 表 (struct inode)
+-----+------+                   +----------------------------+          +------------------------+
| fd3 |  * --+------------------>| f_pos(偏移) | flags | ref=2 |--------->| inode #1024            |
+-----+------+                   +----------------------------+          | 权限 / 大小 / 数据块位置 |
                                               ^                         +------------------------+
进程 B (fork 继承)                             |                                      ^
+-----+------+                                 |                                      |
| fd3 |  * --+---------------------------------+                                      |
+-----+------+                                                                        |
                                 +----------------------------+                       |
进程 C (独立 open 同一文件) ---->| f_pos(独立) | flags | ref=1 |-----------------------+
                                 +----------------------------+
```

这一三层结构立刻解释了两个重要现象：
1. **`fork()` 父子进程共享读写偏移**：因为 `fork()` 复制的是进程 FD 表指针，指向同一个 `struct file`（引用计数加 1），子进程 `read()` 推进 `f_pos` 后，父进程接着读会从新位置继续。
2. **两个进程独立 `open()` 同一文件互不干扰偏移**：各自创建独立的 `struct file`（独立 `f_pos`），但底层指向同一个 `struct inode`（若并发写同一区域仍需 `O_APPEND` 原子追加或文件锁保护）。

### 6.1.3 硬链接与软链接 {#ch6-1-3}

因为文件名（目录项）与文件实体（`inode`）分离，多个目录项可以指向同一 `inode`：

| 特性 | 硬链接（Hard Link，`ln src dst`） | 软链接 / 符号链接（Symbolic Link，`ln -s src dst`） |
| --- | --- | --- |
| **底层本质** | 多个目录项直接指向**同一个 `inode`**，`inode` 链接计数 `+1` | 新建独立文件并拥有**独立的 `inode`**，其文件内容是目标路径字符串 |
| **跨文件系统** | **不支持**（各文件系统 `inode` 编号独立） | **支持** |
| **链接目录** | 通常禁止（防止目录树成环破坏遍历与引用计数） | **支持** |
| **删除源文件后** | 只要链接计数仍 > 0，文件数据完好无损；全部删除且无进程打开时才释放磁盘块 | 软链接依然存在，但变成指向不存在路径的**悬空链接（Dangling Link）** |

> **实战提示**：当某个大日志文件被 `rm` 删除、链接计数归 `0`，但仍有运行中进程打开着它的 `fd` 时，内核不会立刻释放磁盘块（`df` 仍显示磁盘满，但 `du` 查不到文件），直到该进程关闭 `fd` 或退出才会真正回收空间。

## 6.2 文件磁盘布局：从 Ext2 到 Ext4、XFS 与 Btrfs {#ch6-2}

### 6.2.1 逻辑块、空闲管理与 Ext2 块组 {#ch6-2-1}

传统机械盘物理扇区为 512 字节，现代大容量硬盘与 SSD 普遍采用 **4Kn（4096 字节物理扇区）**。为减少寻址与元数据开销，Linux 文件系统以 **4 KB 逻辑块**（Block）为最小分配与读写单位。

在文件数据块组织上，历史上经历了四种演进：
- **连续分配**：顺序读写极快，但外部磁盘碎片严重且文件难以动态扩容；
- **链表分配（隐式链表 / 显式链表 FAT）**：消除外部碎片、易扩容，但隐式链表无法随机访问；FAT 将指针集中到内存表，却在大容量磁盘下内存占用过高；
- **多级间接索引（Unix / Ext2 / Ext3）**：`inode` 存放 12 个直接块指针（小文件零间接寻址）+ 一级/二级/三级间接索引块指针支持大文件。缺点是超大文件仍需多级随机读索引块、元数据庞大且删除慢。

在空闲空间管理上，Linux 抛弃了易膨胀的空闲表与空闲链表，采用**位图法（Bitmap）**（1 bit 对应 1 个块或 1 个 inode，0 空闲 1 已用），并把整块磁盘划分为若干个**块组（Block Group）**（每块组含数据位图、inode 位图、inode 表、数据块，并在部分稀疏块组冗余备份超级块与块组描述符以防单点损坏）。

### 6.2.2 现代文件系统的关键演进（补齐原书空白） {#ch6-2-2}

原书 6.1 节止步于 Ext2/3 多级索引并略过了 Ext4。理解当今 Linux 生产环境主流文件系统，必须掌握三项核心升级：

1. **Ext4 — 区段树（Extent Tree）与日志（Journaling）**：
   - **Extent 替代多级间接块**：一个 Extent 描述一段**物理连续的数据块区间**（起始逻辑块 + 连续块数 + 起始物理块）。例如一个 128 MB 的连续大文件，在 Ext3 下需要 3 万多个块指针和数十个间接索引块，而在 Ext4 下往往只需 **1 个 12 字节的 Extent** 即可描述！少量区间直接内嵌在 `inode` 内，碎片化大文件则自动升级为深度极浅的 Extent B 树，同时配合**延迟分配**（Delayed Allocation）尽量为文件分配连续空间。
   - **日志机制（Journaling）**：借鉴数据库预写日志（WAL），在修改元数据前先把变更写入磁盘日志区（默认 `data=ordered` 模式确保数据先落盘再提交元数据日志）。系统意外掉电重启时，只需重放几秒内的日志即可恢复文件系统一致性，避免 Ext2 时代动辄数小时的全盘 `fsck`。
   - **目录索引（HTree）**：当目录下文件众多时，Ext4 自动从线性列表升级为哈希 B 树（HTree），保持 `O(1)`–`O(log n)` 查找性能。
2. **XFS**：RHEL/CentOS/Rocky Linux 等发行版默认文件系统。采用分配组（AG）高并发锁设计、动态按需分配 inode（不易耗尽 inode），并全面使用 B+ 树管理空闲空间与区段，在大文件与多线程高并发 I/O 场景表现优异。
3. **Btrfs / ZFS（Copy-on-Write 文件系统）**：修改数据时不原地覆写，而是写入新块再原子更新根指针，天然实现秒级无损快照、端到端数据校验和（防静默位翻转）与透明压缩。

## 6.3 设备管理、DMA 与现代块存储层（`blk-mq`） {#ch6-3}

### 6.3.1 设备控制器、DMA 与驱动程序 {#ch6-3-1}

操作系统不直接操作物理外设芯片，而是通过硬件**设备控制器**交互。控制器暴露三类寄存器（状态寄存器、命令寄存器、数据寄存器），CPU 通过**端口 I/O**（如 x86 `in`/`out`）或现代主流的**内存映射 I/O（MMIO，把设备寄存器映射到物理地址空间像读写内存一样访问）**对其进行控制。设备按传输粒度分为**块设备**（硬盘、NVMe，按块随机寻址）和**字符设备**（键盘、串口，按字节流顺序收发）。

为了避免 CPU 在慢速设备读写上空耗，硬件 I/O 控制方式经历了三级演进：

1. **轮询（Polling）**：CPU 死循环读状态寄存器等待完成，白白耗尽 CPU；
2. **中断驱动（Interrupt）**：设备就绪后发硬件 IRQ，但若每字节/每扇区都由 CPU 搬运进内存，高速网卡和磁盘仍会压垮 CPU；
3. **DMA（Direct Memory Access，直接内存访问）**：现代磁盘与网卡均内置独立 DMA 引擎。CPU 只需向 DMA 控制器下发一次传输描述符（源地址、目标内存物理地址、字节数）即可转身执行其他任务；DMA 控制器直接通过总线把数据从设备缓冲区搬入主存，全部完成后仅发**一次硬中断**通知 CPU，极大释放算力。

**设备驱动程序**属于内核代码，向上向操作系统提供统一标准接口（含非标准设备属性控制入口 `ioctl`），向下屏蔽各厂商控制器的寄存器差异并注册中断处理函数。

### 6.3.2 存储软件三层栈与块层演进：从 HDD 电梯到 NVMe `blk-mq` {#ch6-3-2}

一次文件读写穿过 Linux 存储子系统的三层软件栈：

```text
应用程序 (read / write / io_uring)
  └──> 文件系统层 (VFS + Ext4/XFS + PageCache/dentry/inode 缓存)
         └──> 通用块层 (Block Layer：bio 构建、请求合并、blk-mq 多队列调度)
                └──> 设备层 (NVMe/SCSI 驱动 + DMA 控制器 + 物理磁盘/SSD)
```

**核心现代更新（淘汰旧单队列调度器）**：

- **机械硬盘（HDD）的历史算法**：机械硬盘读写延迟的大头是磁头移动的**寻道时间**（数毫秒）。教科书与原书 5.1 节介绍的经典磁盘调度算法——**FCFS**（寻道抖动大）→ **SSTF**（最短寻道优先，易饥饿）→ **SCAN（电梯算法）** → **C-SCAN（循环单向扫描）** → **LOOK / C-LOOK**（只扫到最远请求即折返）——都是为了合并相邻扇区、减少磁头往返。早期 Linux 2.6–4.x 的单队列块层（`noop`、`cfq`、`deadline`）亦建立在此假设之上。
- **NVMe SSD 与 `blk-mq`（Linux 5.0+）**：现代 **NVMe SSD** 没有机械磁头与旋转延迟，随机访问速度极快，且通过 PCIe 原生提供高达数万个硬件 I/O 提交/完成队列。旧版 Linux 所有 CPU 核争抢同一把全局请求队列自旋锁，在百万级 IOPS 的 NVMe 面前本身成了最大瓶颈！因此 **Linux 5.0（2019）正式彻底移除了传统单队列块层与 CFQ 等旧调度器**（原书 7.1 节列举的“5 种旧调度算法”已过时），全面切换至**多队列块层 `blk-mq`（Multi-Queue Block Layer）**：
  - 为每个 CPU 核心（或每 NUMA 节点）分配无锁争用的**软件提交队列**，再映射到 NVMe 设备提供的多个**硬件派遣队列**；
  - 现代 Linux 6.x 可选的 `blk-mq` I/O 调度器（可通过 `/sys/block/<dev>/queue/scheduler` 查看与切换）包括：**`none`**（NVMe 与云盘默认，极低 CPU 开销，仅做极简合并）、**`mq-deadline`**（保障请求截止期防饥饿，常用于 SATA/SAS 盘）、**`bfq`**（桌面交互公平调度）和 **`kyber`**（面向高速 SSD 的目标读写延迟限流）。

### 6.3.3 端到端链路回顾：键盘敲入 `A` 到屏幕显示 {#ch6-3-3}

以交互输入串起设备管理全链路：按下按键时，键盘控制器生成扫描码并通过总线触发硬中断 → CPU 保存当前现场并转入键盘驱动中断处理程序 → 驱动读取扫描码并交由内核输入子系统（现代 Linux 为 USB HID + `evdev`，早期简化模型为直接转 ASCII 写 TTY 读缓冲区）→ 桌面显示合成器（Wayland/X11）或终端进程唤醒读取按键事件 → 应用程序渲染字符并提交帧缓冲给 GPU 驱动显示在屏幕上，同时内核恢复被中断进程的运行。

## 6.4 文件 I/O 分类、PageCache 持久化与 `io_uring` {#ch6-4}

理解文件 I/O 时，必须把三个相互正交的维度拆开看清：

### 6.4.1 缓冲 I/O vs 非缓冲 I/O（用户态维度） {#ch6-4-1}

指是否利用**标准库在用户空间维护的缓冲区**（例如 C `stdio` 的 `fwrite`/`printf` 行缓冲/全缓冲 vs 直接系统调用 `write`）。用户态缓冲把多次零碎小写入攒成一次较大的 `write()` 系统调用，减少态切换开销；若程序异常崩溃，尚未 `fflush()` 到内核的用户态缓冲数据会丢失。

### 6.4.2 直接 I/O vs 非直接 I/O（内核 PageCache 维度） {#ch6-4-2}

- **非直接 I/O（Buffered / PageCache I/O，Linux 默认）**：`read()` 优先命中内存中的 **PageCache**，未命中才读盘并触发顺序**预读（Read-ahead）**；`write()` 仅把数据拷贝到 PageCache 标记为**脏页**（Dirty Page）便立刻返回成功！内核随后由后台回写线程（`flush`/writeback）在以下时机异步刷盘：脏页比例超阈值（`vm.dirty_ratio` / `vm.dirty_background_ratio`）、驻留超期（默认 30 秒）、内存紧张回收，或应用显式调用 **`fsync()` / `fdatasync()`**。
  - **持久化陷阱**：`write()` 返回成功仅代表数据进了内存，宿主机突然断电依然会丢数据！数据库写 Redo Log / WAL 必须调用 `fsync()` 或 `fdatasync()`（后者在文件大小未变时可跳过非必要元数据如 `atime`/`mtime` 更新，性能更高）强制刷盘。
- **直接 I/O（`O_DIRECT`）**：彻底绕过 PageCache，通过 DMA 在用户态缓冲区与磁盘间直接传输（通常要求缓冲区地址、文件偏移与读写长度均按块设备逻辑扇区如 512 B/4 KB 对齐）。适用两大场景：
  1. **自建缓存的数据库**（如 MySQL InnoDB Buffer Pool）：避免同一份数据在 InnoDB 和 PageCache 存两份（双缓存浪费内存）以及多余拷贝；
  2. **大文件顺序传输**：防止一次性读取数 GB 冷文件挤爆 PageCache、驱逐其他热点小文件（详见[第 7 章零拷贝与大文件传输](./chapter-07#ch7-2-3)）。

### 6.4.3 同步 vs 异步 I/O 与现代 `io_uring` {#ch6-4-3}

一次完整的读 I/O 包含两个阶段：**阶段 1（数据准备）**——数据从磁盘/网卡到达内核缓冲区；**阶段 2（数据拷贝）**——数据从内核缓冲区拷贝到用户态缓冲区。

- **阻塞 I/O**：两阶段均阻塞等待；
- **非阻塞 I/O（`O_NONBLOCK`）**：阶段 1 未就绪立即返回 `EAGAIN`，需循环轮询，但就绪后阶段 2 拷贝仍同步等待；
- **I/O 多路复用（`select`/`poll`/`epoll`）**：单线程统一等待多个描述符的阶段 1 就绪，随后仍须主动调用 `read`/`write` 同步完成阶段 2 拷贝（因此与前两者同属**同步 I/O**；详见[第 7 章 I/O 多路复用](./chapter-07#ch7-3)）；
- **异步 I/O（Asynchronous I/O）**：应用提交请求后立即返回，阶段 1 与阶段 2 **全部由内核异步完成**，完成后通知应用直接消费用户缓冲区中的数据。

**Linux 异步 I/O 的跨时代升级 — `io_uring`（Linux 5.1+ 引入，6.x 全面成熟）**：

早期 Linux 缺乏好用的原生异步 I/O：POSIX `aio_read()` 在 glibc 中实际上是用**用户态线程池阻塞读写模拟**的；Linux 专用 `libaio` 则几乎只对 `O_DIRECT` 块文件有效，不支持常规缓冲文件与网络 Socket，且常在元数据锁上悄悄退化为同步阻塞。

**`io_uring`** 通过在用户态与内核态之间 `mmap` 共享两块无锁环形缓冲区彻底解决了上述痛点：

```text
用户态应用                                         Linux 内核
  |                                                  |
  | 1. 批量写入多个请求描述符 (SQE) ──> [ Submission Queue (SQ) 共享环形队列 ] ──> 2. 内核消费 SQE 并异步执行
  |                                                                                  (支持文件缓冲/直接 I/O + 网络 Socket)
  | 4. 直接从内存轮询/收割完成事件 <── [ Completion Queue (CQ) 共享环形队列 ] <── 3. 内核写入完成结果 (CQE)
```

- **批量提交与极简陷入**：一次 `io_uring_enter()` 可提交几十上百个读写/打开/刷盘/网络收发请求；开启 **`IORING_SETUP_SQPOLL`** 后，由内核轮询线程自动消费 SQ，甚至实现**零系统调用**提交；
- **全场景统一异步**：同时原生支持缓冲文件 I/O、直接 I/O、网络 Socket 以及注册固定缓冲区（Registered Buffers）零拷贝，已成为现代高性能存储引擎（RocksDB、PostgreSQL 18+、ScyllaDB）与网络框架的新一代基石。

## 练习 {#ch6-exercises}

本节包含 4 道练习，覆盖三层打开文件表行为、软硬链接与磁盘空间排查、Ext4 与 `blk-mq` 选型以及 PageCache 持久化语义判断。请先独立作答，再展开核对。

### 练习 1：预测两次打开文件与 `fork()` 后的读写偏移结果

假设文件 `data.txt` 内容为 `"ABCDEFGH"`，分析以下两段 C 伪码在 Linux 下的输出结果：

```c
// 场景 A：先 open，再 fork
int fd = open("data.txt", O_RDONLY);
char buf[3] = {0};
if (fork() == 0) {
    read(fd, buf, 2); // 子进程读 2 字节
    exit(0);
}
wait(NULL);           // 等待子进程结束
read(fd, buf, 2);     // 父进程再读 2 字节
printf("A: %s\n", buf);

// 场景 B：先 fork，父子各自 open
if (fork() == 0) {
    int fd1 = open("data.txt", O_RDONLY);
    read(fd1, buf, 2);
    exit(0);
}
wait(NULL);
int fd2 = open("data.txt", O_RDONLY);
read(fd2, buf, 2);
printf("B: %s\n", buf);
```

<details>
<summary>查看参考答案</summary>

- **场景 A 输出：`A: CD`**。
  - 依据：`open()` 在 `fork()` 之前执行，子进程继承父进程的 FD 表项，父子 `fd` 指向内核中**同一个 `struct file`**，共享同一个文件偏移指针 `f_pos`。子进程读走 `"AB"` 将 `f_pos` 推进至 `2`，父进程随后读取得到 `"CD"`。
- **场景 B 输出：`B: AB`**。
  - 依据：父子进程各自独立调用 `open()`，内核创建了两个相互独立的 `struct file`（各自维护独立的 `f_pos = 0`），仅底层共享同一个 `struct inode`。因此父进程仍从偏移 `0` 读到 `"AB"`。

</details>

### 练习 2：为什么 `df -h` 显示磁盘使用率 100%，`du -sh /*` 统计总大小却只有 30%？

某线上业务服务器磁盘报警写满（`df -h` 显示 100%），运维同学删掉了一个 50 GB 的过期日志后再次查看，`df -h` 依然是 100%，但用 `du -sh /*` 统计所有目录总和远小于磁盘总容量。请从文件系统 `inode` 与引用计数机制解释原因并给出定位与解决命令。

<details>
<summary>查看参考答案</summary>

- **根因**：`rm` 命令仅删除了目录项并把对应 `inode` 的硬链接计数（`i_nlink`）减 1。如果此时仍有正在运行的进程持有该文件的打开文件描述符（`i_count > 0`），文件系统不会回收该 `inode` 占用的数据块！
  - `du` 通过遍历目录树统计可见文件大小，看不到已删除目录项的文件；
  - `df` 直接读取文件系统超级块中的已分配块统计，因此仍把这 50 GB 算作已用。
- **定位与解决**：
  - 执行 `lsof +L1`（或 `lsof | grep deleted`）找出仍打开该已删除文件的进程 PID 与 FD；
  - 重启或向该进程发重载日志信号（如 `nginx -s reopen`）关闭旧 FD 即可立即释放空间；若不可重启，应急时可通过清空 `/proc/<pid>/fd/<fd>`（如 `truncate -s 0 /proc/<pid>/fd/<fd>`）截断回收数据块。

</details>

### 练习 3：数据库写 WAL 为什么必须调用 `fdatasync()`，且常开启 `O_DIRECT`？

某自研存储引擎采用“先写 WAL 日志，再更新内存索引”保证崩溃恢复，却在压测断电测试中发现已向客户端返回成功的最后几百条记录全部丢失。检查代码发现写 WAL 只调用了标准库的 `fwrite()` + `fflush()`。请分析：

1. 为什么调用了 `fflush()` 依然会在断电后丢数据？
2. `fsync()` 与 `fdatasync()` 有何区别，为何预分配固定大小的 WAL 文件更偏爱 `fdatasync()`？
3. 为什么 MySQL InnoDB 数据文件常配置 `O_DIRECT`？

<details>
<summary>查看参考答案</summary>

1. **`fflush()` 只刷了用户态缓冲**：`fflush()` 仅把 C 标准库用户态缓冲区通过 `write()` 交给内核的 **PageCache**，此时数据依然停留在易失性 DRAM 内存中，未落盘到非易失 SSD/HDD，断电即失。必须调用 `fsync()`/`fdatasync()` 通知内核与磁盘控制器将脏页落盘。
2. **`fsync()` vs `fdatasync()`**：`fsync()` 强制同步文件数据以及**全部元数据**（包括访问/修改时间 `mtime`/`atime` 等，常触发额外的 inode 块磁盘写）；`fdatasync()` 仅同步文件数据及**读取数据所必需的元数据**（如文件大小变化时的块映射）。若 WAL 文件提前 `fallocate` 预分配了固定尺寸，写入不改变文件大小，`fdatasync()` 可省去一次元数据磁盘 I/O，显著降低提交尾延迟。
3. **InnoDB 使用 `O_DIRECT` 的原因**：InnoDB 自身已经管理着精细的 Buffer Pool，若再经过内核 PageCache，会产生“双份缓存占用内存 + 额外 CPU 内存拷贝 + 不可控的内核脏页刷盘抖动”；开启 `O_DIRECT` 可让数据页直接经 DMA 在 InnoDB Buffer Pool 与磁盘间传输。

</details>

### 练习 4：为什么 NVMe SSD 上关闭 I/O 调度器（设为 `none`）往往比开启复杂调度器更快？

对比机械硬盘（HDD）与 NVMe SSD 的物理架构，解释为什么 Linux 5.0 移除 CFQ 单队列层并引入 `blk-mq` 后，NVMe 设备默认调度器设为 `none`。

<details>
<summary>查看参考答案</summary>

1. **物理延迟特征逆转**：HDD 的核心瓶颈是 5–10 ms 的机械寻道与旋转延迟，花几十微秒 CPU 时间做电梯排序合并能省下几毫秒，稳赚不赔；而 NVMe SSD 无机械部件，随机读取仅需 10–70 µs 且支持高并发内部通道，复杂排序不仅没有寻道收益，调度器自身的锁与排队计算反而成为 CPU 瓶颈、拉高尾延迟。
2. **多队列直通硬件并行**：NVMe 原生支持每个 CPU 核心独占独立硬件提交/完成队列，配合 `blk-mq` 的 `none` 调度器，每个核心的 I/O 请求几乎无锁直达硬件队列，充分发挥百万级 IOPS 能力。

</details>

## 面试题 {#ch6-interview}

本节包含 5 道高频文件系统与存储 I/O 面试题，聚焦底层数据结构与现代 Linux 演进。

### 面试题 1：在 Linux 中，文件名保存在 `inode` 里吗？为什么同一目录下不能有两个同名文件，但不同目录可以指向同一份数据？

<details>
<summary>查看参考答案</summary>

**结论**：文件名**不保存**在 `inode` 中，而是保存在所属**目录文件的数据块**里（内存中缓存在 `dentry`）。

**关键依据**：
- 目录文件内部维护着“文件名 → `inode` 编号”的映射表（如 Ext4 的 HTree），同一目录内文件名作为键必须唯一。
- `inode` 只记录文件元信息与数据块位置，不感知自己有多少个名字；因此不同目录（或同目录不同名）的多个目录项可以指向同一个 `inode` 号，这就是**硬链接**的原理。

</details>

### 面试题 2：Ext4 相比 Ext2/Ext3 在大文件存储和崩溃恢复上做了哪两项最关键的改进？

<details>
<summary>查看参考答案</summary>

**结论**：大文件存储用 **Extent Tree（区段树）** 取代了多级间接块指针；崩溃恢复继承并优化了 **Journaling（日志机制）**（Ext3 起引入，Ext4 增加日志校验和）。

**关键依据**：
- **Extent Tree**：不再逐个记录 4 KB 物理块号，而是用 `(起始逻辑块, 连续长度, 起始物理块)` 描述大段连续空间，极大缩小大文件元数据体积、降低随机寻址次数与删除耗时。
- **Journaling**：通过预写日志确保掉电后重放日志即可秒级恢复文件系统元数据一致，免去 Ext2 漫长的全盘 `fsck`。

</details>

### 面试题 3：为什么说 `select`/`poll`/`epoll` 属于同步 I/O，而 `io_uring` 才是真正的异步 I/O？

<details>
<summary>查看参考答案</summary>

**结论**：判断同步与异步 I/O 的标准在于“**内核空间到用户空间的数据拷贝**”阶段是否阻塞应用程序。

**关键依据**：
- `select`/`poll`/`epoll` 只是异步/多路地通知应用“哪个 fd 的数据已经就绪”，随后应用程序仍必须自己调用 `read()`/`write()` 并**同步阻塞等待内核完成数据拷贝**。
- `io_uring` 中，应用把用户缓冲区地址封装进提交队列（SQE）后立即返回，内核异步完成硬件 I/O **以及**数据向用户缓冲区的搬运，全部就绪后再把结果写入完成队列（CQE）通知应用直接使用。

</details>

### 面试题 4：Linux 为什么默认不对普通磁盘文件使用 `epoll`？

<details>
<summary>查看参考答案</summary>

**结论**：因为 `epoll`（乃至 `select`/`poll`）设计用于监控“就绪状态会随外部事件变化”的流式对象（Socket、管道、eventfd），而内核认为**普通磁盘文件始终处于就绪状态**。

**关键依据**：
- 向 `epoll_ctl` 添加普通磁盘文件 fd 会直接返回错误 **`EPERM`**；即便传给 `select`/`poll`，它也会立刻返回“可读/可写”，但真正调用 `read()` 若未命中 PageCache 依然会同步阻塞磁盘 I/O。
- 若想对磁盘文件做非阻塞真异步读写，现代 Linux 应使用 **`io_uring`**（或辅以专用线程池）。

</details>

### 面试题 5：一台 Linux 服务器上看到物理磁盘剩余空间还有 50%，但创建新文件时却报 `No space left on device`，可能是什么原因？

<details>
<summary>查看参考答案</summary>

**结论**：最常见原因是文件系统的 **`inode` 耗尽**（大量极小文件占满了预先分配的所有 inode）。

**关键依据**：
- Ext4 等传统文件系统在格式化时按比例固定划分了 `inode` 总数；如果业务在某目录下生成了数百万个几百字节的碎小文件，即使数据块还剩一半，`inode` 位图已全满，同样无法创建新文件。
- 可通过 **`df -i`** 查看 `IUse%` 确认；根治需清理海量小文件（或改用动态分配 inode 的 **XFS** / 合并小文件归档）。

</details>
