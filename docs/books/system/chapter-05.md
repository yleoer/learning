# 第 5 章 进程间通信与并发同步

## 本章要点

独立进程的虚拟地址空间彼此隔离，需要借助操作系统内核才能安全交换数据；而同一进程内的多线程直接共享堆与全局变量，通信几乎零成本，挑战反而转为如何避免并发读写冲突与死锁。本章整合原书《图解系统》第 4.2–4.5 节，彻底消除原书在信号量、互斥/自旋锁及读写锁上的多处重复，剥离生活段子，并补齐现代系统工程必备的底层机制：Linux 互斥锁的 **`futex` 用户态快速路径**、**条件变量与虚假唤醒**、**RCU**、CAS 乐观锁的 **ABA 问题**，以及 `eventfd` / `memfd_create` / Unix 域套接字等现代 IPC 实践。

读完本章后，应能依据数据规模、延迟与跨主机需求选型合适的 IPC 机制，严格区分数据竞争与竞态条件、互斥与同步，说明 `futex` 如何在无竞争时避免内核切换，理解经典同步问题的防死锁与防饥饿构造，并掌握死锁四条件与工程破环方法。

> 核对日期：2026 年 11 月 20 日；核对环境为 Linux 6.12 LTS 内核文档与 POSIX Threads（NPTL）手册。

## 5.1 进程间通信（IPC）：经典机制与现代原语 {#ch5-1}

每个进程拥有独立的用户虚拟地址空间，无法直接读写另一进程的用户内存；而所有进程映射同一份内核空间（见[第 3 章虚拟地址布局](./chapter-03#ch3-3-1)），因此**进程间通信（Inter-Process Communication, IPC）本质上都需要内核参与建立通道或映射共享物理页**。

### 5.1.1 主流 IPC 机制全景对比 {#ch5-1-1}

| IPC 机制 | 通信范围 | 传输形态与拷贝次数 | 典型特点与适用场景 |
| --- | --- | --- | --- |
| **匿名管道（`pipe`）** | 亲缘进程（`fork` 继承 fd） | 无格式字节流、单向半双工；2 次拷贝（用户→内核→用户） | 生命周期随进程；Shell 管道 `cmd1 \| cmd2`（创建兄弟子进程） |
| **命名管道（FIFO，`mkfifo`）** | 本机任意进程 | 同匿名管道，通过文件系统路径名寻址 | 适合简单单向流式传递，不支持随机 `lseek` |
| **消息队列（SysV / POSIX）** | 本机任意进程 | 结构化消息块（保留边界）；2 次拷贝 | 生命周期随内核；POSIX `mq_open` 支持 fd 与多路复用，但单消息与队列总长受限 |
| **共享内存（`shm_open`+`mmap` / `memfd_create`）** | 本机任意进程 | 直接读写同一物理页框；**0 次内核拷贝（最快）** | 适合高频大数据量交换；**无内置同步**，须配合信号量/互斥锁/原子操作 |
| **信号（Signal）** | 本机进程 / 内核→进程 | 仅传递信号编号（唯一**异步**机制） | 异常与控制事件通知（如 `SIGINT`、`SIGTERM`、`SIGCHLD`） |
| **Unix 域套接字（`AF_UNIX`）** | 本机任意进程 | 支持字节流（`SOCK_STREAM`）与数据报（`SOCK_DGRAM`），不经网络协议栈 | **现代本机服务通信主力**（Docker、MySQL、systemd）；支持双向通信、全双工、权限校验及传递文件描述符（`SCM_RIGHTS`） |
| **网络套接字（`AF_INET`/`AF_INET6`）** | 跨主机 / 本机 | 完整 TCP/UDP 协议栈 | 分布式网络通信（详见[第 7 章网络协议栈](./chapter-07#ch7-1)） |

### 5.1.2 关键细节与易错点校准 {#ch5-1-2}

1. **匿名管道的写端/读端关闭规则**：`pipe(int fd[2])` 返回读端 `fd[0]` 与写端 `fd[1]`。`fork()` 后父子进程必须各自关闭不用的那一端，否则若写端未全部关闭，读端永远读不到 EOF 而永久阻塞；若所有读端均已关闭而继续写入，内核会向写进程发送 **`SIGPIPE`**（默认终止进程）。
2. **信号处理的两个硬边界**：进程对信号有三种处置方式（默认、自定义捕获、忽略），但 **`SIGKILL`（9）与 `SIGSTOP`（19）绝对无法被捕捉、阻塞或忽略**（修正原书 `SEGSTOP` 笔误），确保管理员永远拥有强制终止或暂停失控进程的手段。此外，信号处理函数可能打断任意代码（包括 `malloc` 内部锁），因此函数体内**只能调用异步信号安全（Async-Signal-Safe）函数**（例如 `write()`，绝不能调用 `printf()` 或 `malloc()`）。
3. **UDP Socket 绑定纠偏**：原书 4.2 节称“每一个 UDP 的 socket 都需要 `bind`”，实际仅**接收端**（服务端）需要显式 `bind()` 固定端口，UDP 发送端（客户端）可直接调用 `sendto()`，内核会自动为其分配一个临时端口。
4. **现代 Linux 事件通知原语**：传统信号异步打断控制流、编写安全代码极难。现代 Linux 提供了三类将异步事件转化为**文件描述符**的轻量原语——**`eventfd`**（进程/线程间轻量事件计数唤醒）、**`signalfd`**（同步读取信号）和 **`timerfd`**（高精度定时），使它们可以像普通 Socket 一样统一接入 `epoll` 或 `io_uring` 事件循环。

## 5.2 并发竞争与现代同步原语 {#ch5-2}

### 5.2.1 竞态条件、数据竞争与临界区 {#ch5-2-1}

多线程共享同一地址空间，对共享变量的并发修改若缺乏同步极易丢失更新。例如一行高级代码 `i++` 在汇编层拆为三条指令：`load`（内存→寄存器）→ `add`（寄存器加 1）→ `store`（寄存器→内存）。两线程并发执行时若在 `load` 与 `store` 之间交错或运行在不同 CPU 核心上，两次自增可能只生效一次。

讨论并发缺陷时应区分两组核心概念：

- **数据竞争（Data Race）vs 竞态条件（Race Condition）**：
  - **数据竞争**指两个或多个线程未加同步地并发访问同一内存地址且至少包含一次写操作（在 C/C++ 中属于未定义行为，在多核下还受 Store Buffer 与重排影响）；
  - **竞态条件**指业务正确性依赖多个事件的特定先后顺序，即便每个单独操作都加了锁（无数据竞争），若复合检查与修改（Check-Then-Act）未作为整体保护，仍可能出现竞态条件。
- **互斥（Mutual Exclusion）vs 同步（Synchronization）**：
  - **互斥**保证同一时刻至多只有一个执行流进入访问共享资源的**临界区（Critical Section）**；
  - **同步**协调多个执行流的先后协作顺序（例如“生产者放好数据之后，消费者才能读取”）。

### 5.2.2 互斥锁（`futex`）与自旋锁 {#ch5-2-2}

互斥锁和自旋锁是所有悲观锁的地基，核心差异在于**加锁失败时的等待策略**：

- **自旋锁（Spinlock）**：基于 CPU 硬件原子指令（如 `Test-and-Set` 或 `CAS`）在循环中不断重试，**不主动让出 CPU、无线程上下文切换**。循环体内应插入架构退让指令（x86-64 `PAUSE`、ARM64 `YIELD`），降低功耗并避免退出自旋时触发严重的内存序流水线冲刷。适用场景：**多核环境且临界区极短**（远小于上下文切换耗时，如几十纳秒内的链表指针修改），或内核中断上下文等严禁睡眠的环境。在非抢占单核 CPU 上使用自旋锁会直接死锁。
- **互斥锁（Mutex）与 Linux `futex` 底层（核心校准）**：原书 4.5 节容易让人误以为“每次互斥锁加解锁都要陷入内核态”。实际上，现代 Linux 的 `pthread_mutex_t`（以及 Go `sync.Mutex`、Rust `parking_lot`）底层均构建在 **`futex`（Fast Userspace Mutex）** 之上：

```text
无竞争快速路径（纯用户态，零系统调用）：
  线程调用 lock() ──> 原子 CAS(state: 0 -> 1) 成功 ──> 直接进入临界区！
  线程调用 unlock() ──> 原子置 state = 0（发现无等待者）──> 直接返回！

发生竞争慢速路径（陷入内核睡眠）：
  线程调用 lock() ──> CAS 失败 ──>（可选：自适应短暂自旋数十次）
                  ──> 仍失败，调用 futex(FUTEX_WAIT) 陷入内核挂起，让出 CPU
  持锁者 unlock() ──> 置 state = 0，发现有等待者 ──> 调用 futex(FUTEX_WAKE) 唤醒等待线程
```

由此可见，**现代互斥锁在无竞争时几乎与自旋锁一样快**；只有在发生真实争用时才会付出两次上下文切换的代价去睡眠，防止空转浪费 CPU。更进一步，glibc 自适应互斥锁（`PTHREAD_MUTEX_ADAPTIVE_NP`）和 Go 互斥锁在多核竞争时会先在用户态短时间自旋、拿不到再挂起，自动吸收了二者的优点。

### 5.2.3 读写锁、条件变量与 RCU {#ch5-2-3}

1. **读写锁（RWLock）**：区分共享**读锁**（多读并发）与独占**写锁**（读写互斥、写写互斥），适用于明确读多写少且读临界区不算极短的场景。按调度倾向分为三类：
   - **读优先**：新读者可不断插队，易致**写者饥饿**；
   - **写优先**：有写者排队时阻断后续新读者，写者持续涌入时易致**读者饥饿**；
   - **公平读写锁**：将读/写请求按 FIFO 排队，兼顾读并发与防饥饿。
   - **工程提醒**：读写锁维护读者计数器本身需要原子递增/递减，多核高频并发读同一个计数器仍会引发严重的 Cache Line 伪共享/失效风暴（见[第 1 章 MESI 与伪共享](./chapter-01#ch1-4-3)），因此读临界区极短时读写锁反而可能慢于普通互斥锁。
2. **RCU（Read-Copy-Update）**：在极度读多写少的系统内核（如路由表、dentry 缓存、进程链表）与部分高性能框架中，现代 Linux 广泛采用 **RCU** 替代读写锁。**读者无需加锁、也不修改任何共享计数**，几乎零硬件同步开销；写者修改时先复制一份新副本、修改完成后原子替换指针，并等待一个**宽限期**（Grace Period，即所有旧读者都已退出读临界区）后再释放旧内存。
3. **条件变量（Condition Variable）与虚假唤醒**：锁解决互斥，而“等待某个业务条件成立（如队列非空）”须借助条件变量（`pthread_cond_wait` / `signal`）。调用 `wait(cond, mutex)` 会**原子地释放互斥锁并挂起线程**，被唤醒返回前重新持有互斥锁。必须谨记一条铁律：**永远使用 `while (!condition)` 而非 `if (!condition)` 包裹 `wait()`**，因为 POSIX 允许操作系统产生**虚假唤醒（Spurious Wakeup）**，且多线程被唤醒后，条件也可能在重新抢到锁之前已被其他线程消耗掉。

### 5.2.4 悲观锁 vs 乐观锁、CAS 与 ABA 问题 {#ch5-2-4}

互斥锁、自旋锁、读写锁均属**悲观锁**——假定冲突概率高，访问前先独占加锁。**乐观锁**则假定冲突稀少，不加阻塞锁，直接读取数据与版本并计算新值，提交时再原子校验原数据是否被他人改过（典型实现：硬件 **CAS `Compare-And-Swap`** 指令、数据库行版本号 `WHERE version = old_ver`、Git 提交冲突检测）。冲突率低时无锁阻塞吞吐极高，但高争用下反复重试会导致 CPU 飙升与活锁退化。

使用底层 CAS 无锁编程时必须警惕经典陷阱——**ABA 问题**：线程 1 读到共享指针为 `A` 后被挂起；期间线程 2 将值由 `A` 改为 `B`、释放了 `A` 节点又分配复用同一地址改回 `A`；线程 1 恢复后执行 `CAS(ptr, A, C)` 误以为从未变动而成功提交，引发链表损坏等隐蔽 Bug。标准解法是为目标值绑定单调递增的**版本号/标签**（如双宽 CAS `CMPXCHG16B` 或 Java `AtomicStampedReference`），让每次变更升级为 `(A, 1) → (B, 2) → (A, 3)`。

## 5.3 信号量与经典同步问题精炼 {#ch5-3}

**信号量**（Semaphore）是一个由操作系统维护的整型计数器 `sem`（代表可用资源数），只能通过两个不可分割的原子操作修改：

- **`P(sem)`（`sem_wait`）**：`sem--`；若 `sem < 0`，当前执行流挂起进入等待队列；
- **`V(sem)`（`sem_post`）**：`sem++`；若 `sem <= 0`，从等待队列唤醒一个阻塞执行流（`V` 永不阻塞）。

信号量初值设为 `1` 可实现互斥，设为 `0` 可实现先后同步，设为 N 可实现容量为 N 的有界资源池限流。下面用信号量精炼提炼操作系统三大经典并发模型的核心设计要点：

### 5.3.1 生产者-消费者问题（有界缓冲区） {#ch5-3-1}

设缓冲区容量为 N，需要三个信号量：`mutex = 1`（互斥操作缓冲区）、`empty = N`（空槽数）、`full = 0`（已填充数据槽数）：

```c
// 生产者                         // 消费者
P(empty);  // 1. 先申请空槽        P(full);   // 1. 先等待数据
P(mutex);  // 2. 再锁缓冲区        P(mutex);  // 2. 再锁缓冲区
put_item();                       take_item();
V(mutex);  // 3. 释放缓冲区锁      V(mutex);  // 3. 释放缓冲区锁
V(full);   // 4. 通知有新数据      V(empty);  // 4. 通知有新空槽
```

**核心易错点**：两个 `P` 操作的顺序绝不可颠倒！若先 `P(mutex)` 再 `P(empty)`，当缓冲区满时生产者拿着 `mutex` 睡眠等待空槽，而消费者想消费腾出空槽却卡在 `P(mutex)` 上，立刻形成**死锁**。

### 5.3.2 哲学家就餐问题（打破环形对称） {#ch5-3-2}

5 位哲学家围坐圆桌，相邻两人间共 5 支叉子，每人需同时拿到左右两支叉子才能进餐。若所有人都按“先拿左叉、再拿右叉”执行，五人同时拿走左叉就会瞬间死锁。

三种典型改进的权衡：
- 加一把全局大锁保护整个取叉过程：消除死锁，但每次只能 1 人就餐，并发度减半；
- **打破对称（资源有序分配，最简洁推荐）**：令偶数号哲学家先左后右、奇数号先右后左（等价于所有人按叉子编号**从小到大**申请锁），彻底消除环形等待，且支持最多 2 人同时就餐；
- 状态数组 + 每人专属信号量（Tanenbaum 解法）：在互斥锁下检查左右邻居均未进餐才一次性授予两支叉子，并发度同样最优。

### 5.3.3 读者-写者问题（消除写者饥饿） {#ch5-3-3}

在最简单的读者优先解法中（`wMutex = 1`、`rCountMutex = 1`、`rCount = 0`，首个读者加 `wMutex`、末个读者放 `wMutex`），只要读者源源不断到来，写者将被无限期饿死。

只需在读者和写者进入之前统一增加一把**排队闸门信号量 `turnstile = 1`**：

- 读者进入前先 `P(turnstile)`，递增 `rCount`（首读者 `P(wMutex)`）后立即 `V(turnstile)` 允许后续读者并发进入；
- 写者到来时先 `P(turnstile)` 占住闸门，再 `P(wMutex)` 等待当前已在读的读者撤完，写完后再依次 `V(wMutex)` 和 `V(turnstile)`。

闸门阻断了新读者插队到等待写者之前的特权，使读写按到达顺序公平推进，彻底消除写者饥饿。

## 5.4 死锁成因、预防与治理 {#ch5-4}

当两个或多个线程彼此持有对方所需的独占资源且互相等待释放，在无外力介入下永久停滞时，即发生**死锁（Deadlock）**。死锁发生必须**同时满足四个必要条件（Coffman 条件）**：

1. **互斥条件**：资源同一时刻只能由一个线程独占使用；
2. **持有并等待条件**：线程已持有至少一个资源，同时又在阻塞请求其他线程占有的资源；
3. **不可剥夺条件**：已持有的资源不能被外部强行夺走，只能由持有者主动释放；
4. **环路等待条件**：存在线程等待链 T1 → T2 → … → Tn → T1 构成闭环。

**工程防死锁策略**只需破坏上述四个条件中的任意一个，现实中最常用且性价比最高的是**破坏环路等待条件**：

- **资源有序分配法（Lock Ordering）**：为所有需要嵌套获取的锁定义全局唯一顺序（例如按锁编号、对象 ID 或内存地址升序），任何线程都必须严格按此固定顺序加锁。例如线程 A 和线程 B 都统一遵循“先锁 `mutex_A`，再锁 `mutex_B`”，环路等待便从数学上不可能成立。
- **尝试加锁与超时回退**：使用 `pthread_mutex_trylock()` 或带超时的锁接口（破坏“持有并等待”），获取第二把锁失败时主动释放第一把锁并随机退避重试（需注意控制重试抖动以防活锁）。
- **死锁检测与排障工具**：开发测试期可借助 **ThreadSanitizer（TSan）** 或 Linux 内核 **`lockdep`** 静态/动态捕获锁顺序违例；线上卡死时，C/C++ 可通过 `pstack` 与 `gdb` 查看线程调用栈及 `pthread_mutex_t.__data.__owner` 持锁 LWP 快速锁定成环线程（完整命令演练见[第 8 章死锁排查实战](./chapter-08#ch8-2-2)）。

### 练习 1：同机进程间通信的架构选型

现有三个本机多进程协作需求（均运行在同一台 Linux 服务器上），请为每个场景选择最合适的 IPC 方式并说明理由：

1. 视频解码进程每秒产生 60 帧 4K 未压缩图像（约 1.5 GB/s），需要交给渲染进程实时读取；
2. 宿主机上的 CLI 客户端需要与本地守护进程（Daemon）进行请求-响应双向控制通信，并验证调用者 UID 权限；
3. 主进程仅需在内存事件队列就绪时，极轻量地唤醒正阻塞在 `epoll_wait()` 上的工作进程。

<details>
<summary>查看参考答案</summary>

1. **共享内存（`shm_open` + `mmap`）+ 信号量/原子环形索引**：1.5 GB/s 吞吐下，管道、消息队列或普通 Socket 的两次内核/用户态内存拷贝会吃满内存带宽；共享内存零拷贝直接映射同一物理页，配合无锁环形缓冲区或信号量通知同步帧就绪是最优解。
2. **Unix 域套接字（`AF_UNIX` + `SOCK_STREAM`）**：原生全双工双向通信、不走 TCP/IP 协议栈开销低，且支持通过 `SO_PEERCRED` 安全获取对端进程 PID/UID/GID 做鉴权（Docker Daemon `/var/run/docker.sock` 即采用此模式）。
3. **`eventfd`**：专为内核/进程/线程间轻量事件通知设计，仅维护一个 64 位内核计数器且本身就是文件描述符，可直接注册进 `epoll` 唤醒目标进程，开销远低于管道或 Socket。

</details>

### 练习 2：找出条件变量等待代码中的两处并发 Bug

以下代码试图实现一个多线程共享任务队列的消费函数（假设队列 `q` 已正确初始化）：

```c
pthread_mutex_lock(&mtx);
if (queue_empty(q)) {
    pthread_cond_wait(&cv, &mtx);
}
task_t task = queue_pop(q);
pthread_mutex_unlock(&mtx);
```

当有多个消费者线程并发运行、生产者每次放入 1 个任务后调用 `pthread_cond_broadcast(&cv)` 时，这段代码存在什么严重缺陷？应如何修改？

<details>
<summary>查看参考答案</summary>

**缺陷分析**：使用 `if (queue_empty(q))` 而非 `while (queue_empty(q))` 会导致两种空队列非法出队（`queue_pop` 崩溃或未定义行为）：
1. **多线程唤醒竞争（Stolen Wakeup）**：生产者只放入 1 个任务却广播唤醒了所有消费者。消费者 1 先抢到 `mtx` 取走了唯一任务并解锁；消费者 2 随后拿到 `mtx` 从 `pthread_cond_wait` 返回，若用 `if` 则不再复查队列是否为空，直接对空队列执行 `queue_pop(q)`！
2. **虚假唤醒（Spurious Wakeup）**：POSIX 规范允许 `pthread_cond_wait` 在没有线程发信号的情况下意外返回。

**修复方法**：将 `if` 改为 `while` 循环复查谓词条件：

```c
pthread_mutex_lock(&mtx);
while (queue_empty(q)) {
    pthread_cond_wait(&cv, &mtx);
}
task_t task = queue_pop(q);
pthread_mutex_unlock(&mtx);
```

</details>

### 练习 3：修改转账函数彻底消除潜在死锁

某多账户并发转账函数简化如下，每个账户自带一把互斥锁 `acc->lock` 和唯一编号 `acc->id`：

```c
void transfer(account_t *from, account_t *to, int amount) {
    pthread_mutex_lock(&from->lock);
    pthread_mutex_lock(&to->lock);
    from->balance -= amount;
    to->balance += amount;
    pthread_mutex_unlock(&to->lock);
    pthread_mutex_unlock(&from->lock);
}
```

1. 指出该函数在什么并发调用组合下会发生死锁（包含一个容易忽略的边界情况！）；
2. 用**资源有序分配法**重写该函数。

<details>
<summary>查看参考答案</summary>

1. **两种死锁场景**：
   - **双向互转死锁**：线程 1 执行 `transfer(A, B, 100)`，线程 2 同时执行 `transfer(B, A, 50)`。线程 1 持 A 等 B，线程 2 持 B 等 A，构成环路等待。
   - **自转死锁（易忽略边界）**：调用 `transfer(A, A, 100)` 时，`from == to`，非重入互斥锁在同一线程内二次加锁会直接自死锁！
2. **修复实现**：先拦截 `from == to`，再统一按账户唯一 `id` 从小到大加锁：

```c
void transfer(account_t *from, account_t *to, int amount) {
    if (from == to) return;

    account_t *first = (from->id < to->id) ? from : to;
    account_t *second = (from->id < to->id) ? to : from;

    pthread_mutex_lock(&first->lock);
    pthread_mutex_lock(&second->lock);
    from->balance -= amount;
    to->balance += amount;
    pthread_mutex_unlock(&second->lock);
    pthread_mutex_unlock(&first->lock);
}
```

</details>

### 练习 4：剖析无锁栈（Lock-Free Stack）中的 ABA 故障过程

某无锁单向链表栈当前结构为 `Top -> A -> B -> C`。线程 1 准备执行 `pop()`，读到 `old_top = A`、`next = B`，尚未执行 `CAS(&Top, A, B)` 时被操作系统抢占挂起。请构造一个具体操作序列，说明在哪些步骤后线程 1 恢复执行时 CAS 会错误成功，并导致栈结构损坏。

<details>
<summary>查看参考答案</summary>

1. 线程 1 挂起期间，线程 2 连续执行：
   - `pop()` 弹出 `A`（栈变为 `Top -> B -> C`）；
   - `pop()` 弹出 `B`（栈变为 `Top -> C`），并释放或重用 `B` 节点；
   - `push(A)` 将刚刚弹出的同一内存地址节点 `A` 重新压栈（此时栈实际为 `Top -> A -> C`）。
2. 线程 1 恢复执行 `CAS(&Top, A, B)`：它只对比了 `Top` 当前地址确实仍是 `A`，于是 **CAS 成功**，强行将 `Top` 指向了早已被弹出甚至已释放的旧节点 `B`，导致 `C` 丢失或触发悬空指针解引用崩溃。
3. **解决思路**：为 `Top` 指针捆绑单调递增版本号（Tagged Pointer，用双宽 CAS 同时比对地址与版本号），或引入 Hazard Pointer / Epoch-based 延迟内存回收防止地址在读线程持有期间被重用。

</details>

## 面试题 {#ch5-interview}

本节精选 5 道高频 IPC 与并发同步面试题，检验核心底层机制与边界辨析。

### 面试题 1：为什么说现代 Linux 的互斥锁（`pthread_mutex_t`）在无竞争场景下性能开销极低，并不一定会陷入内核态？

<details>
<summary>查看参考答案</summary>

**结论**：因为现代 Linux 互斥锁基于 **`futex`（Fast Userspace Mutex）** 实现，无竞争时的加锁与解锁全程在用户态通过原子操作完成，不触发系统调用。

**关键依据**：
- `futex` 将锁状态保存在用户态共享整型变量中。无争用时，单条原子 CAS 指令即可完成加锁，耗时仅十几纳秒。
- 只有当锁已被他人持有（CAS 失败）时，线程才会调用 `futex(FUTEX_WAIT)` 陷入内核休眠；同样，解锁时只有检测到存在内核等待者时，才会调用 `futex(FUTEX_WAKE)` 唤醒。

</details>

### 面试题 2：在读多写少场景下，把互斥锁换成读写锁（RWLock）性能一定会更好吗？

<details>
<summary>查看参考答案</summary>

**结论**：**不一定**；如果读临界区极短且核心数多，读写锁反而可能比普通互斥锁更慢。

**关键依据**：
- 每次加/解读锁都要对共享的“读者计数”执行原子加减（`LOCK XADD` 等），在多核高频并发读时，所有核心都在争抢该计数器所在的同一条 Cache Line，引发严重的 MESI 缓存行颠簸（Ping-Pong）。
- 读写锁只有在**读临界区足够长**（足以分摊计数器原子争用开销）且写操作占比很低时才显著优于互斥锁；若读极多且临界区很短，应优先考虑无锁读机制（如 **RCU**、SeqLock 或写时复制不可变快照）。

</details>

### 面试题 3：同一进程内的线程通信不需要管道或共享内存，但为什么仍可能遇到类似“通信不可见”的并发问题？

<details>
<summary>查看参考答案</summary>

**结论**：共享虚拟地址空间只意味着线程能访问同一内存地址，但并不自动保证**原子性**与**跨核内存可见性顺序**。

**关键依据**：
- 编译器优化可能把共享变量缓存在寄存器中不再回读内存，CPU 的 Store Buffer 与乱序执行也可能导致核 A 的写入延迟对核 B 可见或顺序颠倒。
- 因此线程间共享变量读写仍必须通过互斥锁、原子变量（带合适的内存序如 `acquire`/`release`）或通道等同步原语建立明确的 happens-before 顺序。

</details>

### 面试题 4：在生产者-消费者模型中，如果把生产者的 `P(empty)` 和 `P(mutex)` 顺序调换，会发生什么？

<details>
<summary>查看参考答案</summary>

**结论**：当缓冲区满时必然触发**死锁**。

**关键依据**：
- 缓冲区满时 `empty == 0`。生产者先执行 `P(mutex)` 拿走了缓冲区互斥锁，随后在 `P(empty)` 处阻塞等待消费者腾出空槽；
- 消费者要消费数据腾出空槽，必须先执行 `P(mutex)` 获取缓冲区锁，于是也被阻塞。双方相互持有对方所需条件（锁 vs 空槽），永久死锁。
- 通用原则：**永远先申请资源计数信号量，再获取保护数据结构的互斥锁**（`V` 操作顺序则不影响死锁，但先放 `mutex` 可缩短持锁时间）。

</details>

### 面试题 5：为什么 `kill -9` 能杀死绝大多数进程，进程自己写信号处理函数也拦不住？

<details>
<summary>查看参考答案</summary>

**结论**：`kill -9` 发送的是 `SIGKILL` 信号，操作系统内核在设计上硬性禁止用户进程捕获、阻塞或忽略 `SIGKILL`（以及 `SIGSTOP`），直接由内核强制终止进程。

**关键依据**：
- 相比之下，`kill -15`（`SIGTERM`）允许进程注册信号处理函数执行优雅退出（关闭连接、刷盘日志）。
- `SIGKILL` 不经过用户态处理函数，内核直接回收进程资源并置为终止状态（仅在进程处于 `D` 不可中断睡眠等待内核硬件 I/O 返回前，会暂缓至退出 `D` 状态后立即生效）。

</details>
