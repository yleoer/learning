# 第 3 章 内存管理与页面回收

## 本章要点

在没有内存虚拟化的裸机或单片机环境下，多个程序直接读写绝对物理地址会立刻互相覆盖而崩溃。操作系统通过**虚拟内存**（Virtual Memory）为每个进程提供独立、连续且受权限保护的地址视图，同时在底层高效复用有限的物理内存。本章整合原书《图解系统》第 3 章（虚拟内存）与第 5 章的缺页及页面置换内容，修正原书对内部碎片的定义偏差，并补齐现代 Linux 6.x 的核心机制：5 级页表、ASLR、大页（HugePages/THP）、伙伴系统与 SLUB、`malloc` 底层分配、写时复制（COW）以及 Linux 6.1+ 的多代 LRU（MGLRU）与 OOM Killer。

读完本章后，应能完整推导一次虚拟地址访问穿过 TLB、多级页表和缺页中断的路径，区分内部碎片与外部碎片、次缺页与主缺页，解释 `malloc` 为何不会立刻消耗物理内存，并理解现代 Linux 如何在内存紧张时回收文件页与匿名页。

> 核对日期：2026 年 11 月 23 日；核对环境为 Linux 6.12 LTS 内存管理子系统文档及 x86-64/ARM64 体系结构手册。

## 3.1 虚拟内存、分段与分页 {#ch3-1}

### 3.1.1 虚拟内存的核心价值 {#ch3-1-1}

引入虚拟内存后，应用程序代码只与**虚拟地址（Virtual Address, VA）**打交道，由 CPU 内部的**内存管理单元（MMU）**配合操作系统维护的映射表实时翻译为**物理地址（Physical Address, PA）**。这一抽象带来四项关键能力：

1. **进程地址隔离**：不同进程拥有各自独立的虚拟地址空间与页表映射，即便访问相同的虚拟地址（如 `0x400000`），默认也映射到互不干扰的私有物理页框。需要注意的是，进程隔离**并非**要求不同进程的物理页绝不重叠——`fork()` 后的写时复制（COW）只读共享、多进程共享动态库（`.so`）或只读代码页，以及显式建立的 `mmap(MAP_SHARED)` 共享内存，都会让多个进程的虚拟页指向同一物理页框；进程隔离真正依靠的是**各自独立的虚拟地址空间页表映射**与**页表项的读/写/执行权限位控制**（例如 COW 与只读代码页的页表项均标记为只读，任何写操作都会被 MMU 拦截触发缺页异常或 `SIGSEGV`，确保进程无法越界篡改他人的私有数据）。
2. **内存保护**：页表项中携带读/写/执行（R/W/X）及用户/内核权限位，硬件在翻译地址的同时强制校验权限（例如禁止修改代码段、禁止在栈/堆上执行机器码 NX）。
3. **按需分配与超额承诺（Overcommit）**：进程申请内存时只需登记虚拟地址区间，真正访问时才按需分配物理内存，使所有进程虚拟空间之和远超物理内存容量。
4. **简化内存共享**：多个进程的虚拟页可映射到同一物理页框，实现动态共享库代码复用、共享内存 IPC 与写时复制。

### 3.1.2 内存分段与碎片定义纠偏 {#ch3-1-2}

早期体系结构按程序逻辑模块（代码段、数据段、堆段、栈段）划分变长区域，称为**内存分段（Segmentation）**。虚拟地址由“段选择子 + 段内偏移量”构成，查询段表得到段基址与界限，检查偏移合法后相加即得物理地址。

分段存在两大顽疾：**外部碎片严重**与**交换开销极大**（换出整个大段到磁盘极为卡顿）。这里需要对原书 3.1 节的碎片定义做出明确纠偏：

| 碎片类型 | 准确定义 | 主要出现场景 |
| --- | --- | --- |
| **外部碎片（External Fragmentation）** | 已分配块**之间**残留的零散空闲间隙，总量足够却不连续，无法满足新请求 | **变长分配**（如内存分段、物理连续页分配） |
| **内部碎片（Internal Fragmentation）** | 已分配的固定大小单元**内部**未用满的浪费空间（例如只申请 100 B 却分了整页 4 KB） | **定长分配**（如内存分页、Slab/SLUB 固定槽位） |

（原书 3.1 节曾将分段中“加载了不常用内存”误称为内部碎片，实际上分段主要面对的是外部碎片，而引入分页正是用极小的内部碎片换取彻底消除外部碎片。）

### 3.1.3 内存分页 {#ch3-1-3}

**内存分页（Paging）**将虚拟地址空间和物理内存统一划分为固定大小的块——**页（Page）**（Linux x86-64 默认为 **4 KB**，ARM64 常见为 4 KB 或 16 KB/64 KB）。虚拟地址直接切分为**虚拟页号（VPN）**和**页内偏移（Offset）**：

1. 按 VPN 查询页表，得到对应的**物理页框号**（PFN）与权限/有效位；
2. 将 PFN 与原始 `Offset` 直接拼接，即得物理地址。

因为普通用户态页分配以固定 4 KB 页框为单位，任意离散的空闲页框都能经页表拼装为连续虚拟空间，从而**消除了单页粒度分配与用户虚拟映射的外部碎片**（注：内核需要分配连续物理页框的场景如 2 MB 大页、部分硬件 DMA 缓冲与多页内核栈仍面临页框级物理外部碎片，需由下文的伙伴系统与内存紧缩治理）；同时，内存换入/换出（Swap）与按需加载（Demand Paging）均只需按页粒度推进。

## 3.2 多级页表、TLB 与大页 {#ch3-2}

### 3.2.1 为什么必须采用多级页表 {#ch3-2-1}

单级线性的平铺页表存在致命的空间缺陷：在 32 位 4 KB 页环境下，每个进程需容纳 2<sup>20</sup>（约 100 万）个 4 字节页表项，单进程页表固定占用 **4 MB** 连续内存；在 64 位（48 位虚拟地址）环境下，单级页表需要 2<sup>36</sup> 项、高达数百 GB，完全不可行。

利用程序访问的局部性，**多级页表**（Multi-Level Page Table）把页表本身组织成稀疏前缀树：只有某个大范围虚拟地址真正被进程映射时，内核才按需分配对应的下级子页表，未映射区域在顶级目录中置空即可。

现代 64 位 Linux（x86-64）同时支持 **4 级页表**（48 位规范虚拟地址，总计 256 TiB）和 **5 级页表**（Linux 4.14+ 引入，57 位规范虚拟地址，总计 128 PiB，新增 `P4D` 层级）：

```text
x86-64 5 级页表（57 位规范虚拟地址，4 KB 页 = 12 位页内偏移）：
+-------+-------+-------+-------+-------+--------------+
|  PGD  |  P4D  |  PUD  |  PMD  |  PTE  |    Offset    |
| 9 bit | 9 bit | 9 bit | 9 bit | 9 bit |    12 bit    |
+-------+-------+-------+-------+-------+--------------+
  CR3 ---> PGD ---> P4D ---> PUD ---> PMD ---> PTE ---> 物理页框 + Offset
（在传统 4 级页表 48 位模式下，Linux 内核将 P4D 逻辑折叠，仅使用 PGD/PUD/PMD/PTE 四层）
```

### 3.2.2 TLB 快表与大页（HugePages / THP） {#ch3-2-2}

多级页表节省了空间，却把一次内存访存变成了“4–5 次页表查询 + 1 次数据访问”的时间开销。为此，CPU 的 MMU 内部集成了高速全相联/组相联硬件缓存——**TLB（Translation Lookaside Buffer，转址旁路缓存/快表）**，专门缓存最近使用过的 `VPN → PFN` 映射。

- **TLB 命中**：几乎零额外延迟完成地址翻译（通常与 L1 Cache 寻址重叠）。
- **TLB 未命中（TLB Miss）**：硬件页表遍历器（Page Table Walker）逐级访存查页表并回填 TLB，可能带来几十到上百个时钟周期的延迟。
- **进程切换与 PCID/ASID**：切换进程需要更换页表基址寄存器（x86-64 `CR3`）。现代 CPU 为每条 TLB 表项附带进程上下文标识（x86-64 称 **PCID**，ARM64 称 **ASID**），使不同进程的映射可在 TLB 中共存，避免每次切换都全量冲刷 TLB。

当数据库（如 MySQL/PostgreSQL）、JVM 或大内存缓存服务使用上百 GB 内存时，4 KB 页会产生数千万个页表项，远远超出只有数百至数千条目的 TLB 覆盖范围（TLB Reach），导致高频 TLB Miss。解决方案是使用**大页（HugePages）**：x86-64 硬件原生支持 **2 MB**（在 PMD 级直接指向物理页，省去 PTE 层）与 **1 GB**（在 PUD 级直接映射）大页，使单条 TLB 项覆盖范围放大 512 倍至 262,144 倍。Linux 提供两种形态：

- **静态大页（HugeTLB）**：管理员预先预留，内存锁定不参与 Swap，确定性强，常用于数据库与 DPDK；
- **透明大页（THP，Transparent Huge Pages）**：内核对匿名内存自动尝试分配或后台合并 2 MB 大页，对应用透明；但在高频 `fork()` 写时复制或内存碎片较重、延迟极度敏感的服务（如 Redis）中，大页映射拆分、`khugepaged` 扫描合并与同步内存紧缩易诱发延迟毛刺，常按场景设为 `madvise` 或关闭。

## 3.3 Linux 虚拟地址空间布局与物理内存分配 {#ch3-3}

### 3.3.1 平坦分段与虚拟地址空间分布 {#ch3-3-1}

受早期 Intel x86 硬件要求（必须先段映射再页映射）影响，Linux 在 x86 上采用**平坦内存模型**：所有主要代码/数据段的基址设为 `0`、界限覆盖整个空间，使逻辑地址直接等于线性（虚拟）地址，段机制仅用于特权级区分及 x86-64 下用 `FS`/`GS` 段基址实现高效的线程局部存储（TLS）与每核内核变量。

在 64 位 x86-64 Linux（48 位规范地址，4 级页表，总计 256 TiB）中，规范虚拟地址空间按最高有效位符号扩展对称切分为低、高两个各 **128 TiB** 的半区，中间为硬件禁止访问的非规范地址空洞（Canonical Hole）；启用 5 级页表（57 位规范地址，总计 128 PiB）后，则扩展为低、高半区各 **64 PiB**。每个进程拥有独立的低半区用户空间，高半区内核空间则共享同一套内核物理映射：

```text
0xFFFF_FFFF_FFFF_FFFF ──> +----------------------------------------------+
                          |  内核空间（48 位下占高 128 TiB，全局共享映射） |
0xFFFF_8000_0000_0000 ──> +----------------------------------------------+
                          |        非规范地址空洞（Canonical Hole）        |
0x0000_7FFF_FFFF_FFFF ──> +----------------------------------------------+ (48 位用户空间顶)
                          |  栈（Stack，默认 8 MB，向下增长）              |  局部变量、函数调用帧
                          |                      |                       |
                          |                      v                       |
                          |            （ASLR 随机化空洞）                |
                          |  内存映射区（mmap，现代 x86-64 默认向下增长）   |  共享库(.so)、mmap 文件、大块匿名分配
                          |                      ^                       |
                          |                      |                       |
                          |  堆（Heap，brk 向上增长）                     |  malloc 小块动态分配内存
                          +----------------------------------------------+
                          |  未初始化数据段（.bss）                       |  未初始化/零初始化全局与静态变量
                          +----------------------------------------------+
                          |  已初始化数据段（.data）                      |  已初始化全局与静态变量
                          +----------------------------------------------+
                          |  代码段（.text）与只读常量（.rodata）          |  只读可执行二进制指令
0x0000_0000_0000_0000 ──> +----------------------------------------------+
```

> **现代细节校准**：现代 Linux 默认启用 **ASLR（Address Space Layout Randomization，地址空间布局随机化）**，每次启动进程都会随机偏移栈、堆、mmap 映射区与位置无关可执行文件（PIE）的基址，防止攻击者硬编码返回地址实施内存攻击；且 x86-64 下默认 `mmap` 映射区位于栈下方并**自顶向下**增长（而非原书统一描述的向上增长），以给堆和映射区留出更大的共享弹性空间。

### 3.3.2 物理内存管理：伙伴系统、SLUB 与 `malloc` 底层 {#ch3-3-2}

操作系统内部和用户态程序对内存的粒度需求不同，Linux 采用分层分配体系：

1. **物理页框管理 — 伙伴系统（Buddy System）**：以 4 KB 页为最小单位，维护 2<sup>0</sup>、2<sup>1</sup> … 2<sup>10</sup> 连续物理页的空闲链表。申请时若无恰好大小则拆分更大块；释放时若地址相邻、大小相等的“伙伴”块同样空闲则立即合并，有效控制物理内存外部碎片。
2. **内核小对象分配 — SLUB 分配器**：内核频繁创建几十至几百字节的结构体（如 `task_struct`、`inode`、`sk_buff`），直接按 4 KB 页分配过于浪费。Linux 向伙伴系统批发整页，再由 **SLUB** 分配器切分为等长槽位并缓存复用（注：Linux 6.8 起已彻底移除历史悠久的旧 SLAB 分配器，内核统一采用 SLUB）。
3. **用户态动态分配 — `malloc` 的两条路径**：在 Linux glibc（`ptmalloc2`）中，`malloc()` 并非每次都直接向内核要内存，而是先在用户态内存池（Arena）查找空闲块；池中不足时再分两条系统调用路径向内核申请**虚拟内存**：
   - **小块内存（默认 `< 128 KB`，阈值可动态调整）**：通过 `brk()` 推高堆顶指针。释放时通常先归还给 glibc 内存池复用，不立即还给操作系统，减少系统调用但可能产生用户态堆碎片；
   - **大块内存（默认 `>= 128 KB`）**：通过 `mmap()` 在文件映射区创建私有匿名映射。`free()` 时直接调用 `munmap()` 立即归还操作系统。
   - **关键行为**：无论是 `brk()` 还是 `mmap()`，都只分配了虚拟地址区间（内核中登记为 `vm_area_struct`），**并未立刻分配物理内存**；直到程序首次读写该页触发缺页异常时，内核才真正分配物理页框并建立页表项。

## 3.4 缺页异常、写时复制与页面回收 {#ch3-4}

### 3.4.1 缺页异常、写时复制（COW）与大内存 `fork` 边界 {#ch3-4-1}

当 CPU 访问的虚拟地址对应页表项无效（`Present = 0`）或违反写保护权限时，MMU 同步触发**缺页异常（Page Fault）**。它与外部硬件中断的关键区别在于：缺页异常在指令执行**期间**触发，内核处理完毕更新页表后，CPU 会**重新执行触发异常的那条指令**（而非跳过到下一条）。

按是否涉及磁盘 I/O 与合法性，缺页异常分为三类：

| 类型 | 触发场景 | 是否触发磁盘 I/O | 性能影响 |
| --- | --- | --- | --- |
| **次缺页（Minor Page Fault）** | `malloc` 后首次访问分配匿名零页；页已在 PageCache 中只需建映射；触发写时复制（COW） | **否** | 微秒级，开销较低 |
| **主缺页（Major Page Fault）** | 访问的数据在磁盘文件（未缓存）或已被换出至 Swap 分区 | **是** | 毫秒/百微秒级，进程阻塞，极易引起抖动 |
| **非法缺页（Invalid Fault）** | 访问未映射虚拟地址（如空指针解引用）或写只读代码段 | 否 | 内核发送 **`SIGSEGV`** 终止进程 |

**写时复制（Copy-on-Write, COW）**是缺页异常的经典工程应用：调用 `fork()` 创建子进程时，内核并不复制父进程庞大的物理内存，而是仅复制页表并将父子双方的可写数据页标记为**只读**；一旦任意一方执行写操作，硬件触发写保护次缺页异常，内核才为写入方单独分配一个新 4 KB 物理页、拷贝内容并恢复可写（Redis `bgsave` 持久化与内存放大调优详见[《Redis 核心技术与实战》第 3 章 BGSAVE 与写时复制](../redis/chapter-03#ch3-2-1)）。

**生产深水区：大内存进程执行 `fork()` 的停顿与 `ENOMEM` 真实机制**：

1. **页表同步拷贝停顿（带映射粒度前提）**：`fork()`（内核 `dup_mmap`）虽免去了数据页拷贝，但仍须加锁遍历 VMA、同步分配并复制底层页表项及刷 TLB。以一个 **40 GiB 内存全部采用 4 KiB 基础页映射（未启用大页）** 的进程估算，仅底层 PTE 页表就约占 `40 GiB / 4 KiB × 8 B = 80 MiB`，复制千万级页表项常使父进程主线程停顿数十毫秒。
2. **`fork()` 遭遇 `ENOMEM` 或内存失败的三条内核路径（Linux 6.12 `mm/util.c`）**：
   - **严格超额限制（`vm.overcommit_memory = 2`）**：全机已承诺虚拟空间 `Committed_AS` 加上本次克隆的全部可写私有映射（`VM_ACCOUNT`）超出 `CommitLimit`（`Swap + 物理 RAM × overcommit_ratio`），内核直接拒绝 `fork()` 返回 `ENOMEM`；
   - **启发式模式（默认 `overcommit_memory = 0`，`OVERCOMMIT_GUESS`）下的超大单段 VMA**：Linux 6.12 的 `__vm_enough_memory()` 会将**单次计费请求的页数**与 `totalram_pages() + total_swap_pages` 比较。`fork()` 逐个遍历父进程带 `VM_ACCOUNT` 的可写私有 VMA 计费——因此若父进程 40 GiB 分散在多个小 VMA 中并不会触发该拒绝，但若父进程预先一次性 `mmap` 了**单个超过整机总 RAM + Swap 的超大连续私有可写虚拟区**（例如在 64 GiB 无 Swap 机器上预留了 80 GiB 虚拟竞技场/堆空间，哪怕实际只触页用了 40 GiB RSS），克隆该 VMA 时就会直接被拒并返回 `ENOMEM`；
   - **内核页表分配失败或容器 memcg 硬限**：为子进程新分配数十 MiB 内核页表本身消耗物理页并计入当前容器 `memory.current`，当物理空闲页紧缺或触及容器 `memory.max` 时同样会导致失败或 OOM。
   - **工程根治**：大内存服务（如大模型/Agent 宿主进程）仅为了拉起外部小工具而创建子进程时，现代运行时（Go `os/exec`、JDK `posix_spawn`）统一改用 **`vfork()` 或 `clone(CLONE_VM | CLONE_VFORK)`** 短暂借用父进程页表直接执行 `execve()`，一举消除页表拷贝毛刺与虚拟计费/页表分配导致的 `ENOMEM`。

### 3.4.2 页面回收演进：从经典算法到 Linux MGLRU 与 OOM {#ch3-4-2}

物理内存耗尽时，内核需要驱逐低价值页面。早期理论算法沿着“逼近未来访问局部性并降低维护开销”演进：**OPT**（淘汰未来最久不用，仅理论上限）→ **FIFO**（先进先出，存在扩容反增缺页的 **Belady 异常**）→ **LRU**（最近最久未使用，严格全局链表锁开销过大）→ **Clock（时钟/二次机会算法，修正原书笔误“Lock”）**（环形指针扫描硬件**访问位 Accessed Bit**，为 `1` 清零给二次机会、为 `0` 淘汰）→ **LFU**（按频次淘汰，需配合衰减防历史热点霸占）。

**现代 Linux 的真实页面回收体系**：

Linux 将可回收物理页分为**文件页（File-backed Page / PageCache，干净页直接丢弃、脏页回写后释放）**与**匿名页（Anonymous Page，堆/栈，仅在启用 Swap 或内存压缩设备 `zram` 时才能换出，`vm.swappiness` 调节二者回收倾向）**。内核按水位线（`min` / `low` / `high`）驱动回收：余量跌破 `low` 时唤醒 `kswapd` 后台异步回收；跌破 `min` 时触发**直接内存回收（Direct Reclaim）**，同步阻塞当前申请内存的业务线程。

在冷热页追踪算法上，Linux 完成了关键代际升级：

1. **传统双 LRU（Active / Inactive 链表）**：文件页与匿名页各维护活跃与非活跃两条链表，靠逆向映射（rmap）检查访问位升降级。在大内存与高密度容器混布下，两级粒度过粗，易误杀近期热页且 `kswapd` CPU 扫描开销高。
2. **MGLRU（Multi-Generational LRU，Linux 6.1+ 主流实现）与 Folio**：将页面细分为多个**代（Generation）**，直接顺着进程页表批量扫描访问位，将活跃页晋升至最新代、从最老代精准驱逐冷页；配合 **Linux 5.16+ 引入、6.x 全面普及的 Folio**（以连续复合页整体替代零散单页 `struct page` 参与 LRU 管理），显著降低了高内存压力下的 `kswapd` CPU 消耗、锁争用与主缺页抖动。

当直接回收与 Swap 仍无法腾出足够页框时，内核在**当前触发 OOM 的作用域（整机全局或具体内存 cgroup）**内启动 **OOM Killer**：按 `oom_badness()` 综合计算进程占用的**物理驻留页（RSS）+ Swap 换出页 + 页表占用内存**，再叠加管理员配置的 `/proc/<pid>/oom_score_adj`（`-1000` 豁免查杀至 `1000` 满额加权），向得分最高的候选进程发送 `SIGKILL` 保住系统存活。

### 练习 1：计算 4 级页表与单级页表的空间差距

在 64 位系统（采用 48 位虚拟地址、4 KB 页大小、每个页表项占 8 字节）中，假设某进程实际只使用了 16 MB 连续虚拟内存（从 `0x0` 开始）：

1. 每级页表恰好占满一个 4 KB 物理页，包含多少个页表项？对应地址中的多少 bit 索引？
2. 采用 **4 级页表**映射这 16 MB 连续空间，最少需要分配多少个 4 KB 页表页？总页表占用多少 KB？

<details>
<summary>查看参考答案</summary>

1. **每级页表项数与索引位宽**：
   - 一个 4 KB 页可存放 4096 / 8 = 512 = 2<sup>9</sup> 个页表项，因此每级索引占 **9 bit**。
   - 验证总位宽：9 (PGD) + 9 (PUD) + 9 (PMD) + 9 (PTE) + 12 (Offset) = 48 bit。
2. **映射 16 MB 连续空间所需的最少页表页数**：
   - 16 MB 共包含 16 MB / 4 KB = 4096 个数据页。
   - 每张底层 **PTE 页**可索引 512 个 4 KB 页（即覆盖 2 MB 虚拟空间），因此 16 MB 需要 4096 / 512 = 8 张 **PTE 页**。
   - 这 8 张 PTE 页可全部挂在 **1 张 PMD 页**下（1 张 PMD 可索引 512 张 PTE = 1 GB）。
   - 该 PMD 挂在 **1 张 PUD 页**下，PUD 挂在 **1 张 PGD 页**下。
   - 总计：1 (PGD) + 1 (PUD) + 1 (PMD) + 8 (PTE) = 11 张页表页，仅占用 **11 × 4 KB = 44 KB**（而若用单级页表覆盖 48 位空间需 2<sup>36</sup> × 8 B = 512 GB）。

</details>

### 练习 2：理解 `malloc`、RSS、次缺页与写时复制

分析以下 C 语言程序在 Linux x86-64（4 KB 页）下的物理内存占用（RSS）变化（假设 `malloc` 成功且系统物理内存充足）：

```c
char *buf = malloc(100 * 1024 * 1024); // 步骤 A：申请 100 MB
// 步骤 B：只读取 buf[0], buf[4096], ..., 遍历读完 100 MB
// 步骤 C：向这 100 MB 的每一页写入 'x'
pid_t pid = fork();                    // 步骤 D：创建子进程
if (pid == 0) {
    buf[0] = 'y';                      // 步骤 E：子进程仅修改第 1 字节
}
```

请逐一说明步骤 A、B、C、D、E 分别导致了哪些内核内存行为（虚拟内存变化、物理页分配与缺页类型）。

<details>
<summary>查看参考答案</summary>

- **步骤 A（`malloc` 100 MB）**：因大于 128 KB 阈值，glibc 调用 `mmap()` 分配 100 MB 匿名虚拟内存区间。此时仅增加进程的 **VIRT/VSZ**，**RSS（实际物理内存占用）几乎为 0**，未分配物理页框。
- **步骤 B（只读遍历）**：Linux 对未写入的匿名映射通常映射到共享的全局**只读零页（Zero Page）**，仅触发次缺页建只读映射，依然几乎不消耗新物理内存。
- **步骤 C（逐页写入 `'x'`）**：每一 4 KB 页首次写入都触发一次**次缺页异常（Minor Page Fault）**（共约 25,600 次），内核按需从伙伴系统分配物理页并建立可写映射，RSS 增长约 100 MB。
- **步骤 D（`fork()`）**：触发**写时复制（COW）**机制——内核仅复制页表并将父子双方的这 100 MB 页表项改为**只读**，**不会立刻多占用 100 MB 物理内存**。
- **步骤 E（子进程写入 `buf[0] = 'y'`）**：仅第 0 页触发一次写保护**次缺页异常**，内核为子进程新分配 **1 个 4 KB 物理页**并拷贝原页内容、恢复可写；其余 99.996 MB 物理页仍与父进程只读共享。

</details>

### 练习 3：为什么 Redis 生产环境往往建议关闭透明大页（THP）？

结合[3.2.2 节](#ch3-2-2)的透明大页与[3.4.1 节](#ch3-4-1)的写时复制（COW），解释为什么内存数据库 Redis 在执行 `bgsave`（依赖 `fork()`）及高并发写入时，开启 `always` 模式的 2 MB 透明大页（THP）容易诱发响应延迟尖刺（对比历史旧内核与 Linux 6.12 当前行为）。

<details>
<summary>查看参考答案</summary>

1. **写保护缺页的映射拆分与历史整页复制对比**：
   - **早期旧内核（2.6.38～4.x 部分版本）**：`fork()` 后父进程修改共享 2 MB 大页中的 100 字节，曾直接分配并复制整张 **2 MB** 物理大页，造成瞬时内存暴涨与单次毫秒级拷贝卡顿。
   - **现代 Linux 6.12 行为（`do_huge_pmd_wp_page`）**：若当前进程已独占该大页 Folio 则直接原地恢复可写；若父子进程仍在共享，内核**不再复制整张 2 MB 大页**，而是调用 `__split_huge_pmd()` **先将 2 MB 的 PMD 页表映射拆分为 512 个 4 KB PTE 映射**（注意此时仅拆分页表映射，尚未立即拆碎底层物理复合页 Folio），再回退至 PTE 级 `do_wp_page()` 仅拷贝被修改的那 **1 个 4 KB 子页**。但即便如此，`bgsave` 期间海量随机写引发的密集 PMD 映射拆分、页表锁争用与跨核 TLB 刷新，依然会抬高主线程尾延迟。
2. **`khugepaged` 重组与同步内存紧缩（Compaction）抖动**：`bgsave` 结束后，后台线程 `khugepaged` 扫描被拆散的 4 KB 映射，重新申请连续 2 MB 物理块并加锁拷贝合并页；而在物理内存碎片化严重时，开启 `always` 模式的 THP 在缺页分配路径上还可能触发同步**内存紧缩（Memory Compaction）**迁移页面，直接阻塞对延迟极度敏感的 Redis 单命令执行主线程。

</details>

### 练习 4：分析线上进程触发 OOM 的排查与防护思路

某台未开启 Swap 的 16 GB 物理内存 Linux 服务器（同一根 cgroup 下）运行着一个核心数据库进程（RSS 10 GB）和若干批处理脚本。某天一个内存泄漏的批处理脚本迅速吃光剩余内存触发整机 OOM，结果核心数据库反而被内核杀掉了。

1. 为什么先被 OOM Killer 杀死的可能是核心数据库而不是刚启动的泄漏脚本？
2. 如何通过 Linux 内核机制防止核心数据库被误杀，并限制批处理脚本的内存上限？

<details>
<summary>查看参考答案</summary>

1. **原因**：Linux OOM Killer 在当前触发 OOM 的作用域内调用 `oom_badness()` 按进程当前的**内存总账（`RSS + Swap 换出页 + 页表占用页`）**结合 `oom_score_adj` 计算得分，而**不看内存增长速率**。在本机无 Swap 且同处根作用域下，数据库驻留了 10 GB（加页表总账远高于刚涨到 5 GB 的泄漏脚本），因此得分最高沦为牺牲品。
2. **防护方案**：
   - **调整 OOM 权重**：调低核心数据库的 `/proc/<db_pid>/oom_score_adj`（例如设为 `-500` 或关键单机下设为 `-1000` 豁免查杀）；
   - **缩小故障爆炸半径 — cgroups v2 内存硬限**：将批处理脚本放入独立的子 cgroup（或独立容器），配置 `memory.max`（及 `memory.high` 软节流）。一旦脚本泄漏触及该子组的 `memory.max`，OOM 作用域被严格限制在该子 cgroup 内部，只会杀死脚本自身，绝不波及外部的数据库进程。

</details>

### 面试题 1：为什么说“内存分页消除了外部碎片，但引入了内部碎片”？追问：既然分页已经消除了外部碎片，为什么 Linux 内核物理内存管理层仍然需要“伙伴系统（Buddy System）”来对抗外部碎片？

<details>
<summary>查看参考答案</summary>

**结论**：分页消除的是**单页（4 KB）粒度分配与用户态虚拟空间视角**的外部碎片（离散的 4 KB 物理页框可经页表映射为连续虚拟空间，仅在段尾留有不足 4 KB 的页内内部碎片）；但在**操作系统内核与硬件 DMA 视角**下，许多关键操作依然强制要求**物理地址连续**的多页内存，因此必须靠伙伴系统治理物理页框级的外部碎片。

**关键依据**：
- **必须物理连续的三大场景**：① 部分外设 DMA 控制器要求连续物理内存缓冲区；② 内核线性映射区的大对象与多页内核栈（如 16 KB）；③ **2 MB / 1 GB 大页（HugePages / THP）** 要求底层必须是连续的 512 个或 262,144 个物理页框！
- 若没有伙伴系统按 2<sup>k</sup> 阶合并相邻空闲页框以及内核迁移紧缩（Memory Compaction），运行日久后物理内存虽有大量零散 4 KB 空闲页，但分配 2 MB 大页或高阶内核缓冲仍会因物理外部碎片失败。

</details>

### 面试题 2：进程切换和同进程内的线程切换，对 TLB 分别有什么影响？追问：现代 CPU 有了 PCID/ASID 免清空 TLB 后，多线程高并发程序还会遇到什么棘手的“TLB Shootdown”性能瓶颈？

<details>
<summary>查看参考答案</summary>

**结论**：同进程线程切换共享页表，`CR3` 不变、TLB 继续有效；跨进程切换更换页表，借助 PCID/ASID 可避免立即全量清空 TLB，但容量竞争仍会推高 Miss。而在同进程多核高并发下，**频繁缩减或降权虚拟内存映射（如高频 `munmap`/`free` 大块内存、`mprotect`）会触发昂贵的跨核 TLB Shootdown（核间中断 IPI 同步冲刷）**。

**关键依据**：
- 每个 CPU 核心都有自己私有的硬件 TLB，但主流 x86-64 硬件**并不对 TLB 自动维护类似 MESI 的跨核缓存一致性**！
- 当线程 1 在核 0 调用 `munmap()` 释放一块大内存（例如 glibc `free` ≥ 128 KB 的匿名映射）移除页表项时，同进程运行在核 1～核 63 上的其他线程私有 TLB 里可能还缓存着该旧地址映射。内核必须向所有正在运行该进程的 CPU 核心发送 **IPI（处理器间中断）**，强行打断它们的业务执行、刷新对应 TLB 条目并等待全部核心确认返回——在数十核高频分配释放大对象场景下，系统态 CPU 会被 `smp_call_function` 刷爆。工程上常通过内存池复用或替换为 `jemalloc`/`tcmalloc`（延迟批量归还物理页）化解。

</details>

### 面试题 3：Linux 服务器上 `free -h` 显示 `free` 所剩无几，但 `available` 仍有 15 GB，系统是不是快 OOM 了？追问：哪些真实场景下明明 `available` 很充裕，业务却依然发生内存卡顿或报 OOM？线上能手动执行 `echo 3 > /proc/sys/vm/drop_caches` 释放内存吗？

<details>
<summary>查看参考答案</summary>

**结论**：常规情况下**不是快 OOM**，这是内核将空闲内存用作可随时回收的 PageCache 的正常现象；但在**容器局部限额、高阶连续页碎片化或 VMA 映射数超限**三类边界下，`available` 充足照样会卡顿或报错；**生产高峰期严禁盲目执行 `drop_caches`**。

**关键依据**：
- **`available` 充足仍出故障的三大反例**：
  1. **容器 cgroup 局部触顶**：宿主机全局 `available` 还有 15 GB，但某个容器自身已触及 `memory.max`，触发容器内 Direct Reclaim 停顿乃至 cgroup OOMKill；
  2. **物理内存严重碎片化**：内核或 THP 申请高阶连续物理页（如 `order >= 3`）时，虽然单页总量够，但无连续空闲块（可查 `/proc/buddyinfo`），触发同步内存紧缩（Compaction）导致长尾卡顿；
  3. **虚拟映射区数量耗尽**：高频调用 `mmap`（如分词/向量索引映射大量片段）超过 `vm.max_map_count`（默认 65530），即使内存空余也会直接返回 `ENOMEM`。
- **为何严禁线上乱敲 `drop_caches`**：① 它会一刀切清空所有干净的热点 PageCache 与 `dentry`/`inode` 缓存，瞬间失去缓存保护导致底层磁盘/数据库读 IOPS 被击穿雪崩；② 内核遍历超级块与页缓存树清理期间需持有内核锁，在大内存机器上执行命令本身就会引发系统抖动。

</details>

### 面试题 4：Linux 6.1 引入的 MGLRU（多代 LRU）相比传统的 Active/Inactive 双链表 LRU 解决了什么痛点？追问：与之配合的 Folio 机制又优化了什么？

<details>
<summary>查看参考答案</summary>

**结论**：MGLRU 解决了传统双链表**冷热分级过粗易误杀热页**与**逆向映射（rmap）扫描 CPU 开销过高**两大痛点；**Folio** 则通过以“2<sup>n</sup> 连续复合页”为整体管理单元，大幅削减了页表与 LRU 链表的元数据操作与锁争用。

**关键依据**：
- 传统双 LRU 只有活跃与非活跃两档，且回收检查访问位时需走复杂的对象逆向映射，面对海量容器混布极易把刚冷却片刻的工作集换出触发主缺页颠簸；MGLRU 拆分为多个年龄代，直接顺着进程页表空间局部性批量扫描页表项访问位，既省 CPU 又大幅降低误驱逐率。
- 在没有 Folio 前，内核许多路径每处理 64 KB 数据仍要对 16 个 `struct page` 逐一加引用计数、挂拆 LRU 链表；引入 Folio 后，内核直接基于可变阶连续页块一次性完成页缓存查找、预读回写与 LRU 流转，显著提升高吞吐 I/O 与内存回收效率。

</details>

### 面试题 5：在一台 64 GiB 物理内存、未开启 Swap 的服务器上，一个大内存服务（如 AI Agent 宿主进程或数据库引擎）调用 `fork() + exec()` 拉起一个仅需 5 MiB 内存的外部命令行工具时，在哪些具体内核条件下会直接报 `Cannot allocate memory`（`ENOMEM`）并伴随数十毫秒主线程毛刺？如何根治？

<details>
<summary>查看参考答案</summary>

**结论**：数十毫秒毛刺源于 `fork()` 期间加锁复制父进程海量基础页表项（例如 40 GiB 全 4 KiB 映射对应约 **80 MiB** PTE 页表）与刷 TLB；而直接返回 `ENOMEM` 则发生在**严格 Overcommit 账本超限、单段超大私有 VMA 越过总内存，或页表物理内存/容器 memcg 耗尽**三类条件下。根治方案是改用 **`vfork()` / `posix_spawn()`（底层 `clone(CLONE_VM | CLONE_VFORK)`）**。

**关键依据（Linux 6.12 源码口径）**：
1. **`vm.overcommit_memory = 2`**：整机已承诺虚拟空间 `Committed_AS` 加上克隆父进程全部可写私有映射的账面规模超过 `CommitLimit`，直接拒绝 `fork()`；
2. **`vm.overcommit_memory = 0`（默认 `OVERCOMMIT_GUESS`）**：内核按每个带 `VM_ACCOUNT` 的可写私有 VMA 逐段与 `totalram_pages() + total_swap_pages`（此处为 64 GiB）对比——若服务启动时预先 `mmap` 了**单个超过 64 GiB 的连续私有可写虚拟地址池**（即便实际只用了 40 GiB RSS），克隆该 VMA 时立即触发 `ENOMEM`；
3. **页表分配或容器限额触顶**：若服务运行在 `memory.max = 42 GiB` 的容器内且已用 41.95 GiB，为子进程新分配几十 MiB 内核页表就会直接撞上限额失败。
4. **根治机制**：改用 `posix_spawn` 或现代语言标准库（如 Go `os/exec` 在 Linux 下默认采用 `CLONE_VM | CLONE_VFORK`），子进程在调用 `execve` 替换镜像前短暂借用父进程页表、零页表复制且不触发私有 VMA 虚拟内存翻倍计费，耗时降至微秒级。

</details>
