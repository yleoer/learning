# 第 5 章 主从复制、哨兵高可用与脑裂防护

## 本章要点

单机持久化解决了进程重启后的数据恢复，但硬件宕机期间服务依然中断。Redis 通过“一主多从读写分离 + Sentinel 哨兵自动故障转移”构建高可用底座。工程实践中，“为什么网络闪断一下竟触发全集群重传 RDB 风暴”“5 个哨兵挂掉 3 个为什么判了主库下线却切不动主库”“主从切换后为什么原主库上刚写入成功的几千条订单凭空消失”都是高频深水区考题。本章依次拆解 `PSYNC` 复制状态机与共享复制缓冲区、哨兵集群仲裁选举与三轮选主打分规则，最后给出一套无死角的主从滞后监控与防脑裂参数闭环。

> 核对日期：2026 年 11 月 17 日；核对环境为 Redis 8.10.3、Linux/AMD64。

## 5.1 主从全量 / 增量同步与级联复制拓扑 {#ch5-1}

### 5.1.1 PSYNC 三阶段全量同步与主-从-从级联分担 {#ch5-1-1}

在从节点执行 **`REPLICAOF <master_ip> <master_port>`**（Redis 5.0 起取代旧命令 `SLAVEOF`）后，主库承接全部写请求并异步传播给从库，首次建立主从关系执行三阶段**全量同步**：

```text
从库 (Replica)                                  主库 (Master)
   │──── 1. PSYNC ? -1 (未知 runID 与偏移) ────►│
   │◄─── +FULLRESYNC <runID> <offset> ─────────│
   │                                           │── 2. fork 执行 BGSAVE 生成 RDB（或无盘直传 Socket）
   │◄─── 接收 RDB，清空旧库并加载 RDB 入内存 ────│── 期间新写命令记入复制缓冲区
   │◄─── 3. 发送同步期间累积的增量写命令流 ──────│
   │──── 建立长连接持续接收日常异步写命令流 ◄────│
```

主从全量同步之所以选用 **RDB 而非 AOF**，是因为 RDB 是压缩后的紧凑二进制快照，网络传输字节量远小于全历史命令日志，且从库直接反序列化还原内存结构比单线程重放亿级命令快得多。在万兆内网配慢磁盘环境下，Redis 6.0+/7.0+ 还支持无盘复制 `repl-diskless-sync yes`，由主库子进程直接将 RDB 字节流写入从库 Socket 省去本地落盘开销。

若一主直接挂载十几个从库，主库反复 `fork` 与并发推送多份 RDB 会打满主库 CPU 与出口带宽。工程上可采用 **“主 - 从 - 从”级联复制**：选取 1～2 台高配从库执行 `REPLICAOF` 指向主库，其余读扩展从库再 `REPLICAOF` 指向该级联从库，将生成与传输 RDB 的负担从主库彻底卸载。

### 5.1.2 环形积压缓冲区容量核算与共享复制缓冲区演进 {#ch5-1-2}

长连接传播阶段若遭遇短暂网络闪断，重连后从库发送 `PSYNC <runID> <slave_repl_offset>` 请求**增量同步**：只要从库缺失的偏移量仍在主库环形积压缓冲区（`repl_backlog_buffer`）内未被新命令覆盖，主库即回复 `+CONTINUE` 并仅补发断连期间的增量命令；**一旦环形缓冲太小已被新写入覆盖，就会被迫退化为昂贵的重新全量同步**！

因此，积压缓冲区容量 `repl-backlog-size`（默认仅 `1mb`）必须按峰值写入速率与最大容忍断连时长留足 **2 倍以上安全冗余**：

```text
repl-backlog-size ≥ 2 × (主库每秒写入字节数 - 断连期间实际传输字节数) × 最大容忍断连秒数
```

例如主库峰值每秒写入 `2000` 条命令、平均每条 `2 KiB`（即 `4 MiB/s`），希望容忍长达 `30s` 的网络分区重连不触发全量同步，则至少应将 `repl-backlog-size` 调大至 `2 × 4 MiB/s × 30s = 240mb`（或整取 `256mb`）。

> [!IMPORTANT]
> **Redis 7.0+ 共享复制缓冲区重大架构升级**：在原书（Redis 5.0/6.0）中，主库除了全局唯一的环形 `repl_backlog_buffer` 外，还必须为**每一个从库连接单独分配一份 `replication buffer`**——如果有 5 个从库同时同步且主库写入猛烈，5 份独立内存拷贝极易瞬间把主库撑到 OOM！**自 Redis 7.0 起，内核彻底合并了这两块区域**：主库只维护唯一一条带引用计数的全局 **`replBufBlock` 字节块链表**，所有从库的输出游标与增量积压索引全部共享指向同一份物理内存块，多从库复制内存开销直降 35%～70%。

## 5.2 哨兵集群自动发现、仲裁与新主选举 {#ch5-2}

### 5.2.1 基于 Pub/Sub 的互发现机制与主客观下线仲裁 {#ch5-2-1}

哨兵（Sentinel）是运行在特殊模式下的独立 Redis 进程，承担**监控、自动选主、配置通知**三大职责。运维只需在每个哨兵配置文件中声明主库地址与法定票数 `quorum`：

```ini
sentinel monitor mymaster 172.16.10.1 6379 2
sentinel down-after-milliseconds mymaster 5000
```

多个哨兵之间无需互相硬编码对端 IP：所有哨兵连上主库后，一方面向主库发 `INFO` 自动获取全部从库列表并逐一建连监控；另一方面共同订阅并向主库的 **`__sentinel__:hello`** 频道广播各自的 IP 与端口，自动完成哨兵集群组网；客户端则通过订阅哨兵的 `+switch-master` 等事件频道实时感知主库切换。

为防止单个哨兵自身网络闪断引发误切换，哨兵集群将故障判定与选主拆分为递进的三个阶段：

| 阶段名称 | 适用实例范围 | 达成票数门槛 | 核心协作命令与发布频道 |
| --- | --- | --- | --- |
| **主观下线（SDOWN）** | 主库、从库、其他哨兵 | 单个哨兵自身 `PING` 超时（`down-after-milliseconds`） | 发布 `+sdown` 事件（从库仅走到此步即不提供切换） |
| **客观下线（ODOWN）** | **仅针对主库** | 赞成主库失联的哨兵数 **`≥ quorum`** | 发送 `SENTINEL is-master-down-by-addr`，达标发布 `+odown` |
| **Leader 哨兵选举** | 全体哨兵节点竞选 | **同时满足 `≥ quorum` 且 `≥ ⌊N/2⌋ + 1`（严格过半）** | 每轮任期每哨兵仅 1 票先到先得，胜出者执行切主并广播 `+switch-master` |

### 5.2.2 Sentinel Leader 选举双条件与新主三轮打分规则 {#ch5-2-2}

如上表所示，判定客观下线后，由**哪一个哨兵**真正出手执行主从切换，需要经过类 Raft 的 **Sentinel Leader 选举**——候选哨兵胜出必须**同时满足以下两个硬条件**：

1. 获得的赞成票数 **大于等于 `quorum`**；
2. 获得的赞成票数 **严格超过已知哨兵实例总数的半数（即 `≥ ⌊N/2⌋ + 1`）**！

> [!CAUTION]
> **高频容灾陷阱：分母 `N` 是集群曾经注册过的总哨兵数，而非当前存活哨兵数**！例如部署了 `N = 5` 个哨兵、配置 `quorum = 2`，若因机房故障挂掉了 3 个哨兵、仅剩 2 个哨兵存活：当主库宕机时，剩余 2 个哨兵满足 `2 >= quorum(2)` **能够成功判定主库客观下线（`+odown`）**，但选举 Leader 需要至少 `⌊5/2⌋ + 1 = 3` 票，2 个存活哨兵最多投出 2 票，**永远选不出 Leader，故障转移彻底卡死**！因此哨兵集群至少部署 3 个奇数节点并分散在不同物理机/可用区。

当选的 Leader 哨兵按 **“一轮淘汰筛选 + 三轮优先级打分”** 从所有从库中选出唯一新主库：

```text
全体从库 ──► [淘汰筛选] 剔除已下线、replica-priority == 0、以及主库失联前已与主库断连超 (10 × down-after-ms) 的从库
                 │  （注：订正原书“断连超过 10 次”误述，源码实际校验连续断连时长是否超 10 倍阈值！）
                 ▼
            [第 1 轮：配置优先级] 比较 replica-priority（默认 100，数值越小但非 0 越优先！）──► 胜出则当选
                 │ 平局
                 ▼
            [第 2 轮：复制偏移量] 比较 slave_repl_offset，数值越大（越接近旧主库最新进度）越优先 ──► 胜出则当选
                 │ 平局
                 ▼
            [第 3 轮：实例运行 ID] 按字典序选 runID 最小的从库打破平局 ──► 执行 REPLICAOF NO ONE 升主
```

## 5.3 主从复制常见深坑与脑裂数据丢失治理 {#ch5-3}

### 5.3.1 异步滞后监控、过期键 PEXPIREAT 转换与时钟同步 {#ch5-3-1}

围绕主从读写分离，生产上有三处极易踩坑的配置与机制细节需严格厘清：

1. **异步复制延迟与过期键读取真相（订正原书 `EXPIRE` 转发误述）**：
   - 从库自身不主动执行定期随机删除来物理抹除主库同步来的过期键，而是等待主库触发惰性/定期删除后同步 `DEL`/`UNLINK`。但在 **Redis 3.2+** 中，客户端读从库命中已过期键时，从库会校验当前时间并直接返回空值 `nil`。
   - 原书第 32 讲称“主库原样把 `EXPIRE key 60` 发给从库导致从库从接收时刻重新算 60 秒而延后过期”——**该描述与源码事实不符**！早在 Redis 2.6 起，主库在向复制流和 AOF 传播任何相对过期命令（`EXPIRE`/`PEXPIRE`）时，都会在内核统一改写为**绝对毫秒时间戳命令 `PEXPIREAT`**！真正会导致从库仍读出已过期数据的唯一元凶是**主从服务器系统时钟不同步（从库时钟慢于主库）**，因此所有主从节点必须通过 **NTP / Chrony** 保持毫秒级时钟同步。
2. **`replica-serve-stale-data` 的真实作用范围**：设为 `no` **仅在从库与主库断连、或正在加载初始全量 RDB 期间**拒绝客户端查询（返回 `-MASTERDOWN`）；在日常连接正常但存在毫秒级异步滞后时它不会拦截读请求，强敏业务需外部巡检 `master_repl_offset - slave_repl_offset` 超阈值自动摘流。
3. **哨兵与实例 `bind` 配置铁律（订正原书远端白名单误导）**：`redis.conf` / `sentinel.conf` 中的 `bind` 指定的是**当前机器本地网卡监听 IP**（如 `bind 172.16.10.11`），**绝不是允许来访的远端哨兵 IP 白名单**！把其他机器 IP 写进 `bind` 会导致进程启动直接报 `Cannot assign requested address` 退出。

### 5.3.2 主从脑裂复盘与 min-replicas 参数闭环设计 {#ch5-3-2}

**主从脑裂**（Split-Brain）是导致已确认写入数据成批丢失的头号杀手。典型事故时序如下：

1. `t1`：原主库因同机进程打满 CPU、自身发生 Swap 或处理超大键而**假死卡顿**（或遭遇网络分区），无法响应哨兵 `PING`；
2. `t2`：超过 `down-after-milliseconds`（如 `10s`），哨兵集群判其客观下线并选出从库 B 升为**新主库**；
3. `t3`：原主库卡顿恢复（或与部分同网段客户端网络仍通），尚未收到哨兵降级通知的旧客户端继续向**原主库**成功写入几千条新数据（此时集群同时存在两个可写主库！）；
4. `t4`：哨兵连上原主库下发 `REPLICAOF` 强制其降级为新主库的从库——**原主库执行第一次全量同步时先清空自身全部内存再加载新主库 RDB，`t3～t4` 期间写入原主库的所有新数据瞬间灰飞烟灭**！

防御脑裂的标准武器是在主库同时配置以下两个参数（Redis 5.0+ 标准命名，取代旧 `min-slaves-*`）：

```ini
# 主库必须至少连着 N 个正常从库，且这些从库心跳上报（REPLCONF ACK）延迟不超过 T 秒，否则主库直接拒写！
min-replicas-to-write 1
min-replicas-max-lag 8
```

> [!WARNING]
> **防脑裂参数设计的隐藏时间窗死角**：`min-replicas-max-lag`（秒）乘以 `1000` 后，**必须严格小于哨兵的 `down-after-milliseconds`**！假设哨兵 `down-after-milliseconds = 10000`（`10s`）、切换耗时 `5s`，而你把 `min-replicas-max-lag` 误设成了 `15`（`15s`）：一旦原主库恰好卡死 **`12s`** 后恢复，哨兵在第 `10s` 已经发起切主，但原主库在第 `12s` 苏醒时距从库失联仅 `12s < 15s`，尚未触发禁写保护，在第 `12s～15s` 的 3 秒窗口内依然会放行脏写入并随后被新主清空！

## 练习 {#ch5-exercises}

以下 2 道练习分别检验积压缓冲区定量计算与哨兵多数派故障推演，以及脑裂时间窗参数审计与修复。建议先独立计算，再展开核对参考答案。

### 练习 1：核算主从积压缓冲区容量并推演跨机房哨兵故障

某 1 主 2 从架构部署在 A、B 两个机房：主库与 1 个从库及 **3 个哨兵**部署在 A 机房，另 1 个灾备从库与 **2 个哨兵**部署在 B 机房（共 5 个哨兵，配置 `quorum = 2`）。主库高峰期平均写入流量为 `5000 OPS`，每条写命令平均序列化长度为 `1 KiB`。请回答：
1. 若跨机房专线偶发最长 `45 秒` 闪断，为确保 B 机房从库重连时 100% 走增量同步而不触发全量 RDB 同步，`repl-backlog-size` 至少应设为多大？
2. 若某天 **A 机房整体断电**（主库、1 个从库与 3 个哨兵同时失联），B 机房存活的 2 个哨兵能否自动将 B 机房从库提升为新主库？应如何调整部署拓扑避免该死局？

<details>
<summary>查看参考答案</summary>

1. **`repl-backlog-size` 容量核算**：
   - 主库每秒写入速率 = `5000 × 1 KiB ≈ 5 MiB/s`；`45s` 断连期间累计产生约 `5 × 45 = 225 MiB` 增量流。
   - 按 2 倍安全冗余原则，`repl-backlog-size` 应配置为 `2 × 225 MiB = 450mb`（工程上取整配置 **`512mb`**）。
2. **A 机房整体断电后的哨兵切换结果与拓扑改进**：
   - **无法自动切换**！虽然 B 机房存活的 2 个哨兵满足 `2 >= quorum(2)` 可将原主库标为客观下线，但哨兵总数 `N = 5`，选出执行切换的 Leader 哨兵必须拿到 **`≥ ⌊5/2⌋ + 1 = 3` 票**；B 机房仅有 2 个哨兵存活，永远凑不够 3 票，灾备自动切换彻底失效。
   - **拓扑改进**：必须采用**三机房**（或同城三可用区 AZ）部署哨兵，例如按 **`2 + 2 + 1`** 分布在三个故障域——任意单一机房整体断电后，其余两机房仍有 `3` 个或 `4` 个哨兵存活，始终满足 `≥ 3` 票多数派仲裁自动切主。

</details>

### 练习 2：审计并修复仍会发生丢数的“半吊子”防脑裂配置

某支付缓存集群（1 主 3 从 + 3 哨兵）曾发生脑裂丢数据，DBA 随后在主库 `redis.conf` 与哨兵 `sentinel.conf` 中补充了如下配置：

```ini
# redis.conf
min-replicas-to-write 2
min-replicas-max-lag 15

# sentinel.conf
sentinel down-after-milliseconds paymaster 10000
```

上线一周后，主库因宿主机内核卡顿冻结了 `11 秒` 后恢复，哨兵顺利完成了主从切换，但业务核账发现切换期间客户端写入原主库的 400 多笔流水**依然丢失了**！请精确还原这 400 笔数据丢失的时间线，并给出无漏洞的参数组合（同时评估可用性平衡）。

<details>
<summary>查看参考答案</summary>

1. **丢数时间线还原**：
   - `t = 0s`：原主库冻结，停止处理命令与心跳；
   - `t = 10s`：超过 `down-after-milliseconds (10s)`，哨兵判定原主库客观下线并启动选主切换（假设选主与重配耗时 `4s`，于 `t = 14s` 完成切主并下发降级指令）；
   - **`t = 11s`（致命漏洞窗口开启！）**：原主库宿主机恢复响应！此时距其最后一次收到从库 `REPLCONF ACK` 仅过去了 **`11s < min-replicas-max-lag (15s)`**，主库误认为仍有至少 2 个从库延迟未超标，**并未触发禁写拒绝**！
   - `t = 11s ～ 14s`：旧客户端向原主库写入 400 多笔流水全部返回 `OK`，紧接着 `t = 14s` 原主库收到哨兵 `REPLICAOF` 清空内存同步新主库，数据全部丢失。
2. **修复准则与推荐配置**：
   - 必须保证 **`min-replicas-max-lag × 1000 + 主库每秒检查误差(1000ms) < down-after-milliseconds`**！同时 3 个从库配 `min-replicas-to-write 2`（半数以上）合理：
     ```ini
     # redis.conf：从库失联超 6s 立即主动拒写（加上定时检查最多 7s 封死写入）
     min-replicas-to-write 2
     min-replicas-max-lag 6

     # sentinel.conf：12s 才触发客观下线切主，确保切主前旧主库必定已提前进入拒写保护态！
     sentinel down-after-milliseconds paymaster 12000
     ```

</details>

## 面试题 {#ch5-interview}

以下 3 道面试题聚焦复制底层设计演进、从库过期键一致性与选主规则。建议先独立作答，再展开核对参考答案。

### 面试题 1：为什么主从全量同步用 RDB 而不用 AOF？Redis 7.0 的共享复制缓冲区解决了什么痛点？

<details>
<summary>查看参考答案</summary>

1. **全量同步选 RDB 的原因**：① **体积小、传输快**：RDB 只保存当前时刻键值的紧凑二进制编码，而未重写的 AOF 包含大量历史冗余修改命令，文件体积大得多；② **加载还原极快**：从库直接解析二进制数据块重建内存字典，远快于单线程通过伪客户端逐条执行数千万条 AOF 命令。
2. **Redis 7.0 共享复制缓冲区的价值**：7.0 之前主库为每个从库单独开辟独立的输出缓冲区（`replication buffer`）外加全局 `repl_backlog_buffer`，一主多从并发全量同步时多份重复副本极易打爆主库内存导致 OOM；7.0 起所有从库与积压缓冲共享同一条引用计数 `replBufBlock` 链表，内存中只存一份增量流，彻底消除了多从库复制内存倍增隐患。

</details>

### 面试题 2：既然从库不会主动删除主库同步过来的过期 key，客户端读从库会读到已经过期的数据吗？

<details>
<summary>查看参考答案</summary>

- 在现代 **Redis 3.2 及以上版本中，只要主从时钟同步，客户端绝不会读到过期数据**：虽然从库不主动物理删除主库同步的过期键（需等主库惰性/定期删除后发来 `DEL` 保持主从绝对一致），但从库处理读命令时会先比对键的绝对过期时间戳（主库传播 `EXPIRE` 时已统一改写为毫秒级绝对时间戳 `PEXPIREAT`），一旦发现当前时间已超过到期时间，立即向客户端返回空值 `nil`。
- **唯一例外风险**：如果**从库操作系统时钟明显慢于主库时钟**，主库已到期的 `PEXPIREAT` 时间戳在从库看来尚未到期，就会短暂读出脏旧数据，因此主从机器必须开启 NTP 时钟同步。

</details>

### 面试题 3：主库宕机后，哨兵是如何从多个从库中选出新主库的？如果想指定某台高配从库优先升主或某台跨城灾备从库永不升主，怎么配？

<details>
<summary>查看参考答案</summary>

1. **“一筛三打分”流程**：
   - **先筛选**：淘汰已断连下线、`replica-priority == 0`、以及主库失联前就已与主库连续断连超过 `10 × down-after-milliseconds` 的滞后从库；
   - **第 1 轮比优先级**：选 `replica-priority` 非零且**数值最小**（优先级最高）的从库；
   - **第 2 轮比数据新旧**：若优先级相同，选 `slave_repl_offset` **最大**（复制进度最接近原主库）的从库；
   - **第 3 轮比实例 ID**：若偏移量仍相同，选 `runID` 字典序最小的从库。
2. **定向运维配置**：
   - 让高配机器优先升主：将其 `replica-priority` 调小（例如从默认 `100` 设为 **`10`**）；
   - 让跨城高延迟灾备或专门跑分析报表（`--bigkeys`）的从库**永不参选主库**：将其设为 **`replica-priority 0`**。

</details>
