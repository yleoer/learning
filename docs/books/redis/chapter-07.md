# 第 7 章 缓存读写模式、淘汰算法（LRU / LFU）与异常治理

## 本章要点

把 Redis 用作数据库前置加速层时，业务必须正面回答三大核心工程问题：第一，缓存与数据库双写并发交错时如何避免脏旧数据长期驻留缓存；第二，有限内存写满后如何精准识别并留住真正高频热点，防止一次全表批量扫描把热数据全部挤出内存（缓存污染）；第三，面对雪崩、击穿与恶意穿透冲击时如何构筑无损与兜底双层防线。本章依次拆解旁路缓存（Cache-Aside）一致性矩阵与 `CLIENT TRACKING` 多级缓存、近似 LRU 与 LFU 24 比特对数衰减算法，以及结合 Redis 8 原生布隆/布谷鸟过滤器的缓存异常治理实战。

> 核对日期：2026 年 11 月 17 日；核对环境为 Redis 8.10.3、Linux/AMD64。

## 7.1 旁路缓存模式、双写一致性与客户端缓存 {#ch7-1}

### 7.1.1 Cache-Aside 只读缓存与直写 / 写回模式边界 {#ch7-1-1}

不同于对软件透明的 CPU 高速缓存或内核 Page Cache，Redis 属于需要业务代码显式编排回源与失效逻辑的**旁路缓存（Cache-Aside）**。按写请求的处理路径划分为两类模式：

- **只读缓存（工业界通用标准）**：读请求先查 Redis，命中即返，未命中则查后端数据库并回填写入 Redis；**所有增删改写请求一律直接更新后端数据库，随后将 Redis 中对应的旧缓存键直接删除**（而非去计算更新缓存值），下次有读请求时再按需懒加载。
- **读写缓存（同步直写 Write-Through / 异步写回 Write-Back）**：需要特别明确一条底层边界——**原生 Redis 在内存满淘汰键值时，无论数据是否修改过一律直接丢弃，绝不支持自动回调将脏数据刷回后端数据库**！因此原生 Redis 无法安全充当无外部落盘组件兜底的纯 Write-Back 缓存；若采用双写更新缓存，并发乱序极易导致数据库与缓存永久分叉。

### 7.1.2 数据库与缓存双写并发时序分析与最终一致性保障 {#ch7-1-2}

即便采用“写数据库 + 删缓存”的只读缓存模式，先后顺序颠倒在并发读写下也会产生天壤之别的一致性后果：

| 执行顺序 | 高并发读写交错竞态时序 | 不一致后果与持续时间 | 工程定论与兜底方案 |
| --- | --- | --- | --- |
| **先删缓存，再更 DB**（不推荐） | `t1` 写线程 A 删缓存 -> `t2` **读线程 B 读缺失查 DB 拿到旧值并抢先回填进缓存** -> `t3` 写线程 A 才把 DB 更成新值 | **极严重**：缓存被旧值长期污染，直至 TTL 自然到期前所有读请求全拿脏数据！ | 所谓“延迟双删 `sleep(N)`”中 `N` 根本无法精准评估慢查询抖动，生产不推荐作为主方案 |
| **先更 DB，再删缓存（标准推荐）** | `t1` 写线程 A 更完 DB -> `t2` 读线程 B 命中尚未删掉的旧缓存 -> `t3` 写线程 A 删掉缓存 | **极轻微**：仅在 `t1～t3` 几毫秒内偶发读旧值，随后缓存被清空，后续所有读均拿新值 | **生产首选**！（极端路径“缓存恰好过期 + 读旧值慢回填晚于写完 DB 删缓存”因内存写远快于磁盘写，概率微乎其微） |

唯一剩下的隐患是 **“第一步更新 DB 成功，第二步网络抖动导致删除 Redis 缓存失败”**。工业界标准解耦闭环是：**业务只管写 MySQL 事务提交，由独立基础设施（如 Canal / Debezium）实时订阅解析 MySQL Binlog 投递至 Kafka/RocketMQ，由消费端幂等执行 `DEL`/`UNLINK` 缓存并带指数退避重试**，彻底剥离业务侵入并保障秒级最终一致性。

### 7.1.3 服务端协助的客户端缓存（CLIENT TRACKING） {#ch7-1-3}

对于极致热点键，在业务进程本地内存（如 Caffeine / Go 本地 Map）再架设一层 L1 缓存可将延迟压至纳秒级，难点在于多实例本地缓存如何及时感知数据变更。**Redis 6.0+ 原生提供服务端协助的客户端缓存（Client-Side Caching）**——推荐先发 `HELLO 3` 通过 RESP 3 `>` Push 帧单连接接收失效推送；若受限于 RESP 2，也可通过 `REDIRECT <sub_client_id>` 转发至订阅了 **`__redis__:invalidate`** 频道的辅助连接（注意订正原书漏写双下划线 `_redis_:invalidate` 的笔误！）。其两种核心追踪模式如下：

1. **默认精确追踪模式（`CLIENT TRACKING ON`）**：服务端在全局追踪表中记录每个客户端读取过的键；当该键被任何客户端修改、删除或过期淘汰时，服务端向读过它的客户端发送**一次性（one-shot）** `invalidate` 消息并清理该记录（客户端下次重读后才重新注册追踪，极大节省服务端内存）。
2. **前缀广播模式（`CLIENT TRACKING ON BCAST PREFIX cfg: PREFIX hot:`）**：服务端无需逐键记录谁读过什么，客户端仅声明关注的键前缀；凡匹配前缀的键发生变更，服务端直接向所有订阅该前缀的客户端广播失效通知，非常适合配置字典与商品基础信息本地缓存。

## 7.2 8 种内存淘汰策略与近似 LRU / LFU 底层机制 {#ch7-2}

### 7.2.1 容量规划与 8 种 maxmemory-policy 选型法则 {#ch7-2-1}

结合互联网重尾访问分布，生产通常将缓存容量 `maxmemory` 规划为后端活跃热数据集的 **15%～30%**，并按业务语义从 8 种 `maxmemory-policy` 中显式指定淘汰策略（默认值 `noeviction` 写满即报错，纯缓存库严禁保持默认）：

| 淘汰候选范围 | 策略名称 | 核心淘汰规则与生产适用场景 |
| --- | --- | --- |
| **不淘汰** | `noeviction`（默认） | 内存达 `maxmemory` 后拒绝新写入（仅允许 `DEL` 与读请求），**仅用于将 Redis 当纯主存储的场景** |
| **全体键值（`allkeys-*`）** | **`allkeys-lfu`（推荐）** | 在所有键中按**访问频次 + 衰减时间**淘汰，有效抵御批量扫描引发的缓存污染，**通用缓存首选** |
| | `allkeys-lru` | 在所有键中按最近最少访问时间戳采样淘汰，适合常规冷热分明且无大批量单次扫描的场景 |
| | `allkeys-random` | 全库随机淘汰，仅在所有键访问概率完全均等时使用 |
| **仅设了 TTL 的键（`volatile-*`）** | **`volatile-lfu` / `volatile-lru`** | **仅在设置了过期时间的键中淘汰**；实战妙用：**给绝对不能丢的置顶公告/核心配置不设 TTL，普通缓存设 TTL**，即可在同一实例内实现核心数据免死金牌！ |
| | `volatile-ttl` / `volatile-random` | 优先淘汰剩余存活时间最短的键（适用于业务明确知晓数据下线次序时）或带 TTL 键随机淘汰 |

### 7.2.2 采样近似 LRU、扫描污染与 LFU 24-bit 概率衰减算法 {#ch7-2-2}

若像教材那样为几千万个键维护全局双向链表并在每次 `GET` 时摘除移到链表头，额外指针将吃掉数 GB 内存且锁/指针操作拖慢吞吐。Redis 通过巧妙复用每个值对象头中仅占 **`24 bit` 的 `lru` 字段**，实现了零链表开销的近似淘汰算法：

1. **采样候选池近似 LRU 及其污染软肋**：
   - `lru` 字段记录秒级相对访问时间戳。触发淘汰时随机抽样 `maxmemory-samples` 个键（默认 `5`，**调至 `10` 即极度逼近真实全局 LRU，切勿像原书示例那样盲目设为 `100` 浪费 CPU**）塞入固定大小的淘汰候选池，每次踢掉池中时间戳最老的键。
   - **致命软肋——缓存污染**：一旦后台跑了一次历史订单全量导出批处理，只会被读取**唯一一次**的百万条冷数据瞬间刷上“最新访问时间戳”，反而把刚在 5 秒前被访问过上千次的真热点数据全部挤出内存！
2. **Redis 4.0+ LFU（Least Frequently Used）底层位拆分与对数衰减机制**：
   - 在 `allkeys-lfu` / `volatile-lfu` 模式下，这 **`24 bit`** 被一分为二精巧复用：

```text
|<──────────── 高 16 bits：ldt (分钟级时间戳) ────────────>|<── 低 8 bits：counter (0~255) ──>|
  记录上次衰减时间（最大折返周期约 45.5 天）                  对数访问频次计数（新键初值 LFU_INIT_VAL = 5）
```

   - **为什么仅 `8 bit`（最大值 `255`）就能区分十万次与百万次访问？——非线性概率对数递增**：每次命中键时，先执行时间衰减，再按公式 `p = 1 / ((counter - 5) × lfu_log_factor + 1)` 计算递增概率，仅当 `[0, 1)` 随机数 `< p` 时才令 `counter + 1`！在默认 **`lfu-log-factor 10`** 下，真实访问 `100` 次对应 `counter ≈ 10`，`1000` 次对应 `18`，**约 `100 万` 次访问才会触顶 `255`**；若业务热点量级达千万级，可将 `lfu-log-factor` 调大至 `100` 拉开区分度。
   - **防止历史旧热点赖着不走——线性分钟衰减**：每次访问该键时，计算当前分钟与 `ldt` 的差值 `num_periods = Δminutes ÷ lfu_decay_time`（默认 **`lfu-decay-time 1`**），直接将 `counter` 减去 `num_periods`（最低减至 `0`）。这样既让单次扫描数据（`counter = 5`）迅速被淘汰，又让过气老热点每闲置 1 分钟自动降权 1 点及时腾出空间。

## 7.3 缓存雪崩、击穿与穿透全链路防御 {#ch7-3}

### 7.3.1 雪崩、击穿与穿透成因对比及互斥重建 / 逻辑过期 {#ch7-3-1}

三大经典缓存高并发异常的触发根因、核心差异与分层防御矩阵如下：

| 异常类型 | 故障本质特征 | 事前无损预防（主力手段） | 事发并发控制与有损兜底 |
| --- | --- | --- | --- |
| **缓存雪崩** | **成批大量 Key 同一时刻集中过期**，或 **Redis 集群节点宕机**，海量请求瞬间冲垮 DB | ① 批量写入 TTL 统一叠加 **`1～5` 分钟随机抖动**；② 部署主从哨兵或 Cluster 高可用自动切主 | 接入层限流保护 DB；非核心接口**服务降级**返回预设兜底值，极端情况熔断暂停故障缓存调用 |
| **缓存击穿** | **单个极高频热点 Key 恰好到期失效**瞬间，成千上万并发读同时穿透打到同一条 DB 记录 | 活动预知极热点键**物理不设 TTL**，活动结束后异步清理 | ① **互斥锁单线程重建**（`SET lock:k id NX PX 3000` 抢到锁的唯一线程查 DB 回填，其余线程休眠 `30ms` 重试读缓存）；② **逻辑过期**（值内嵌 `expire_at` 字段，物理永不过期；发现逻辑过期后异步启后台协程刷库，当前请求立即返回旧值零阻塞） |
| **缓存穿透** | 高频请求查询**缓存与数据库中均根本不存在的数据**（如恶意遍历负数/随机黑客 ID），每次必打穿到 DB | 接口入口严格校验参数格式、ID 取值范围与鉴权签名 | ① **缓存短 TTL 空值**（如缓存 `"NULL"` 设 `30～60s` 过期，简单但随机海量假 ID 会耗内存）；② **前置布隆或布谷鸟过滤器拦截**（注意：**服务熔断治不了穿透**，暂停查缓存只会让 100% 恶意流量直击 DB！） |

### 7.3.2 基于原生布隆与布谷鸟过滤器的零查库防穿透实战 {#ch7-3-2}

布隆过滤器（Bloom Filter）通过一个全 `0` 初始位数组与 `K` 个独立哈希函数映射全量合法主键 ID：写入时将 `K` 个哈希位全部置 `1`；查询某个 ID 时，**只要 `K` 个位中有任意 1 个为 `0`，即可 100% 断定该 ID 在数据库中绝对不存在**，直接在内存微秒级拦截返回！仅当 `K` 个位全为 `1` 时才存在极低概率（如 `1%`）哈希碰撞误判放行。

在 **Redis 8** 中，无需再像原书时代那样外挂第三方模块，引擎已**原生内置 `BF.*` 布隆过滤器与支持删除元素的 `CF.*` 布谷鸟过滤器（Cuckoo Filter）**：

```bash
# 1. 预分配误判率 0.1%（0.001）、预期容量 1000 万合法商品 ID 的原生布隆过滤器
BF.RESERVE bf:valid_skus 0.001 10000000

# 2. 商品上架时同步写入过滤器，详情页请求到达最前线先调用 BF.EXISTS 零成本判存
BF.ADD bf:valid_skus sku_800192
BF.EXISTS bf:valid_skus sku_attack_9999999   # 返回 0 -> 100% 不存在，直接拒绝，绝不触碰 MySQL！

# 3. 若业务存在频繁下架/物理删除 ID 且不希望残留误判率累积，改用原生支持删除的布谷鸟过滤器：
CF.RESERVE cf:valid_users 10000000
CF.ADD cf:valid_users u_10086
CF.DEL cf:valid_users u_10086
```

### 练习 1：复盘“先删缓存再更 DB”线上脏数据事故并设计多级缓存改造

某商品价格服务原更新代码逻辑为：`① redis.Del("price:101") -> ② db.Exec("UPDATE item SET price=199 WHERE id=101")`（原价为 `299`，缓存 TTL 为 `24 小时`）。大促改价瞬间，监控发现数据库价格已成功变为 `199`，但随后整整 24 小时内用户刷出的商品价格始终是旧价 `299`！请画出导致该故障的最小双线程并发时序，并给出同时包含“应用本地 Caffeine L1 + Redis 8 L2 + MySQL”的完整一致性改造方案。

<details>
<summary>查看参考答案</summary>

1. **最小双线程竞态污染时序**：
   - `t1`：改价写线程 A 执行 `redis.Del("price:101")` 删除缓存成功；
   - `t2`：高并发下读线程 B 恰好到达，`GET price:101` 未命中，立即查 MySQL（此时线程 A 的 `UPDATE` 尚未提交），读出旧价 `299`；
   - `t3`：写线程 A 完成 MySQL 更新提交，数据库变为新价 `199`；
   - `t4`：读线程 B 将刚查到的旧价执行 `SET price:101 299 EX 86400` 写回 Redis！自此缓存被旧值 `299` 锁死整整 24 小时。
2. **L1 + L2 + MySQL 多级一致性闭环方案**：
   - **调整写路径为“只写 MySQL + Binlog 异步删 L2”**：改价接口仅执行 MySQL 事务更新 `price = 199`；部署 Canal 监听该表 Binlog 投递 MQ，消费者可靠重试执行 `DEL price:101` 删除 Redis L2 缓存。
   - **打通 L2 -> L1 毫秒级广播失效**：所有商品服务实例连接 Redis 8 时执行 `HELLO 3` 与 **`CLIENT TRACKING ON BCAST PREFIX price:`**；一旦 Canal 消费者删掉（或修改）Redis 中的 `price:101`，Redis 立即通过 RESP 3 Push 通道向全部业务实例推送 `invalidate` 消息，各实例回调立即驱逐本地 Caffeine 中的 `price:101`（同时本地 Caffeine 设 `30s` 兜底过期时间防极端断连）。

### 练习 2：治理每晚全量对账任务引发的缓存命中率断崖下跌

某账务查询系统配置了 `maxmemory 16gb` 与 `maxmemory-policy allkeys-lru`。日常白天缓存命中率稳定在 `96%`，但每天 01:00 对账批处理服务按页遍历查询前一日全部 3000 万笔冷门归档订单后，次日早高峰 08:00 线上实时热单缓存命中率暴跌至 `42%`。此外，大促日某爆款活动结束后，其百万次访问过的商品页长期霸占内存达数小时。请给出完整的 Redis 配置调优命令并解释每项参数的作用。

<details>
<summary>查看参考答案</summary>

1. **故障诊断**：`allkeys-lru` 仅看最近一次访问时间戳，凌晨 01:00 单次扫过的 3000 万笔归档冷单时间戳最新，触发典型的**扫描式缓存污染**，把前一天积累的真正高频热单全部挤出了 `16 GiB` 内存。
2. **LFU 调优配置与原理**：
   ```bash
   CONFIG SET maxmemory-policy allkeys-lfu
   CONFIG SET maxmemory-samples 10
   CONFIG SET lfu-log-factor 10
   CONFIG SET lfu-decay-time 1
   ```
   - `allkeys-lfu`：改为按访问频次淘汰，凌晨仅扫 1 次的对账冷单 `counter` 停留在初值 `5`，无法挤走高频热单；
   - `maxmemory-samples 10`：将淘汰采样基数从 5 提升到 10，以极小 CPU 代价提升 LFU 候选池淘汰精准度；
   - `lfu-log-factor 10`：对数递增因子设为 10，保证百万级访问以内频次层次分明不轻易饱和；
   - `lfu-decay-time 1`：每闲置 1 分钟允许衰减 1 点计数，确保爆款活动结束后不再被访问的旧热点在 3～4 小时内平滑衰减让出空间（同时建议对活动键附加合理的业务 TTL）。

</details>

## 面试题 {#ch7-interview}

以下 3 道面试题聚焦双写更新策略对比、LFU 位编码精妙设计与三大缓存异常辨析。建议先独立作答，再展开核对参考答案。

### 面试题 1：在数据库与缓存双写场景下，为什么大家普遍采用“更新数据库 + 删除缓存”，而不是“更新数据库 + 更新缓存”？

<details>
<summary>查看参考答案</summary>

主要有**并发写乱序脏数据**与**写多读少计算浪费**两大原因：

1. **并发写写乱序导致永久脏数据**：假设请求 A 将库存改为 `10`，紧接着请求 B 将库存改为 `20`。在数据库端 A 先执行、B 后执行（最终 DB 为 `20`）；但由于网络与线程调度抖动，在更新缓存时可能变成 **B 先写缓存 `20`，A 后写缓存 `10`**——导致缓存永久停留在错误旧值 `10`！而“删除缓存”是幂等失效操作，无论谁先删谁后删，结果都是缓存置空，下次读请求必从 DB 拉取最终正确值 `20`。
2. **避免冷数据无效写放大**：若某个字段 1 分钟内被连续修改 50 次但期间只被读取 1 次（尤其缓存值还涉及多表拼装计算时），每次都重算更新缓存纯属浪费 CPU 与带宽；直接删缓存实现懒加载划算得多。

</details>

### 面试题 2：Redis 的 LFU 淘汰算法只用了 `redisObject` 里的 `24` 个比特位，它是怎么同时放进“访问次数”和“衰减时间戳”且统计上百万次访问的？

<details>
<summary>查看参考答案</summary>

Redis 将 `24 bit` 的 `lru` 字段拆分为**高 `16 bit` 时间戳 `ldt` + 低 `8 bit` 对数计数器 `counter`**：

1. **高 `16 bit`（`ldt`）**：以**分钟**为单位记录最近一次衰减检查时间戳（`2^16 = 65536` 分钟 ≈ 45.5 天循环折返），每次键被访问时计算距上次过了多少个 `lfu-decay-time` 周期，对计数器做减法衰减，淘汰同频次键时也用它打破平局。
2. **低 `8 bit`（`counter`，范围 `0～255`，新键初值 `5`）**：不采用每访问一次就 `+1` 的线性计数，而是采用**概率对数递增**——按 `p = 1 / ((counter - 5) × lfu_log_factor + 1)` 生成递增概率，`counter` 越大继续 `+1` 的概率呈反比例指数级减小。在默认因子 `10` 下，仅用 `0～255` 一字节即可映射高达百万量级的真实访问频次。

</details>

### 面试题 3：请一句话区分缓存雪崩、缓存击穿和缓存穿透，并说明为什么“对缓存做服务熔断”不能解决缓存穿透？

<details>
<summary>查看参考答案</summary>

1. **三者核心区分**：
   - **缓存雪崩**：**大批 Key 同时过期**或 **Redis 宕机**，全量正常流量涌向 DB；
   - **缓存击穿**：**单个极热 Key 过期**瞬间，针对该单键的超高并发请求同时击穿去查 DB；
   - **缓存穿透**：高并发请求查询 **Redis 和 DB 中根本都不存在的非法/空数据**，每次都穿透两层存储。
2. **服务熔断无法解决穿透的原因**：缓存服务熔断是指当 Redis 故障时暂时绕开 Redis 避免拖死应用线程；但缓存穿透时 Redis 完全健康，问题出在请求查询的数据在 DB 里也为空——如果把 Redis 熔断绕开，不仅丧失了 Redis 缓存短 TTL 空值和原生 `BF.EXISTS` 布隆过滤器的前置拦截能力，反而会让 100% 恶意穿透流量毫无遮拦地直接砸死后端数据库！防御穿透必须靠**入口参数校验 + 布隆/布谷鸟过滤器前置拦截 + 缓存短过期空对象**。

</details>
