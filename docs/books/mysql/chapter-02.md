# 第 2 章 InnoDB 行格式与数据页结构

## 本章要点

理解 B+ 树索引、MVCC 版本链与间隙锁之前，必须先看清“一行记录如何编码成字节序列”以及“多条记录如何在 16KB 数据页内组织与检索”。本章自底向上拆解这两层物理载体：前半部分深入 InnoDB 默认 `DYNAMIC`（及同源 `COMPACT`）行格式的变长字段长度列表、`NULL` 值位图、40 位记录头信息、三大隐藏列与单行 `65535` 字节上限及行溢出机制；后半部分剖析 `FIL_PAGE_INDEX` 数据页的七大组件，揭示伪记录单向链表、垃圾链表空间重用、页目录槽分裂二分查找以及页首尾撕裂写校验的协同设计。

> 核对日期：2026 年 11 月 17 日；核对环境为 MySQL 8.4.13、Linux/AMD64。

## 2.1 InnoDB 行格式与记录二进制布局 {#ch2-1}

InnoDB 以**页**为磁盘与内存交互的最小单元，默认页大小为 `16384` 字节（`16 KiB`），由初始化期只读变量 `innodb_page_size` 决定，并提供四种行格式：

| 行格式名称 | 核心特征与溢出列策略 | 现行状态与适用建议 |
| --- | --- | --- |
| **`DYNAMIC`（默认）** | 紧凑变长编码；行溢出时采用**完全行溢出**，本页真实数据区仅留 `20` 字节溢出页指针 | **MySQL 5.7.9+ 及 8.0 / 8.4 默认格式**，单页能装更多记录，常规表首选 |
| `COMPACT` | 额外信息与 `DYNAMIC` 完全相同；但行溢出时在本页保留 **`768` 字节前缀 + `20` 字节指针** | 5.1～5.6 主流格式，大字段多时易导致单页记录数骤降、B+ 树层级升高 |
| `REDUNDANT` | 5.0 前旧格式：无 `NULL` 位图，逆序保存**所有列**结束偏移量，记录头占 `6` 字节，`CHAR(M)` 固定占满 `M × W` 字节 | 仅用于兼容远古遗留表空间 |
| `COMPRESSED` | 在 `DYNAMIC` 完全行溢出基础上对页面做 `zlib` 压缩 | 占用额外 CPU 解压缩，现代存储层压缩通常更高效 |

### 2.1.1 DYNAMIC / COMPACT 记录额外信息与隐藏列 {#ch2-1-1}

在 `DYNAMIC` 与 `COMPACT` 格式下，每条记录在物理上紧邻排布为**记录的额外信息**与**记录的真实数据**两段：

```text
◄─────── 从指针位置向左逆序读取元数据 ───────┼─────── 从指针位置向右顺序读取列数据 ───────►
[ 变长字段长度列表 | NULL 值列表 | 记录头信息(5B) ] [ row_id(可选6B) | trx_id(6B) | roll_ptr(7B) | 列1 | 列2 ... ]
                                                 ▲
                                      next_record 指针精确指向此处！
```

各组成部分的精确编码规则如下：

1. **变长字段长度列表（按列逆序、仅计非 `NULL` 变长列）**：涵盖 `VARCHAR(M)`、`VARBINARY(M)`、`TEXT`、`BLOB` 以及**使用变长字符集（如 `utf8mb4`、`gbk`）的 `CHAR(M)` 列**。设列字符集 `Maxlen` 为 `W`、声明最大字符数为 `M`、当前值实际字节数为 `L`，单列长度占用 `1` 字节还是 `2` 字节遵循唯一充要规则——**当且仅当 `M × W > 255` 且实际字节数 `L > 127` 时占 `2` 字节，其余所有非空变长列均占 `1` 字节**；值为 `NULL` 的列不计入该列表，也在真实数据区占 `0` 字节。
2. **`NULL` 值列表（按列逆序、整字节高位补 `0`）**：**仅统计允许为 `NULL` 的列**，主键与显式 `NOT NULL` 列均不占比特位。每个可空列对应 `1` 比特——`1` 代表 `NULL`、`0` 代表非空，总字节数为 `⌈可空列数 ÷ 8⌉`；若全表所有列均为 `NOT NULL`，则完全省去该列表。
3. **记录头信息（固定 `5` 字节 = `40` 比特）**：各比特位职责速查如下：

| 字段名称 | 位数 | 核心作用与取值规则 |
| --- | :---: | --- |
| `预留位 1 / 2` | `2 bit` | 传统表为 `0`；**MySQL 8.0.12+ / 8.0.29+ 执行 `ALGORITHM=INSTANT` 秒级加删列后**，借用此处标志位标识记录携带额外列数或 `1` 字节行版本号 |
| `deleted_flag` | `1 bit` | `0` 正常记录；`1` 已被 `DELETE` 原地打标待后台 `purge` 回收（见 [8.3 节](./chapter-08#ch8-3)） |
| `min_rec_flag` | `1 bit` | 仅 B+ 树非叶子层最左侧的那条最小目录项记录置为 `1`，普通用户记录恒为 `0` |
| `n_owned` | `4 bit` | 页目录分组内每组最后一条最大记录（槽主）记录本组总条数，组内其余记录均为 `0` |
| `heap_no` | `13 bit` | 记录在页面堆中的物理分配序号：`Infimum = 0`、`Supremum = 1`，用户记录从 `2` 起递增且终生不变 |
| `record_type` | `3 bit` | `0` 普通用户记录；`1` B+ 树非叶子层目录项记录；`2` 最小伪记录 `Infimum`；`3` 最大伪记录 `Supremum` |
| `next_record` | `16 bit` | 有符号相对字节偏移量：从当前记录真实数据起点指向**键值更大的下一条记录**真实数据起点 |

注意上图中 **`next_record` 指针恰好指向“记录头信息”与“真实数据”的交界点**：CPU 顺着指针跳到该地址后，向左紧挨着读取 5 字节记录头、逆序的 `NULL` 位图与逆序的第 1 列长度，向右紧挨着读取第 1 列真实数据——前序高频列的元数据与数据紧凑落在同一条 CPU 高速缓存行（Cache Line）内，最大限度减少内存访问延迟。

4. **主键生成回退与三大隐藏列**：聚簇索引记录优先以显式 `PRIMARY KEY` 为主键；若未定义，选用**首个所有列均声明 `NOT NULL` 的 `UNIQUE` 键**；若仍不满足，InnoDB 自动补充 `6` 字节隐藏主键列 **`DB_ROW_ID`**。此外，每条聚簇索引记录必定携带 `6` 字节事务 ID **`DB_TRX_ID`** 与 `7` 字节回滚指针 **`DB_ROLL_PTR`**（支撑 MVCC，见 [9.2 节](./chapter-09#ch9-2)）。
5. **变长字符集下 `CHAR(M)` 的空间保留机制**：在 `ascii` / `latin1` 下 `CHAR(10)` 固定占 `10` 字节且不计入变长字段列表；但在 `utf8mb4`（`W = 4`）下，`CHAR(10)` 实际可占 `10～40` 字节，因此**既要记入变长字段长度列表，又会在真实数据区至少预留 `10` 字节**（不足部分填空格 `0x20`），目的是后续将该列更新为不超过 `10` 字节的新值时可直接就地覆盖而不引发页内碎片。

### 2.1.2 单行 65535 字节上限与行溢出边界推导 {#ch2-1-2}

需严格区分 **SQL Server 层单行定义上限** 与 **InnoDB 16KB 页内行溢出阈值** 两个不同层面的限制：

- **Server 层单行最大 `65535` 字节限制**（不含 `TEXT` / `BLOB` 外部存储区）：建表时所有列在 Server 层计算的字节总和不得超过 `65535`。例如在默认 `utf8mb4`（`W = 4`）下创建仅含单个可空 `VARCHAR(M)` 列的表，需扣除 `2` 字节长度头与 `1` 字节 `NULL` 位图，最大字符数 `M = ⌊(65535 - 2 - 1) ÷ 4⌋ = 16383`；若声明 `VARCHAR(16384)` 会直接报错 `ERROR 1074: Column length too big for column 'c' (max = 16383)`；改为 `NOT NULL` 省去 `1` 字节位图后上限仍为 `⌊65533 ÷ 4⌋ = 16383`。
- **InnoDB 数据页行溢出条件**：InnoDB 强制规定每个 B+ 树索引页**至少容纳 `2` 条记录**（否则层级会退化为链表）。扣除单页固定头尾与伪记录开销 `132` 字节，以无显式主键的单列变长表（单行固定元数据与隐藏列共 `27` 字节）为例，不发生行溢出的条件为：

```text
132 + 2 × (27 + n) < 16384  ══►  n < 8099 字节
```

一旦单列或多列总长令单页无法装下 `2` 条完整记录，InnoDB 即把超长列数据拆入 `FIL_PAGE_TYPE_BLOB` 溢出页链表：在默认 **`DYNAMIC`** 格式下，本页真实数据处**只留 `20` 字节溢出指针**，把全部真实字节迁往溢出页，确保主数据页始终紧凑高效。

## 2.2 InnoDB 16KB 数据页七大组件剖析 {#ch2-2}

### 2.2.1 页面总体布局、伪记录单向链表与垃圾重用 {#ch2-2-1}

存放 B+ 树节点的数据页 `FIL_PAGE_INDEX`（页类型 `0x45BF`）固定由七部分组成：

| 顺序 | 组件名称 | 占用空间 | 核心职责说明 |
| :---: | --- | :---: | --- |
| 1 | `File Header`（文件头部） | 固定 **`38 B`** | 通用页头：页校验和、本页页号、上下页双向链表指针、页面最新 LSN、页类型、表空间 ID |
| 2 | `Page Header`（页面头部） | 固定 **`56 B`** | 索引页专属状态：页目录槽数、空闲堆顶、正常记录数 `PAGE_N_RECS`、B+ 树层级 `PAGE_LEVEL`、二级索引 `PAGE_MAX_TRX_ID` 等 |
| 3 | `Infimum + Supremum` | 固定 **`26 B`** | 系统内置最小伪记录（偏移 `99`）与最大伪记录（偏移 `112`），各占 `5B 头 + 8B 文本 = 13B` |
| 4 | `User Records`（用户记录） | 动态增长 | 从 `Free Space` 自上而下分配物理堆槽位，通过 `next_record` 按键值从小到大串成单向链表 |
| 5 | `Free Space`（空闲空间） | 动态收缩 | 尚未使用的连续空闲字节区；当与页目录相遇时触发页内重组或页分裂 |
| 6 | `Page Directory`（页目录） | `2B × 槽数` | 紧贴 `File Trailer` **从高地址向低地址逆序生长**的槽数组，每个槽存分组最大记录的页内偏移量 |
| 7 | `File Trailer`（文件尾部） | 固定 **`8 B`** | 通用页尾：前 `4B` 页校验和 + 后 `4B` LSN 低位，配合双写缓冲区检测断电半页写 |

记录在页内的增删改围绕两条链表运转：

- **正常记录单向链表**：无论物理插入先后（`heap_no` 仅反映物理堆位置），`next_record` 始终按主键值严格升序串联：`Infimum` → 最小用户记录 → … → 最大用户记录 → `Supremum`（`next_record = 0`）。
- **垃圾链表（`PAGE_FREE`）与页面重组**：记录被彻底清理（Purge）后不会立即平移后续物理字节，而是置 `deleted_flag = 1` 并挂入由 `PAGE_FREE` 指向的可重用垃圾链表，同时将字节数计入 `PAGE_GARBAGE`。后续插入若能直接复用垃圾链表头节点空间则零碎片覆盖；若连续 `Free Space` 不足、但 `Free Space + PAGE_GARBAGE` 足够容纳新记录，InnoDB 会在内存中执行一次**页面重组**（Page Reorganization）紧缩消除所有空洞，无须提前触发昂贵的页分裂。

### 2.2.2 页目录（Page Directory）槽分裂与二分查找 {#ch2-2-2}

若页内有数百条记录，单纯沿单向链表顺序扫描开销过高。InnoDB 将页内所有正常记录（含两条伪记录，不含已删记录）按以下三条铁律切分为若干分组，并把每组最后一条最大记录的页内偏移量存入 `2` 字节的**槽（Slot）**：

1. **`Infimum` 所在首组**：永远独占 `1` 条记录（`n_owned = 1`）；
2. **中间普通分组**：记录条数严格维持在 **`4～8` 条**（`n_owned ∈ [4, 8]`）；
3. **`Supremum` 所在末组**：记录条数允许为 **`1～8` 条**（`n_owned ∈ [1, 8]`）。

当某个已满 `8` 条记录的分组插入第 `9` 条记录时，自动分裂为前组 `4` 条、后组 `5` 条，并在 `Page Directory` 新增一个槽。由此，**页内按主键查找任意目标值 `K` 只需高效的两步（`O(log₂ S) + O(1)`）**：

1. **对槽数组做二分查找**：维护 `low = 0`、`high = 槽数 - 1`，每次读取中间槽指向的最大记录主键值与 `K` 比较，收缩区间直至 `high - low == 1`，锁定目标必落在槽 `high` 管辖的分组内。
2. **跳回前驱槽顺序遍历最多 8 条记录**：由于单向链表无法倒退，读取前一个槽 `low` 指向的记录，顺其 `next_record` 迈出一步即到达槽 `high` 分组的最小记录，随后最多向后比对 `8` 次即可精确命中或判定不存在。

### 2.2.3 File Header 双向页链表与 File Trailer 撕裂页校验 {#ch2-2-3}

单个 16KB 页之外，`File Header` 与 `File Trailer` 解决了跨页扫描与落盘完整性两大难题：

- **同层页间双向链表**：数据页在表空间文件中的页号（`FIL_PAGE_OFFSET`）未必物理相邻，`File Header` 通过 `4` 字节 **`FIL_PAGE_PREV`** 与 `4` 字节 **`FIL_PAGE_NEXT`** 将同一层级的索引页串成双向链表，使范围查询到达当前页 `Supremum` 后能直接 `O(1)` 跳往下一页，也支撑 `ORDER BY ... DESC` 反向跨页扫描。
- **断电撕裂页（Torn Page）检测**：操作系统文件系统块通常为 `4 KiB`，刷写一个 `16 KiB` InnoDB 页需要分 `4` 个物理块落盘。若写完前 `8 KiB` 时突然断电，`File Header` 中的新校验和（及 `FIL_PAGE_LSN`）已落盘，而位于页末最后 `8` 字节的 **`File Trailer`** 仍保留旧校验和与旧 LSN 低 4 字节——重启恢复对比首尾不一致即可立刻识破物理页损坏，并从独立双写文件（`.dblwr`，见 [3.1 节](./chapter-03#ch3-1)）还原完好页面副本后再重放 Redo 日志。

### 练习 1：核算 DYNAMIC 行格式下单条记录的精确字节长度

已知在 MySQL 8.4 中执行以下建表与插入语句：

```sql
CREATE TABLE user_profile (
    id BIGINT NOT NULL,
    nick VARCHAR(20) NOT NULL,
    bio VARCHAR(100) NULL,
    tag CHAR(4) NULL,
    PRIMARY KEY (id)
) ENGINE=InnoDB CHARSET=utf8mb4 ROW_FORMAT=DYNAMIC;

INSERT INTO user_profile VALUES (1001, '张伟', NULL, 'vip');
```

请逐项计算这条记录的“变长字段长度列表”“`NULL` 值列表”“记录头信息”“隐藏列”与“各用户列真实数据”各自占用的字节数，并求出整条记录占用的总字节数。

<details>
<summary>查看参考答案</summary>

1. **变长字段长度列表（共 `2` 字节）**：
   - `nick VARCHAR(20)`：`M × W = 20 × 4 = 80 ≤ 255`，实际写入 `'张伟'` 占 `6` 字节，长度头占 **`1` 字节**。
   - `bio VARCHAR(100)`：本行值为 `NULL`，**不计入**变长字段长度列表（`0` 字节）。
   - `tag CHAR(4)`：表字符集为变长 `utf8mb4`（`W = 4`），故 `CHAR(4)` 须计入变长字段长度列表；`4 × 4 = 16 ≤ 255`，长度头占 **`1` 字节**。
   - 按逆序存放 `[tag长度, nick长度]`，合计 `1 + 1 = 2` 字节。
2. **`NULL` 值列表（共 `1` 字节）**：
   - `id` 与 `nick` 均为 `NOT NULL`，仅 `bio` 与 `tag` 两列允许为 `NULL`，共 `2` 个比特位，向上按字节对齐占 **`1` 字节**——二进制 `00000001`，最低位对应第 1 个可空列 `bio = NULL`。
3. **记录头信息**：固定占 **`5` 字节**。
4. **隐藏列（共 `13` 字节）**：表已有显式主键 `id`，不生成 `DB_ROW_ID`；仅含 `DB_TRX_ID`（`6` 字节）+ `DB_ROLL_PTR`（`7` 字节）= **`13` 字节**。
5. **用户列真实数据（共 `18` 字节）**：
   - `id BIGINT`：固定 **`8` 字节**；
   - `nick = '张伟'`：UTF-8 编码每个常见汉字 3 字节，占 **`6` 字节**；
   - `bio = NULL`：真实数据区占 **`0` 字节**；
   - `tag = 'vip'`：`utf8mb4` 下 `CHAR(4)` 至少保留 `M = 4` 字节，`'vip'` 3 字节后补 1 个空格 `0x20`，占 **`4` 字节**。
6. **整条记录总字节数**：`2 + 1 + 5 + 13 + (8 + 6 + 0 + 4) = 39` 字节。

### 练习 2：推演数据页插入记录时的槽分裂与二分查找步骤

向一张新建空表（主键为 `id INT`）按升序依次插入主键为 `10, 20, 30, 40, 50, 60, 70, 80` 共 8 条记录（均落在同一个数据页内）。请回答：

1. 插入完这 8 条记录后，该页 `Page Directory` 共有几个槽？每个槽指向哪条记录，对应的 `n_owned` 分别是多少？
2. 紧接着再插入 `id = 90` 后，槽数量与各槽的 `n_owned` 如何变化？此时在该页按主键查找 `id = 60` 的精确步骤是什么？

<details>
<summary>查看参考答案</summary>

1. **插入 8 条记录后的页目录状态**：
   - 空页初始有 2 个槽：槽 0 指向 `Infimum`（`n_owned = 1`），槽 1 指向 `Supremum`（`n_owned = 1`）。
   - 插入 `10～70` 共 7 条记录后，槽 1（`Supremum` 组）包含 `10..70 + Supremum` 共 **8 条记录**（尚未超过上限 8，不分裂）。
   - 插入第 8 条用户记录 `id = 80` 时，槽 1 组达到 **9 条记录**，触发分裂为前组 `4` 条（`10～40`）和包含 `50～80` 与 `Supremum` 的后组 `5` 条！
   - 因此插入完 `10～80` 后共有 **`3` 个槽**：
     - **槽 0**：指向 `Infimum`，`n_owned = 1`；
     - **槽 1**：指向 `id = 40`，`n_owned = 4`；
     - **槽 2**：指向 `Supremum`，`n_owned = 5`。
2. **再插入 `id = 90` 后及查找 `id = 60` 的步骤**：
   - 插入 `90` 落入槽 2（`Supremum` 组），组内条数由 `5` 变为 `6`（仍 `≤ 8` 不再分裂），故仍为 **`3` 个槽**，仅槽 2 的 `n_owned` 更新为 **`6`**。
   - **查找 `id = 60`**：① 初始 `low = 0, high = 2`，计算 `mid = 1`；读取槽 1 指向的记录主键值 `40 < 60`，更新 `low = 1`；此时 `high - low == 1` 二分结束，锁定目标在槽 2 分组。② 取出槽 `low = 1` 指向的记录 `id = 40`，沿 `next_record` 跳到 `id = 50`，再跳一步即命中 `id = 60`。

</details>

## 面试题 {#ch2-interview}

以下 3 道面试题聚焦 `VARCHAR` 与 `CHAR` 存储误区、行格式演进及页内数据结构设计。建议先独立作答，再展开核对参考答案。

### 面试题 1：在默认 `utf8mb4` 下单列 `VARCHAR(M)` 最大能建多大？同样存 `'abc'`，`VARCHAR(10)` 和 `VARCHAR(1000)` 在磁盘和执行期有区别吗？

<details>
<summary>查看参考答案</summary>

1. **最大声明字符数**：Server 层规定除 `TEXT` / `BLOB` 外单行最大字节和为 `65535`。若表只有这一个 `VARCHAR(M)` 列（无其他列占用字节），扣除 `2` 字节变长头（以及可空时的 `1` 字节 `NULL` 位图），在 `utf8mb4`（4 字节/字符）下最大可建 **`VARCHAR(16383)`**；若表还有其他字段，需先扣减其他字段及可空位图字节后再除以 `4`。
2. **`VARCHAR(10)` 与 `VARCHAR(1000)` 存 `'abc'` 的差异**：
   - **InnoDB 磁盘行体积完全相同**——均为 `1` 字节变长长度头加 `3` 字节 `'abc'`，因为即使 `M × W = 4000 > 255`，只要实际长度 `L = 3 ≤ 127` 依然只用 `1` 字节记录长度；
   - **但在查询优化与执行期存在显著差异**：① `EXPLAIN` 评估索引扫描边界 `key_len` 时按 `M × 4 + 2` 预留，索引键缓冲开销更大；② 在排序缓冲区（Sort Buffer）或早期 `MEMORY` 引擎临时表中可能按最大声明宽度预留内存或触发更早的磁盘溢出，因此仍应按真实业务上限合理声明 `M`，切勿无脑全写成 `VARCHAR(1000)`。

</details>

### 面试题 2：在 `utf8mb4` 表中把定长状态码声明为 `CHAR(10)`，它在 InnoDB 底层的存储真的是定长 10 字节吗？

<details>
<summary>查看参考答案</summary>

**不是定长 10 字节，而是 `10～40` 字节的变长存储，且同样要占用 `1` 字节变长字段长度列表！**

只有在 `ascii` 或 `latin1` 等单字节定长字符集下，`CHAR(10)` 才不计入变长字段长度列表并严格固定占 `10` 字节。在 `utf8mb4` 下，10 个汉字或 Emoji 需占 `30～40` 字节，因此 InnoDB 必须将其视为变长列记入变长字段长度列表；唯一与 `VARCHAR(10)` 不同的是，即便只存入 `'A'`，`CHAR(10)` 也会在真实数据区保底填充空格占满 `10` 字节（预留给就地更新）。因此若字段只存纯 ASCII 数字字母编码（如手机号、固定长度哈希或单号），显式为该列指定 `CHARACTER SET ascii` 或改用 `VARCHAR` 更节省空间。

</details>

### 面试题 3：为什么 MySQL 默认行格式从 `COMPACT` 换成了 `DYNAMIC`？两者处理大字段行溢出有什么本质区别？

<details>
<summary>查看参考答案</summary>

本质区别在于**发生行溢出时主数据页保留多少字节**：

- **`COMPACT`（部分行溢出）**：超长列溢出时仍强行在主 B+ 树叶子页保留前 **`768` 字节前缀** + `20` 字节溢出指针（共 `788` 字节）。若一张表有多个 `TEXT` / 长 `VARCHAR` 列，单条记录在主页就占去数 KB，导致一个 `16 KiB` 叶子页只能装几条记录，B+ 树退化变高、范围扫描与全表扫描即便不查该大字段也要多读大量页面。
- **`DYNAMIC`（完全行溢出）**：一旦触发行溢出，把该列的**全部真实字节**迁入外部 `BLOB` 溢出页，主数据页仅保留 **`20` 字节指针**，使聚簇索引主树保持极高扇出与紧凑度，不读取该大列时零额外 I/O 浪费。

</details>
