# 第 1 章 网络分层模型、一次网页访问全过程与 Linux 协议栈

## 本章要点

理解计算机网络最有效的方式，是先建立清晰的**分层边界**，再沿着一次真实的 HTTP 请求俯瞰数据包如何穿过主机协议栈、交换机和路由器，最后下沉到 Linux 内核看清网卡与 CPU 如何协作收发字节。本章整合原书《图解网络》基础篇全部内容（2.1–2.3 节），消除 TCP/IP 模型在原书多处重复的铺垫，将 DNS、IP 路由与 ARP 的深入细节交由[第 2 章](./chapter-02)展开，同时修正原书在浏览器临时端口归属、网卡硬件帧封装、TCP 乱序包处理、NAPI 中断恢复时机、`ksoftirqd` 调度以及 `skb_clone` 拷贝机制上的技术偏差。

读完本章后，应能准确对照 TCP/IP 与 OSI 各层职责及封装单位，完整串联“键入网址到网页显示”的每一跳地址变换规律，清晰区分二层交换机与三层路由器的转发行为，并能绘制 Linux 内核基于 DMA、NAPI 与 `struct sk_buff` 的零拷贝收发包全路径。

> 核对日期：2026 年 11 月 20 日；核对环境为 RFC 1122、IEEE 802.3 以太网规范及 Linux 6.12 LTS 网络子系统实现。

## 1.1 TCP/IP 网络模型与 OSI 分层架构 {#ch1-1}

### 1.1.1 为何需要分层与两种模型对照 {#ch1-1-1}

同机进程间通信可依赖管道、共享内存或 Unix Domain Socket，而跨主机通信面对的是异构硬件、不同操作系统与复杂多跳链路。网络协议通过**分层解耦**解决复杂性：每一层只向下层委托传输、向上层提供约定接口，单层演进不影响上下层（例如将 HTTP 底层从 TCP 替换为 QUIC，上层 HTTP 语义保持不变）。

国际标准化组织提出了理论完备的 **OSI 七层参考模型**，而互联网与 Linux 内核实际落地的是更简洁实用的 **TCP/IP 四层模型**（RFC 1122）：

| OSI 七层模型 | TCP/IP 四层模型 | 核心职责 | 常见协议 | 传输数据单位（PDU） | 典型设备 / 工程映射 |
| --- | --- | --- | --- | --- | --- |
| 7. 应用层<br>6. 表示层<br>5. 会话层 | **应用层**<br>（用户态） | 提供应用交互语义、编解码与会话管理 | HTTP/HTTPS、DNS、SSH、gRPC、WebSocket | 报文 / 消息（Message） | 应用程序、七层负载均衡（Nginx/Envoy） |
| 4. 传输层 | **传输层**<br>（内核态为主） | **端到端**进程通信、端口复用、可靠性与流控 | TCP、UDP、QUIC（用户态居多） | 段（Segment，TCP）/ 数据报（Datagram，UDP） | 四层负载均衡（LVS/Maglev） |
| 3. 网络层 | **网络层**<br>（内核态） | **主机到主机**跨网段寻址、路由转发与分片 | IPv4、IPv6、ICMP、IGMP | 包 / 分组（Packet） | 三层路由器、三层交换机 |
| 2. 数据链路层<br>1. 物理层 | **网络接口层**<br>（驱动 + 硬件） | **相邻节点**成帧、MAC 寻址、差错校验与光电信号传输 | Ethernet、Wi-Fi（802.11）、ARP/NDP | 帧（Frame）/ 比特（Bit） | 网卡（NIC）、二层交换机 |

> **工程术语对齐**：日常架构中常说的“**四层负载均衡**”与“**七层负载均衡**”沿用的是 **OSI 编号**——四层对应传输层（基于 IP+端口转发 TCP/UDP 连接），七层对应应用层（解析 HTTP URL、Header 或路由规则）。此外，现代 **QUIC** 虽运行在用户态并封装在 UDP 之上，但其职责属于传输层（见[第 6 章 QUIC 与 HTTP/3](./chapter-06#ch6-4)）。

### 1.1.2 逐层封装、MTU 与 MSS 的协作关系 {#ch1-1-2}

应用数据自顶向下穿越协议栈时，每一层都在前一层数据前添加本层协议头部（链路层还会在末尾附加 4 字节 FCS 帧校验序列）；到达接收端后，再自底向上逐层剥离头部：

```text
应用层:                                        [      HTTP 报文      ]
传输层:                        [ TCP 头 (20B+) |      HTTP 报文      ]  <-- Segment (受 MSS 约束)
网络层:        [ IP 头 (20B+)  | TCP 头 (20B+) |      HTTP 报文      ]  <-- Packet  (受 MTU 约束)
链路层: [ MAC 头 (14B) | IP 头 | TCP 头        |      HTTP 报文      | FCS (4B) ] <-- Frame
```

这里有两个最容易混淆的长度上限：
- **MTU（Maximum Transmission Unit，最大传输单元）**：链路层单帧可承载的最大载荷（即 IP 包总大小上限），标准以太网为 **1500 字节**。若 IPv4 报文超过 MTU 且未禁止分片，将在网络层被拆分为多个分片。
- **MSS（Maximum Segment Size，最大报文段长度）**：TCP 单个段所能承载的纯应用数据最大长度。以太网无扩展选项下，IPv4 的 MSS 通常为 `1500 - 20(IPv4头) - 20(TCP头) = 1460` 字节（开启 12 字节 TCP 时间戳选项后为 `1448` 字节；IPv6 因首部固定 40 字节，常规 MSS 为 `1440` 字节）。TCP 主动按 MSS 切分数据，正是为了避免低效且易放大丢包代价的 IP 层分片（详见[第 3 章 MSS 与 IP 分片](./chapter-03#ch3-1-3)）。

## 1.2 键入网址到网页显示的全链路追踪 {#ch1-2}

设想在浏览器地址栏输入 `https://www.example.com/index.html`（以下为聚焦基础网络路径，先以 TCP + HTTP 封装为例，HTTPS 加密细节见[第 7 章](./chapter-07)），整个请求经历 **7 个连贯阶段**：

### 1.2.1 URL 解析、DNS 查询与传输层封装 {#ch1-2-1}

1. **解析 URL 与构造 HTTP 请求**：浏览器拆解出协议方案（`https`）、主机名（`www.example.com`）、端口（默认 443/80）与路径（`/index.html`，省略时默认 `/`），组装 HTTP 请求报文。
2. **DNS 域名解析**：发送数据前必须知道目标服务器的 IP 地址。客户端在常见默认配置下通常依次检索**浏览器 DNS 缓存 → 操作系统缓存 → 本机 `hosts` 文件**；若均未命中，则向配置的本地递归 DNS 解析器发起查询，由其逐级迭代询问**根 DNS（`.`）→ 顶级域 DNS（`.com`）→ 权威 DNS（`example.com`）**拿到目标 IP。需要注意，这只是常见典型顺序而非统一铁律——Linux 实际解析顺序由 `/etc/nsswitch.conf` 的 `hosts:` 配置决定（如常见的 `files dns` 会先查 `/etc/hosts`），且现代浏览器启用 DoH 或自带解析器时可能跳过系统 `hosts` 文件与 OS 缓存（完整流程与 DoH/DoT 见[第 2 章 DNS](./chapter-02#ch2-3-1)）。
3. **建立连接与 TCP 封装**：应用程序通过操作系统 Socket 接口委托内核协议栈工作。内核先与目标 IP:端口完成 **TCP 三次握手**（若为 HTTPS 还需紧接着完成 TLS 握手），再将超过 MSS 的 HTTP 数据分段并封装 TCP 头（源端口、目的端口、序列号、确认号、标志位与接收窗口）。
   - **口径校准**：原书 2.1 节称“浏览器每个标签页是独立进程，操作系统为进程分配临时端口号”。严谨来说，临时端口（Ephemeral Port）是按**传输层 Socket 连接**分配的，并非按标签页或进程一一对应；现代浏览器（如 Chromium）由独立的 Network Service 进程统一管理连接池，多个访问同一源站的标签页还会复用同一条 HTTP/2 或 HTTP/3 连接。

### 1.2.2 IP 路由选路与 MAC 下一跳封装 {#ch1-2-2}

4. **IP 封装与路由决策**：网络层加上 IP 头，填入源 IP、目的 IP 与上层协议号（TCP 为 `6`，UDP 为 `17`，ICMP 为 `1`）。若主机有多块网卡，内核通过查询**本地路由表**（现代 Linux 使用 `ip route` 查看，替代已废弃的 `route -n`）按**最长前缀匹配**决定出接口与下一跳：
   - 若目的 IP 与本机在同一子网，命中直连网段路由，直接将该目的 IP 作为下一跳；
   - 若跨子网，**并非一律走默认网关**：当路由表中存在指向更具体目标网段的路由条目时，内核按最长前缀匹配优先走对应路由指定的下一跳与出接口；仅当所有更具体网段均未命中时，才退而匹配默认路由（`default` / `0.0.0.0/0`），将**默认网关（路由器）IP** 作为下一跳，并用对应出接口的 IP 填充源 IP；若全无匹配且未配置默认路由，则直接判定目标网络不可达（`ENETUNREACH`，详见[第 2 章路由表与最长前缀匹配](./chapter-02#ch2-1-3)）。
5. **MAC 封装与 ARP 解析**：以太网仅识别 48 位 MAC 地址。内核查询 **ARP 缓存表**（现代 Linux 使用 `ip neigh` 查看，替代 `arp -a`）获取下一跳 IP 对应的 MAC 地址；若未命中，则在局域网广播 ARP 请求查询下一跳 MAC。随后封装 14 字节以太网帧头：源 MAC 为本机出接口网卡 MAC，目的 MAC 为**下一跳设备**（直连目标或默认网关）的 MAC，EtherType 填 `0x0800`（IPv4）或 `0x86DD`（IPv6）。
6. **网卡硬件发出电/光信号**：网卡通过 DMA 读取内存中的以太网帧，**由网卡硬件（MAC/PHY 芯片）**在帧前附加前导码（Preamble）与起始帧分界符（SFD）、在帧尾计算并附加 4 字节帧校验序列（FCS），再调制成电信号、光信号或无线电波发出。（校准原书 2.2 节表述：前导码/SFD/FCS 属于网卡硬件职责，并非由驱动拷贝数据后软件拼接。）

### 1.2.3 交换机、路由器接力与对端解封 {#ch1-2-3}

数据包离开主机后，通常依次经过**二层交换机**和**三层路由器**的多跳接力：

```text
[主机 A] ──(源MAC:A, 目的MAC:R1)──> [二层交换机] ──(帧原样转发)──> [路由器 R1]
                                                                       │
         <──(源IP:A, 目的IP:B 全程不变[无NAT]; 每过一跳路由重封装 MAC 头)──┘
                                                                       v
[服务器 B] <──(源MAC:R2, 目的MAC:B)── [二层交换机] <──(源MAC:R2)── [路由器 R2]
```

| 对比维度 | 二层交换机（Switch） | 三层路由器（Router） |
| --- | --- | --- |
| **工作层级与依据** | 数据链路层（L2），查 **MAC 地址表**（MAC ↔ 物理端口） | 网络层（L3），查 **IP 路由表**（网段 ↔ 下一跳/出接口） |
| **接口地址特性** | 透明转发端口本身不参与 MAC 过滤，直接接收所有进入帧（网管型交换机仅为管理/STP/LLDP 配备控制面 MAC） | 每个三层路由接口均具备独立的 **MAC 地址与 IP 地址**，只接收目的 MAC 匹配自身（或广播/组播）的帧 |
| **地址表学习与未知处理** | 自动学习入帧的**源 MAC**；查不到目的 MAC 或遇广播帧（`FF:FF:FF:FF:FF:FF`）时向除入端口外的同广播域端口**泛洪（Flooding）** | 由静态配置或动态路由协议（OSPF/BGP）维护路由表；无匹配条目时丢弃并回复 ICMP 不可达 |
| **对报文的改动** | **原样转发**，不修改源/目的 MAC 与 IP 头 | 剥离旧 MAC 头，将 IPv4 **TTL 减 1**（归零则丢弃并回 ICMP 超时），查下一跳 ARP 并**重新封装新的源/目的 MAC 头** |

**跨网段传输的核心不变式**：在不经过 NAT 设备的前提下，数据包从客户端发往服务器的整个多跳过程中，**源 IP 与目的 IP 始终不变**（标识全局起终点）；而**源 MAC 与目的 MAC 每经过一台路由器都会重新替换**（标识当前链路区间的相邻两跳）。

7. **服务器解封与响应**：目标服务器网卡校验 FCS 与目的 MAC 匹配后上交协议栈；IP 层核对目的 IP 并按协议号 `6` 交给 TCP 层；TCP 层按四元组定位到监听 80/443 端口的已连接 Socket，核对序列号并回复 ACK，按序将数据写入 Socket 接收缓冲区交由 Web 服务进程。
   - **重要勘误**：原书 2.2 节称“TCP 拆开包头看序列号是不是想要的，如果不是就丢弃”。这是不准确的——当收到的乱序报文段**落在当前接收窗口内**时，TCP **不会丢弃**它，而是暂存到内核的**乱序队列**（Linux 中以红黑树组织），同时立即回复携带 SACK 块的重复 ACK 提醒发送方补发空洞，待缺失数据到达后再一并按序交付应用层；只有落在接收窗口之外或已确认重复的报文才会被丢弃。

Web 服务器生成 HTTP 响应报文后，反转源/目的地址沿路返回，浏览器收齐资源并完成 HTML/CSS/JS 解析与页面渲染。

## 1.3 Linux 内核收发网络包全路径 {#ch1-3}

了解端到端通信后，再将视角切入单台 Linux 6.12 主机内部，观察一个数据包如何穿越网卡驱动、中断子系统与内核协议栈。本节侧重从网络协议栈职责与收发路径保持专题独立可读性；若希望进一步串联内核底层完整收包细节、零拷贝（`sendfile`/SG-DMA/kTLS）与 `epoll`/`io_uring` 模型，可对照[《图解系统》第 7 章](../system/chapter-07#ch7-1)。

### 1.3.1 `struct sk_buff`：跨层零拷贝封装的关键 {#ch1-3-1}

如果传输层、网络层与链路层各自维护独立结构体并在跨层时拷贝载荷，高并发下 CPU 内存带宽将瞬间耗尽。Linux 内核统一使用 **`struct sk_buff`（Socket Buffer）** 描述贯穿全协议栈的网络包，仅通过移动内部指针 `skb->data` 实现原地加/脱协议头：

```text
+------------+----------+---------+---------+---------------------+-----------+
|  headroom  |  MAC 头  |  IP 头  |  TCP 头 |      应用层载荷      |  tailroom |
+------------+----------+---------+---------+---------------------+-----------+
^            ^          ^         ^         ^                     ^           ^
head       <── 发包时减小 skb->data 写各层头   ──> 收包时增大 skb->data 剥离头   end
```

- **发送方向**：内核申请缓冲区时预先在数据前方留出足够的 `headroom`；从 TCP 层向下走到 IP 层、链路层时，依次调用 `skb_push()` **减小 `skb->data`**，直接在预留空间填入 TCP 头、IP 头与 MAC 头。
- **接收方向**：从网卡驱动向上走到链路层、IP 层、TCP 层时，依次调用 `skb_pull()` **增大 `skb->data`**，直接跳过各层协议头定位到应用载荷。

### 1.3.2 接收路径：DMA、NAPI 与软中断校准 {#ch1-3-2}

```text
物理网卡 ──DMA直写预分配内存页──> RX Ring Buffer ──硬中断(关闭该队列IRQ)──> 触发 NET_RX 软中断
  ──> irq_exit() 直接执行 napi_poll() (超预算才唤醒 ksoftirqd) ──> 链路层 / IP 层 / TCP 层
  ──> 放入 Socket 接收缓冲区 ──> 唤醒用户进程 read()/epoll_wait() 拷贝至用户态
```

需要重点纠正原书 2.3 节的三处内核机制偏差：

1. **RX Ring Buffer 收包不发生整包内存拷贝**：网卡驱动初始化时已预先分配好内存页（`page pool` / 接收缓冲）并将物理地址填入 RX Ring Buffer 描述符。数据包到达时，网卡通过 **DMA 直接写入这些内存页**；内核收包时只需摘取缓冲构建 `sk_buff` 元数据并补充新空闲页，无需从 Ring Buffer 再拷贝一份到 `sk_buff`。
2. **NAPI 硬中断中不能立刻恢复中断**：原书 2.3 节称硬中断处理函数“屏蔽中断 → 发起软中断 → 然后恢复刚才屏蔽的中断”，**这是错误的**。Linux 引入 **NAPI（中断 + 轮询混合）**正是为了消除高流量下的中断风暴：首个数据包触发硬中断后，驱动**屏蔽该队列的网卡硬中断**并触发 `NET_RX` 软中断；随后软中断回调驱动的 `napi_poll()` 批量拉取数据包（受单次 `budget` 限制，默认 64 包），**直到把 RX 队列收空之后，才由 `napi_poll()` 重新打开网卡硬中断**。若在硬中断结束时就立刻恢复中断，NAPI 将彻底退化为“每包一次中断”。
3. **`NET_RX` 并非总在 `ksoftirqd` 中执行**：原书表述容易让人误以为软中断始终交给 `ksoftirqd` 线程处理。实际上，Linux 优先在硬中断返回路径 **`irq_exit()` 的软中断上下文中就地执行**（响应最快）；只有当单轮处理超过预算时间（如 2 ms）或循环次数上限仍未收完时，才将剩余工作转交给每核绑定的 **`ksoftirqd/N`** 内核线程继续处理，防止饿死用户态进程。

### 1.3.3 发送路径、内存拷贝辨析与现代加速 {#ch1-3-3}

发送流程沿协议栈自顶向下推进：

1. 应用程序调用 `send()`/`write()` 陷入内核，将用户态数据**拷贝（第 1 次真实数据拷贝）**到内核 Socket 发送缓冲区的 `sk_buff` 中。
2. **TCP 层的 `skb_clone()` 辨析**：TCP 必须保留原始报文直至收到对端 ACK 以便重传，因此传递给 IP 层的是一个副本。但需要纠正原书“这是第 2 次数据内存拷贝”的笼统说法——Linux 内核调用的是 **`skb_clone()`**，它**仅复制约 200 多字节的 `sk_buff` 元数据结构体，底层实际数据载荷通过引用计数共享，不发生载荷内存拷贝**！
3. **TSO/GSO 替代 IP 分片**：传统协议栈在 TCP 层按 MSS 切分，现代 Linux 默认开启 **TSO（TCP Segmentation Offload）/ GSO**，允许协议栈把长达 64 KB 的大块合并报文一路送到网卡驱动，交由网卡硬件在发出前自动按 MSS 切分并重算校验和，大幅削减协议栈开销，同时避免低效的 IP 层分片。
4. IP 层查路由、经 `netfilter`（`nftables`/`iptables`）过滤，链路层查 ARP 填 MAC 头，放入流量控制队列 **`qdisc`**。队列空闲时发送线程可直接同步驱动网卡发送；队列繁忙时触发 `NET_TX` 软中断异步调度。
5. 驱动将 `sk_buff` 数据地址挂入 **TX Ring Buffer** 并通知网卡通过 **DMA** 发出；发送完成后网卡触发硬中断并经 `NET_TX` 回收克隆的 `sk_buff` 元数据；待收到对端 TCP ACK 后，传输层才最终释放原始 `sk_buff` 与载荷内存。

**现代高速网络三大加速演进**：
- **RSS（Receive Side Scaling）**：多队列网卡按五元组哈希将不同连接的数据包分散到多个 RX 队列与不同 CPU 核心并行处理，避免单核 `NET_RX` 软中断打满（可用 `ethtool -l` 查看队列数）。
- **eBPF / XDP（eXpress Data Path）**：在网卡驱动收到帧、**尚未分配 `sk_buff`** 的最早期阶段执行受验证的 eBPF 程序，实现纳秒级丢包（如抗千万 PPS DDoS）或直通转发。
- **零拷贝与 kTLS**：静态文件发送可通过 `sendfile()` + SG-DMA 彻底省去用户态拷贝；开启 **Linux kTLS（4.13+）** 后，HTTPS 加密连接也能继续享受内核态零拷贝发送。

## 练习 {#ch1-exercises}

本节包含 4 道递进练习，依次覆盖封装开销与 MSS 计算、跨网段 MAC/IP 地址变化追踪、交换机/路由器行为判别及 Linux 协议栈收发机制辨析。请先独立推演，再展开参考答案核对。

### 练习 1：计算以太网下的 MTU、MSS 与有效载荷占比

假设一条标准以太网链路（MTU = 1500 字节）承载 IPv4（无选项，20 字节）与 TCP（开启 12 字节 Timestamps 选项，总长 32 字节）流量，且数据链路层以太网帧头占 14 字节、FCS 占 4 字节（忽略前导码与帧间隙）：

1. 该连接协商后的 **MSS** 应为多少字节？
2. 满载发送单个 TCP 段时，链路层单个以太网帧的总长度是多少字节？应用层有效载荷占该以太网帧总长度的比例约为多少？
3. 如果改用 **IPv6**（固定首部 40 字节，同样开启 12 字节 TCP Timestamps），MSS 会变为多少字节？

<details>
<summary>查看参考答案</summary>

1. **IPv4 下的 MSS**：
   - MTU（1500 B）不包含以太网帧头和 FCS，仅包含 IP 头 + TCP 头 + 应用数据。
   - 因此 `MSS = 1500 - 20 (IPv4) - 32 (TCP 含 Timestamps) = 1448 字节`（注：TCP 三次握手通告的 MSS 字段通常按基本头计算填 `1460`，Linux 发送时自动减去 12 B Timestamps 选项，实际单段载荷为 `1448` B）。
2. **以太网帧总长度与有效载荷占比**：
   - 帧总长度 = `14 (MAC头) + 1500 (IP包) + 4 (FCS) = 1518 字节`。
   - 有效载荷占比 = `1448 / 1518 ≈ 95.39%`。
3. **IPv6 下的有效 MSS**：
   - `1500 - 40 (IPv6) - 32 (TCP 含 Timestamps) = 1428 字节`（握手中基础 MSS 通告为 `1500 - 40 - 20 = 1440` 字节）。

</details>

### 练习 2：追踪跨网段请求中 IP 与 MAC 地址的逐跳变化

主机 A（IP `10.0.1.10/24`，MAC `AA`）访问公网服务器 B（IP `203.0.113.50`，MAC `BB`）。路径拓扑如下（假设全程**无 NAT**）：

```text
主机 A (10.0.1.10 / AA) ──> 二层交换机 S1 ──> 路由器 R1 (LAN: 10.0.1.1 / R1_L; WAN: 198.51.100.1 / R1_W)
  ──> 路由器 R2 (WAN: 198.51.100.2 / R2_W; LAN: 203.0.113.1 / R2_L) ──> 服务器 B (203.0.113.50 / BB)
```

请填写数据包在以下三个链路位置时的**源 IP、目的 IP、源 MAC、目的 MAC**：
1. 离开交换机 S1 发往路由器 R1 时；
2. 离开路由器 R1 发往路由器 R2 时；
3. 离开路由器 R2 发往服务器 B 时。

<details>
<summary>查看参考答案</summary>

| 链路位置 | 源 IP | 目的 IP | 源 MAC | 目的 MAC | 关键依据 |
| --- | --- | --- | --- | --- | --- |
| **1. S1 → R1** | `10.0.1.10` | `203.0.113.50` | `AA` | `R1_L` | 主机 A 查路由表发现跨网段，ARP 解析默认网关 `10.0.1.1` 得到 `R1_L`；二层交换机 S1 原样转发不改任何地址 |
| **2. R1 → R2** | `10.0.1.10` | `203.0.113.50` | `R1_W` | `R2_W` | 路由器 R1 剥离旧 MAC 头，TTL 减 1，查路由表将下一跳定为 R2 WAN 口，重新封装为 `R1_W → R2_W` |
| **3. R2 → B** | `10.0.1.10` | `203.0.113.50` | `R2_L` | `BB` | 路由器 R2 发现目的 IP 在直连子网 `203.0.113.0/24`，通过 ARP 获取服务器 B 的 `BB`，重新封装后发出 |

**规律总结**：无 NAT 时源/目的 IP 全程不变；源/目的 MAC 每经过一台三层路由器就更换一次。

</details>

### 练习 3：识别两处关于 Linux 收发包的常见错误说法

某技术文档中关于 Linux 网络收发包有以下两段描述，请精准指出其中的错误并给出正确机制：

> 描述甲：“当网卡收到一个数据包触发硬中断后，硬中断处理函数会屏蔽中断、触发 `NET_RX` 软中断并立刻恢复中断，随后由 `ksoftirqd` 内核线程把数据从 Ring Buffer 拷贝到新分配的 `sk_buff` 中。”
>
> 描述乙：“TCP 发送数据时，从传输层进入网络层必须把整个应用数据再拷贝一份新的 `sk_buff` 副本以备重传，因此常规 `send()` 至少有两次完整的数据内存拷贝。”

<details>
<summary>查看参考答案</summary>

- **描述甲包含三处错误**：
  1. **中断恢复时机错误**：NAPI 在硬中断中屏蔽网卡队列中断后**不会立刻恢复**，而是等到 `napi_poll()` 将 RX Ring Buffer 中的数据包批量收空后，才重新开启该队列的硬中断。
  2. **软中断执行主体不准确**：`NET_RX` 软中断优先在硬中断退出的 **`irq_exit()` 软中断上下文中直接执行**；只有超出处理预算（包数或时间片）仍有剩余数据包时，才唤醒 `ksoftirqd` 线程兜底。
  3. **RX Ring Buffer 无整包拷贝**：网卡驱动预先分配好内核内存页填入 Ring Buffer，网卡收包直接通过 DMA 写入这些内存页，收包流程只需组装 `sk_buff` 元数据，不需要将整个数据包从 Ring Buffer 拷贝到 `sk_buff`。
- **描述乙包含一处核心错误**：
  - TCP 传输层交由网络层发送时，调用的是 **`skb_clone()`**——它**只克隆轻量级的 `sk_buff` 结构体元数据**，原始 `sk_buff` 与克隆体通过引用计数共享同一块底层载荷数据内存，**不会拷贝应用数据载荷**。因此常规 `send()`（不触发 IP 分片且未用零拷贝时）只发生 **1 次 CPU 内存拷贝**（用户态 → 内核 Socket 缓冲）加 1 次网卡 DMA 发送。

</details>

### 练习 4：分析二层交换机首次通电时的转发行为

一台刚清空 MAC 地址表的 4 口二层交换机分别连接了主机 A（口 1，MAC `AA`）、主机 B（口 2，MAC `BB`）、主机 C（口 3，MAC `CC`）。现在主机 A 向主机 B 发送了一个单播以太网帧（源 MAC `AA`，目的 MAC `BB`），随后主机 B 向主机 A 回复了一个单播帧。请写出这两步中交换机的转发端口与 MAC 地址表变化。

<details>
<summary>查看参考答案</summary>

1. **A → B（源 `AA`，目的 `BB`）**：
   - 交换机从 **口 1** 收到帧，首先学习源地址：将 **`AA → 口 1`** 写入 MAC 地址表。
   - 查询目的地址 `BB`，表中未命中（未知单播），于是将该帧向除入端口 1 之外的**口 2、口 3（及所有其他活跃端口）泛洪**。
   - 主机 C 收到后比对目的 MAC 不匹配直接丢弃；主机 B 匹配接收。
2. **B → A（源 `BB`，目的 `AA`）**：
   - 交换机从 **口 2** 收到回复帧，学习源地址：将 **`BB → 口 2`** 写入 MAC 地址表。
   - 查询目的地址 `AA`，命中 **`AA → 口 1`**，于是**仅向口 1 单播转发**，不再泛洪。

</details>

## 面试题 {#ch1-interview}

本节精选 5 道高频网络基础面试题，覆盖分层边界、设备差异与 Linux 协议栈核心原理；请先独立作答，再展开核对。

### 面试题 1：既然有了 IP 地址，为什么还需要 MAC 地址？或者反过来，只有 MAC 地址行不行？

<details>
<summary>查看参考答案</summary>

**结论**：两者承担不同层级的职责——**MAC 地址扁平无层次，适合局域网内相邻两跳交付；IP 地址具有网络号/主机号层次结构，支持跨网段路由聚合与寻址**，缺一不可。

**关键依据**：
- **只有 MAC 地址不行**：MAC 地址由厂商烧录固化（前 24 位 OUI 表示厂商，与设备所处地理位置或网络拓扑毫无关系）。如果全球互联网直接按 MAC 寻址，每台路由器都必须保存全球数十亿台设备的扁平路由表，内存与查表开销彻底不可扩展。
- **只有 IP 地址不够**：IP 负责跨网络的“端到端导航”，而在以太网/Wi-Fi 等共享链路介质中，网卡硬件帧识别、局域网交换机二层转发以及未分配 IP 阶段（如 DHCP 发现）均依赖链路层 MAC 地址完成“相邻两跳交付”。

</details>

### 面试题 2：在“键入网址到网页显示”的过程中，如果服务器收到一个乱序到达的 TCP 数据包，会直接把它丢弃吗？

<details>
<summary>查看参考答案</summary>

**结论**：**不会直接丢弃**（只要该报文段落在接收窗口内且有效）。

**关键依据**：
- 当 TCP 接收端收到序号大于期望值 `RCV.NXT`、但仍在当前接收窗口 `[RCV.NXT, RCV.NXT + RCV.WND)` 内的乱序报文段时，内核会将其缓存到**乱序队列**（Linux 内核使用红黑树 `out_of_order_queue` 维护），同时回复携带期望序号的重复 ACK（开启 SACK 时附带已收乱序区间），以便发送方只重传缺失空洞而无需重发已到达的乱序段。
- 只有落在接收窗口之外、已确认重复、校验和错误或内存极度受限（触发 `TCPOFODrop`）时才会丢弃。

</details>

### 面试题 3：Linux 网络协议栈为何在各层加头和剥头时不需要反复整包拷贝数据？

<details>
<summary>查看参考答案</summary>

**结论**：Linux 内核用统一的 **`struct sk_buff`** 贯穿整个网络协议栈，仅通过前后移动数据指针 **`skb->data`** 完成各层首部的添加与剥离。

**关键依据**：
- 发送时内核预先在载荷前预留充足 `headroom`，经 TCP、IP、链路层时依次调用 `skb_push()` 减小 `skb->data` 原地写入头部；
- 接收时自底向上依次调用 `skb_pull()` 增大 `skb->data` 跳过帧头、IP 头、TCP 头；数据载荷始终停留在原内存页中。

</details>

### 面试题 4：Linux NAPI 机制如何解决高吞吐场景下的网卡中断风暴？

<details>
<summary>查看参考答案</summary>

**结论**：NAPI 采用**“硬中断唤醒 + 软中断批量轮询”混合模式**，在流量突发时暂时关闭网卡硬中断，将“每包一次中断”收敛为“一次中断批量收割数十个包”。

**关键依据**：
- 首个数据包通过 DMA 写入 RX Ring Buffer 后触发硬中断，驱动立即**屏蔽该队列的硬中断**并调度 `NET_RX` 软中断；
- `NET_RX` 在 `irq_exit()`（或超预算后在 `ksoftirqd`）中循环执行 `napi_poll()` 批量收包，直到把 Ring Buffer 取空后才重新开启网卡硬中断，极大降低了中断上下文切换开销。

</details>

### 面试题 5：为什么说“四层负载均衡”转发的是 TCP/UDP，而“七层负载均衡”转发的是 HTTP？TCP/IP 模型明明只有四层。

<details>
<summary>查看参考答案</summary>

**结论**：这里的“四层”和“七层”沿用的是 **OSI 七层参考模型**的层号，而非 TCP/IP 四层模型。

**关键依据**：
- 在 OSI 七层模型中，第 4 层为**传输层**（TCP/UDP），四层负载均衡（如 LVS）仅解析到 IP+端口级别即可转发或做 NAT，性能极高但无法识别 URL、Cookie 或 Host；
- 第 7 层为**应用层**（HTTP/HTTPS/gRPC），七层负载均衡（如 Nginx、Envoy）需要终止客户端 TCP/TLS 连接并解析应用层报文，才能实现按路径路由、灰度分流与 WAF 防护。

</details>
