# 第 1 章 并发缺陷、内存模型与 CSP 建模

## 本章要点

编写并发程序真正的难点不在于启动协程的语法，而在于缺少时序与可见性约束时，看似正确的代码会在高负载或特定硬件调度下暴露出隐蔽缺陷。本章首先从阿姆达尔定律出发，界定并发加速比的理论上限，辨析开发者最易混淆的“数据竞争”与“竞争条件”以及原子性的作用域相对性；接着对比死锁、活锁与饥饿三类活性故障的成因与破解路径；随后给出日常核验跨协程内存可见性必查的 Go 内存模型 `happens-before` 规则表；最后回到通信顺序进程（CSP）思想，建立通道与互斥锁的工程选型决策框架。

> 核对日期：2026 年 11 月 17 日；核对环境为 Go 1.27.4、Linux/AMD64。

## 1.1 阿姆达尔定律与原子性边界 {#ch1-1}

### 1.1.1 阿姆达尔定律与并发、并行职责分层 {#ch1-1-1}

摩尔定律单核频率增长放缓后，多核与分布式横向扩展成为提升算力的主航道，但并行化收益始终受制于 **阿姆达尔定律（Amdahl's Law）**。设程序中可并行化部分占比为 `P`，必须串行执行部分占比为 `1 - P`，投入 `N` 个处理器核心时的理论最大加速比为：

```text
S(N) = 1 / ((1 - P) + P / N)
```

当核心数 `N` 趋近无穷大时，加速比上限收敛于 `1 / (1 - P)`：若一段任务有 `20%` 的逻辑必须串行同步（如全局锁竞争、结果顺序聚合或人工交互等待），即便堆叠上百核，整体提速也绝不会超过 `5` 倍；反之，各分片互不依赖的“易并行问题（Embarrassingly Parallel）”可随核心数与节点数近乎线性横向扩展。

在代码建模层面，原书强调了一条核心边界：**并发（Concurrency）属于代码结构属性，并行（Parallelism）属于运行期物理属性**。我们编写的是将问题拆解为独立执行流的**并发代码**，至于这些执行流在单核 CPU 上分时交错推进，还是在多核 CPU 上真正同一时刻并行运转，由运行时调度器、操作系统与容器配额在底层透明决定。关于何时值得引入并发的基础判断详见[《Go 语言学习指南》13.1 节](../go-guide/chapter-13#ch13-1)。

### 1.1.2 竞争条件 vs 数据竞争与原子性作用域 {#ch1-1-2}

排查并发正确性缺陷时，必须严格区分两个不等价的概念：

- **数据竞争（Data Race）**：两个及以上 Goroutine 在**缺乏同步机制**的前提下并发访问同一内存地址，且至少一方为写入操作。数据竞争属于明确的破坏性缺陷，可通过 `-race` 检测器捕获，详见[基准测试与 `-race` 检测](../go-guide/chapter-17#ch17-4-2)。
- **竞争条件（Race Condition，又称逻辑竞态）**：两个及以上操作必须按特定相对顺序执行才能保证业务正确，但程序并未约束该顺序。

**消除了数据竞争，绝不等于消除了竞争条件。** 观察原书第 1 章的经典反例（按需导入 `"fmt"` 与 `"sync"`）：

```go
var mu sync.Mutex
var value int

go func() {
	mu.Lock()
	value++
	mu.Unlock()
}()

mu.Lock()
if value == 0 {
	fmt.Printf("the value is %d\n", value)
} else {
	fmt.Printf("the value is %d\n", value)
}
mu.Unlock()
```

互斥锁 `mu` 保护了每一处临界区（Critical Section），运行 `go run -race` 不会报出任何数据竞争；但后台协程与主协程谁先抢到锁依然完全随机，输出可能是 `0` 也可能是 `1`。同理，在协程启动后插入 `time.Sleep(time.Second)` 只是用拉低吞吐的代价改变调度概率，永远无法把概率巧合变成逻辑正确。

这引出了**原子性**（Atomicity）的核心准则：**操作的原子性取决于所定义的上下文（作用域）**。一句看似不可分割的 `i++`，在机器指令上下文中至少包含“读取 `i` → 寄存器加 1 → 写回 `i`”三步；在单协程局部变量的上下文中它是原子的，一旦暴露给多协程上下文就不再原子。此外，**若干个独立原子操作顺序拼合在一起，并不会自动构成更大的原子操作**——若 `GetBalance()` 与 `Deduct()` 各自内部加锁，两步之间仍会被其他协程插队扣成负数，必须将“检查并扣减”收拢进同一个原子作用域。

## 1.2 死锁、活锁与饥饿对照诊断 {#ch1-2}

即便通过同步消除了数据错乱，并发程序仍可能陷入无法正常推进工作的三类**活性（Liveness）故障**。

### 1.2.1 三类活性故障特征与 Coffman 死锁四条件 {#ch1-2-1}

死锁、活锁与饥饿的线上表象与处置方向对照如下：

| 故障类型 | 核心定义 | 线上进程与 CPU 表象 | 典型诱因与根治手段 |
| --- | --- | --- | --- |
| **死锁（Deadlock）** | 所有相关协程彼此等待对方释放资源，无外力干预永不恢复 | 全局死锁触发 `fatal error` 退出；**局部死锁进程存活但相关接口永久卡死，相关协程 CPU 为 0%** | 多把锁交叉加锁、无缓冲通道收发失配；需破坏任一 Coffman 条件 |
| **活锁（Livelock）** | 协程仍在主动执行指令并响应信号，但系统业务状态原地踏步 | **进程不报错且 CPU 利用率居高不下**，吞吐指标却跌至零 | 无协调的对等退让或碰撞重试；需引入**随机退避抖动**（Jitter）或主从非对称协调 |
| **饥饿（Starvation）** | 一个或多个协程长期抢不到执行所需的锁、CPU 或 I/O 资源 | 整体有产出，但部分任务尾延迟极高或完成计数远低于预期 | 贪婪协程粗粒度长持锁、无界并发抢占共享资源；需缩小临界区并监控分位耗时指标 |

需要注意，Go 运行时仅在**进程内全部 Goroutine 均处于休眠阻塞**时才能报出 `all goroutines are asleep - deadlock!`；只要后台还有一个定时器、HTTP 监听协程或健康检查协程在运转，业务子图的局部死锁就会静默挂起，线上排查方式见 [5.4 节](./chapter-05#ch5-4)。

1971 年 Edgar Coffman 总结了死锁成立的四个**同时具备**的必要条件（**Coffman 条件**）：

1. **互斥（Mutual Exclusion）**：并发参与者独占持有资源，排斥其他参与者同时访问。
2. **持有并等待（Hold and Wait）**：参与者已持有一项资源，同时阻塞等待获取额外资源。
3. **不可抢占（No Preemption）**：已持有的资源只能由持有者主动释放，外部无法强行剥夺。
4. **循环等待（Circular Wait）**：参与者 `P1` 等待 `P2` 持有的资源，而 `P2`（或经链路）同时等待 `P1` 持有的资源。

工程上预防死锁只需**打破上述四个条件中的任意一条**。例如 `printSum(&a, &b)` 与 `printSum(&b, &a)` 因加锁顺序相反触发循环等待死锁时，最通用的破解法是为锁关联的资源定义全局唯一偏序（如按账户 ID 或内存地址从小到大加锁），直接消除“循环等待”。

### 1.2.2 活锁走廊效应与粗粒度锁饥饿 {#ch1-2-2}

**活锁**常源于“试图在缺乏中心协调的情况下规避死锁”，典型如原书中的**走廊让路效应（Hallway Shuffle）**：两人在狭长走廊迎面相遇，同时向左侧让步撞上，又以相同节拍同时向右侧让步再次撞上。在分布式锁抢占、CAS 自旋冲突或网络包碰撞重传中，若各方采用固定且相同的重试周期，就会陷入高 CPU 空转的活锁；标准解法是引入**指数退避加随机抖动**或按节点优先级打破对称性。

**饥饿**则往往暴露了临界区粒度失衡。原书对比了两类总工作量相同的协程：

- **贪婪协程（Greedy Worker）**：一把锁包住整个三阶段耗时循环，减少自身加解锁次数，却长期霸占共享锁；
- **平和协程（Polite Worker）**：仅在真正触碰共享状态的子步骤加锁，用完即放。

在原书实测中，贪婪协程在相同时长内完成的循环数是平和协程的近两倍，实质是通过不必要地扩大临界区饿死了协作同伴。虽然自 Go 1.9 起标准库为 `sync.Mutex` 引入了 **1ms 饥饿模式**——当等待者阻塞超过 `1ms` 时，锁所有权直接从解锁协程移交给等待队列队首，禁止新到协程插队自旋抢锁——但数据库连接、磁盘 I/O 与自定义资源池仍会发生饥饿。性能调优应遵循“**先将锁严格收窄在最小临界区，仅当实测证明加解锁本身成为瓶颈时再谨慎合并**”的原则。

## 1.3 Go 内存模型与 happens-before 速查 {#ch1-3}

在缺乏同步事件约束时，编译器指令重排与多核 CPU 写缓冲（Store Buffer）会导致协程 `G1` 对变量的写入无法按源码顺序被协程 `G2` 观测到。Go 官方《Go 内存模型》用偏序关系 **先行发生（`happens-before`）** 严格定义了内存可见性：仅当写事件 `W` 先行发生于读事件 `R`，且中间无其他写入覆盖时，`R` 才被**保证**读到 `W` 写入的值。

日常并发编码依赖的全部标准同步 `happens-before` 保证汇总如下：

| 同步原语 / 事件 | 严格保证的 `happens-before` 顺序关系 | 常见误区与工程应用 |
| --- | --- | --- |
| **Goroutine 创建** | `go` 语句本身 **先行发生于** 新 Goroutine 开始执行 | 创建前已写入的变量在子协程内安全可见（前提是此后不再并发修改） |
| **Goroutine 退出** | **无任何隐式 `happens-before` 保证！** | 不借助通道、锁或 `WaitGroup` 汇合时，外层裸读子协程写入的变量属数据竞争 |
| **通道发送 → 接收** | 向通道第 `k` 次发送 **先行发生于** 对应第 `k` 次接收**完成** | 无论有缓冲还是无缓冲，发送前构造的数据在接收方拿到元素后完整可见 |
| **通道关闭 → 接收** | `close(ch)` **先行发生于** 因通道已关闭而读出零值的接收完成 | 支撑 `close(done)` 广播取消信号前的状态写入对所有监听协程可见 |
| **无缓冲通道接收 → 发送** | 无缓冲通道的**接收操作 先行发生于 对应发送操作完成** | 注意看似“反直觉”的措辞：是**接收开始配对**先行于**发送语句返回**，保证握手同步 |
| **容量为 `C` 的缓冲通道** | 第 `k` 次接收 **先行发生于** 第 `k + C` 次发送**完成** | 赋予缓冲信号量内存安全性：`sem <- struct{}{}` 获取槽位，`<-sem` 释放槽位，最多 `C` 个在途任务 |
| **`Mutex` / `RWMutex`** | 锁变量 `l` 的第 `n` 次 `Unlock()` **先行发生于** 第 `m` 次（`m > n`）`Lock()` 返回 | `RWMutex` 中释放写锁 `Unlock` 先行于后续 `RLock` 返回；释放读锁 `RUnlock` 先行于后续写锁 `Lock` 返回 |
| **`sync.Once`** | `once.Do(f)` 中单次 `f()` 执行完成 **先行发生于** 任意并发调用方的 `once.Do(f)` 返回 | 保证所有协程从 `Do`（或 `OnceValue`）返回后立即安全读取初始化结果 |
| **`sync/atomic`（Go 1.19+）** | 原子读操作 `R` 若观测到原子写操作 `W` 的值，则 `W` **同步先行发生于** `R` | 遵循顺序一致性（Sequential Consistency），可用于无锁发布不可变配置指针 `atomic.Pointer[T]` |

上表中最易写反的是缓冲通道信号量：由于规范保证的是“第 `k` 次**接收**先行发生于第 `k + C` 次**发送完成**”，只有用**发送获取令牌（满时阻塞）、接收归还令牌**，才能天然从零空槽起步并建立正确的释放→再获取内存屏障，具体实现见[学习指南 13.3.1 节](../go-guide/chapter-13#ch13-3-1)。

## 1.4 CSP 建模、并发契约与同步选型决策 {#ch1-4}

1978 年 Tony Hoare 在《Communicating Sequential Processes》（CSP）论文中提出：**输入与输出不该只是边缘辅助函数，而应作为并发建模的一等公民原语**，并结合 Dijkstra 的守护命令（Guarded Commands）将独立顺序进程通过端口连接起来。Go 直接继承了这一思想——无需像传统语言那样手工估算 OS 线程池大小并维护遍布对象图的锁，而是按问题域自然拆出轻量级 Goroutine，用通道传递数据所有权、用 `select` 组合多路事件。

暴露任何可能涉及并发的导出函数或类型前，必须通过**类型签名或文档注释**向调用方明确回答**并发安全三问契约**：

1. **谁负责启动并发？**——函数内部已自行并发扇出，还是保持同步执行、交由调用方按需加 `go`？
2. **问题域如何映射到并发原语？**——例如返回只读通道 `<-chan T` 即可直观宣告内部已启动后台生产协程。
3. **谁负责内存访问同步？**——传入结构体指针时，是类型自身内部持锁并发安全，还是要求调用方在外部串行化？

Go 同时提供 CSP 通道与 `sync` 内存访问同步原语，原书第 2 章给出了按序判断的**四步决策树**，基础原语对照另见[学习指南 13.4 节](../go-guide/chapter-13#ch13-4)：

| 决策步骤（自上而下依次判断） | 若回答为“是” | 关键依据与边界 |
| --- | --- | --- |
| **1. 是否经剖析确认属于极端性能瓶颈临界区？** | **使用 `Mutex` / `atomic`** | 通道自身在底层依赖互斥锁同步，纳秒级热点临界区用原语更快 |
| **2. 是否正在跨协程转让数据的所有权？** | **使用通道 `chan T`** | 保证同一时刻仅一个协程持有可变数据，支持队列解耦与类型约束 |
| **3. 是否在保护单个结构体的紧耦合内部状态？** | **使用 `Mutex` / `RWMutex`** | 将锁严格隐藏在类型内部，对外暴露干净的普通同步方法签名 |
| **4. 是否在协调多个逻辑片段、流水线或超时取消？** | **使用通道 `chan T`** | 通道配合 `select` 天然具备可组合性，跨对象拼装多把锁极易死锁 |

谨记两条反模式红线：一是**切勿把互斥锁暴露到结构体类型词法边界之外**，跨多模块拼装锁极易诱发循环等待死锁；二是**通道底层本身依赖运行时锁与队列同步**，保护纯内存映射或计数器时强套通道不仅更繁琐，吞吐也低于内聚的 `sync.Mutex` 或 `atomic`。

## 练习 {#ch1-exercises}

以下 2 道练习分别检验破坏 Coffman 循环等待条件消除双向死锁，以及依据 Go 内存模型修复跨协程可见性缺陷。代码默认位于 `package main`，按需导入 `"sync"`。建议先独立作答，再展开核对参考答案。

### 练习 1：按固定全序加锁修复双向并发转账死锁

已知账户结构体定义如下：

```go
type Account struct {
	ID      int // 全局唯一账户编号
	mu      sync.Mutex
	Balance int
}
```

若实现 `Transfer(from, to *Account, amount int) bool` 时直接依次执行 `from.mu.Lock()` 和 `to.mu.Lock()`，当两个协程同时调用 `Transfer(a, b, 50)` 与 `Transfer(b, a, 30)` 时会发生死锁。请编写无死锁、并发安全的 `Transfer` 函数：要求妥善处理 `from == to` 同账户边界，且余额不足时返回 `false`。

<details>
<summary>查看参考答案</summary>

```go
func Transfer(from, to *Account, amount int) bool {
	if amount <= 0 {
		return false
	}
	if from.ID == to.ID {
		return true
	}

	first, second := from, to
	if first.ID > second.ID {
		first, second = second, first
	}

	first.mu.Lock()
	defer first.mu.Unlock()
	second.mu.Lock()
	defer second.mu.Unlock()

	if from.Balance < amount {
		return false
	}
	from.Balance -= amount
	to.Balance += amount
	return true
}
```

**关键依据**：无论调用方向是 `(a, b)` 还是 `(b, a)`，比较全局唯一的 `Account.ID` 后始终先锁编号较小的一方、再锁编号较大的一方，从根源上破坏了 Coffman 四条件中的**循环等待**条件；前置判断 `from.ID == to.ID` 则避免了同一 Goroutine 对不可重入的 `sync.Mutex` 连续加锁两次导致自锁。

</details>

### 练习 2：利用 Go 内存模型修复无同步标志位可见性缺陷

分析以下并发初始化代码在 Go 内存模型下存在哪两处缺陷，并分别给出基于**无缓冲通道**和基于 **`atomic.Pointer`**（Go 1.19+）的正确无锁/轻量同步修复写法：

```go
var config map[string]string
var ready bool

func setup() {
	config = map[string]string{"env": "prod"}
	ready = true
}

func readEnv() string {
	go setup()
	for !ready {
	}
	return config["env"]
}
```

<details>
<summary>查看参考答案</summary>

**原代码两处核心缺陷**：

1. **存在数据竞争与可见性缺失**：`ready` 的读写没有任何同步原语保护，属数据竞争。按 Go 内存模型，编译器和 CPU 允许重排 `setup` 内的写入顺序，且编译器甚至可将空循环 `for !ready {}` 优化为死循环而不重新从内存加载 `ready`；即使 `readEnv` 偶然看到 `ready == true`，也不保证 `config` 的底层映射初始化对当前核心可见。
2. **忙等空转浪费 CPU**：`for !ready {}` 在等待期间紧占 CPU 空转。

**修复写法一——关闭通道建立单次汇合 `happens-before`**：

```go
func readEnvWithChan() string {
	var config map[string]string
	done := make(chan struct{})
	go func() {
		config = map[string]string{"env": "prod"}
		close(done) // config 写入先行发生于 close(done)，进而先行发生于 <-done 返回
	}()
	<-done
	return config["env"]
}
```

**修复写法二——`atomic.Pointer` 无锁发布不可变配置**：

```go
var cfgPtr atomic.Pointer[map[string]string] // 需导入 "sync/atomic"

func publishConfig() {
	m := map[string]string{"env": "prod"} // 发布后严禁原地修改 m
	cfgPtr.Store(&m)
}

func currentEnv() (string, bool) {
	p := cfgPtr.Load()
	if p == nil {
		return "", false
	}
	return (*p)["env"], true
}
```

关闭通道方案利用了“`close(ch)` 先行发生于接收零值返回”规则且等待时不消耗 CPU；`atomic.Pointer` 方案利用了 Go 1.19+ 原子操作的顺序一致性保证，`Store(&m)` 之前的映射初始化先行发生于读到非空指针的 `Load()`。

</details>

## 面试题 {#ch1-interview}

以下 3 道面试题聚焦竞态本质、通道内存屏障细节与线上三类活性故障排查。建议先独立作答，再展开核对参考答案。

### 面试题 1：程序中所有共享变量的读写都已经用 `sync.Mutex` 包裹且 `go test -race` 通过，是否就一定没有竞争条件（Race Condition）了？

<details>
<summary>查看参考答案</summary>

**不一定，仍然可能存在竞争条件（逻辑竞态）。**

`sync.Mutex` 与 `-race` 解决和检验的是底层的**数据竞争（Data Race）**，即防止多个协程在同一时刻无同步地并发读写同一块内存。但如果业务逻辑要求“先检查余额再扣款”却被拆成了两次独立的加解锁调用，或者主流程依赖两个并发子协程的特定先后完成顺序却未做显式汇合编排，程序在每次运行时的加锁先后顺序依然不确定，照样会算出错误业务结果。只有让**临界区范围完整覆盖业务不变量所需的原子上下文**，并在有因果依赖的步骤间建立显式 `happens-before` 同步，才能消除逻辑竞态。

</details>

### 面试题 2：在 Go 内存模型中，无缓冲通道的发送与接收满足怎样的 `happens-before` 关系？下面两段代码各自能否保证打印 `"hello, world"`？

```go
// 片段 A
var a string
c := make(chan int)
go func() {
	a = "hello, world"
	<-c
}()
c <- 0
print(a)

// 片段 B（仅将通道改为缓冲容量 1）
var b string
c2 := make(chan int, 1)
go func() {
	b = "hello, world"
	<-c2
}()
c2 <- 0
print(b)
```

<details>
<summary>查看参考答案</summary>

- **片段 A 严格保证打印 `"hello, world"`**；**片段 B 不保证（存在数据竞争，可能打印空字符串甚至崩溃）！**

**关键依据**：Go 内存模型规定了两方向规则：

1. 对任何通道，第 `k` 次**发送**先行发生于第 `k` 次**接收完成**；
2. 对**无缓冲通道**，第 `k` 次**接收**先行发生于第 `k` 次**发送完成**；更一般地，容量为 `C` 的通道满足第 `k` 次接收先行于第 `k + C` 次发送完成。

在片段 A 中，`c` 是无缓冲通道，子协程内的 `a = "hello, world"` 先行于 `<-c`，而无缓冲通道的 `<-c` **先行于主协程 `c <- 0` 发送完成返回**，因此主协程执行 `print(a)` 时必然能看到 `"hello, world"`。而在片段 B 中，`c2` 容量为 `1`，主协程 `c2 <- 0` 写入缓冲后无需等待接收方配对就立即返回执行 `print(b)`，与子协程的 `b = "hello, world"` 没有任何 `happens-before` 约束，构成数据竞争。

</details>

### 面试题 3：线上 Go 服务未崩溃重启，但某类请求大量超时，如何快速判断是发生了局部死锁、活锁还是饥饿？

<details>
<summary>查看参考答案</summary>

可结合 **CPU 利用率、业务吞吐指标与 `goroutine` 堆栈画像**三步定界：

1. **看关联协程状态与阻塞时长（判别局部死锁）**：抓取 `/debug/pprof/goroutine?debug=2`，详见 [5.4 节](./chapter-05#ch5-4)。若超时请求对应的协程全部长期卡死在 `sync.Mutex.Lock`、`chan receive` 或 `select` 上，阻塞分钟数持续增长且完全不消耗 CPU，属于**局部死锁**或通道泄漏挂起。
2. **看 CPU 与有效业务进展的比值（判别活锁）**：若进程 CPU 占用率很高、协程频繁调度运行或不断打印重试日志，但成功处理的请求计数长期为 `0`，说明多协程陷入了无协调互撞的**活锁**。
3. **看吞吐分布是否两极分化（判别饥饿）**：若系统整体仍有业务吞吐、部分任务飞快完成，唯独特定协程或尾部请求（P99/P999）迟迟拿不到锁或连接配额，采集 `mutex` / `block` 画像可见少数重任务长期霸占共享资源，即属于**饥饿**。

</details>
